# Журнал разрешения red-team (пакет v1.1 → v1.2)

**Дата:** 2026-07-10
**Вход:** red-team-прогон по модели угроз пакета (промпт враждебной роли, чистый контекст).
**Выход:** пакет v1.2 — надстройка над v1.1 без удаления и ослабления существующих норм.

Назначение журнала — трассировка: какая атака каким решением закрыта, что осознанно принято как остаточный риск, что отложено. Без этой таблицы следующий контролёр не отличит закрытое от забытого.

---

## Сводка

Прирост v1.1 → v1.2: **+4 ADR** (008–011), **+3 актора** (T5 инсайдер, T6 враждебное/дефектное приложение, T7 автоклиент), **+1 актив** (A7 источник случайности), **+14 требований**. Все находки — либо закрыты структурной нормой, либо осознанно приняты/отложены с обоснованием.

---

## Разрешения по векторам атаки

### Утечка скрытых данных механики (актив A1)
- **Вектор:** правильные ответы/веса кладутся в `appSettings` — категорию, которую уровни видимости v1.1 не проецировали; или приложение мислейблит `visibility` события, а ядро валидировало лишь форму payload.
- **Закрыто:** ADR-008 → REQ-CORE-008 (поле-уровневая видимость `appSettings`, fail-safe `module-private` по умолчанию, проекция ядром) + REQ-CTR-009 (ядро отклоняет фиксацию события с `visibility` слабее задекларированного для типа).
- **Класс решения:** структурная проверка ядром по всем трём каналам отдачи (конфиг, состояние, события). Перенос инварианта с доверия приложению на ядро.

### Честность арбитража «кто первый» (актив A3)
- **Вектор:** присуждение по «первому закоммитившему» вознаграждает субчеловеческую скорость бота (T7); под retry-контенцией размер payload влияет на исход гонки за seq — упреждающий клиент с минимальным payload обгоняет более раннего человека.
- **Закрыто:** ADR-009 → REQ-RT-013 (анти-упреждающий контроль: минимальный интервал «открытие раунда → приём» либо дискретное окно приёма, примитив окна от ядра) + REQ-RT-007 (payload-нейтральность присвоения seq, тест отсутствия смещения).
- **Отклонено осознанно:** proof-of-humanity/CAPTCHA на каждый ответ — непропорциональный удар по конверсии живого события; окно приёма закрывает вектор без фрикции для человека.

### Стойкость розыгрыша (актив A7 — новый)
- **Вектор:** предсказуемый ГПСЧ (сид от времени/seq) или клиентское влияние на сид → предсказание/смещение победителя (T6/T1).
- **Закрыто:** ADR-010 → REQ-RWD-011 (серверный CSPRNG, сид не из наблюдаемых участником величин, исход непредсказуем из доступного состояния).
- **Отложено:** REQ-RWD-012 публичная верифицируемость (VRF/commit-reveal) — под спрос на розыгрыши между недоверяющими удалёнными сторонами; вне продуктовой ставки MVP (живое событие в кругу знакомых).
- **Остаточный риск принят:** без верифицируемости инсайдер, контролирующий `winnerSelection`, технически способен сместить исход незаметно — принято для доверенного очного контекста, закрывается активацией отложенной фазы.

### Призовой фонд (актив A4)
- **Вектор:** конкурентная выдача N наград разным identity сверх `quantity` → перевыпуск фонда/уход quantity в минус; уникальность победителя и ограниченность фонда смешаны в одном требовании.
- **Закрыто:** REQ-RWD-010 (ограниченность фонда как отдельный DB-инвариант: атомарный ограниченный декремент + `CHECK (quantity >= 0)`) явно отделена от REQ-RWD-003 (единичность победителя через partial unique). Два разных инварианта — две разные нормы.

### Привилегированный инсайдер (актор T5 — новый)
- **Вектор:** скомпрометированный/сговорный MODERATOR устраняет конкурентов перед развязкой «первый побеждает» или срывает событие изнутри — концентрация влияния на A3/A5/A6 у не-владельца.
- **Закрыто:** ADR-011 → REQ-ID-018 (аудит действий модератора, rate-limit исключений, запрет/отсрочка исключения в критическом окне арбитража, право организатора на откат).

### Идентичность на стыках (активы A6, A2)
- **Вектор — kind-флип:** неопределённость жизненного цикла токена при привязке аккаунта гостём (GUEST→REGISTERED). **Закрыто:** REQ-ID-017 (переиздание токен-пары, инвалидация room-scoped гостевого токена).
- **Вектор — осиротение приза:** TTL гостя обнуляет имя победителя до вручения. **Закрыто:** REQ-RWD-013 (приостановка TTL при открытой `AWARDED`).
- **Вектор — раскрытие существования комнаты** при закрытой политике через различие ответов. **Закрыто:** REQ-ID-013 (неотличимый ответ «неверный код» и «верный код + закрытая политика» до установления членства).
- **Вектор — распределённый перебор кода** мимо per-IP лимита. **Закрыто:** REQ-ID-019 (глобальный backoff, не препятствующий входу по верному коду — исключён само-DoS).

### Доступность живого события (актив A5)
- **Вектор:** участник-флудер раздувает лог/эмиссию; reconnect-шторм одной identity удорожает восстановление для всех. **Закрыто:** REQ-RT-014 (хард rate-limit эмиссии per-actor, режим отказа для чувствительных комнат), REQ-RT-015 (reconnect rate-limit с бэкоффом, изоляция стоимости), REQ-RT-016 (запечатывание лога в терминальном статусе — инвариант ядра).

### Враждебное/дефектное приложение и supply-chain (актор T6 — новый)
- **Вектор:** app-модуль сам или через скомпрометированную зависимость мислейблит visibility, кладёт исход в проецируемую конфигурацию, использует слабый розыгрыш.
- **Закрыто распределённо:** REQ-CORE-008 + REQ-CTR-009 (ядро не доверяет разметке приложения) + REQ-RWD-011 (CSPRNG как норма, не выбор приложения). Инвариант «скрытое не утекает» и «розыгрыш непредсказуем» вынесены в ядро, вне зоны доверия приложению.

### Sybil-накрутка розыгрыша (актив A6 × T7)
- **Вектор:** размноженные гостевые identity набирают вес в розыгрыше.
- **Закрыто с осознанным дефолтом:** REQ-RWD-014 (атрибут `draw_eligibility`; при `verified` вес только у REGISTERED). Дефолт `guests_allowed` — риск Sybil для гостевого розыгрыша **принят осознанно**; штатное усиление для денежных призов в открытом доступе — организатор ставит `verified`.

## Замечания red-team, НЕ породившие изменений (переоткрытия и принятые риски)

Ожидаемо переоткрыты и не требуют действий (уже закрыты в v1.1 с явным принятием обходимости):
- Накрутка сменой устройства/сети мимо device-cookie+IP — REQ-ID-006 честно признаёт обходимость; штатный ответ — политика `registered`/`invite_only`.
- Обход per-IP через смену IP — усилен REQ-ID-019, но полное закрытие требует `verified` (REQ-RWD-014), что уже предусмотрено.

Эти пункты — не пробелы, а задокументированные границы защиты. Не сверять построчно как регресс.

---

## Оценка перекоса (ответ на вопрос владельца)

Внутри документа перекоса нет: каждый новый ADR отбивает переусложнённую альтернативу в «Отклонено», два тяжелейших контроля (VRF, proof-of-humanity) осознанно отложены/отклонены. Дефолты выбраны в пользу конверсии (`guests_allowed`), а не максимальной паранойи.

Перекос — на уровне процесса, не документа: центр тяжести проверок сместился целиком на ось «безопасность/корректность» (аудит + red-team), тогда как оси «юридика», «эксплуатация», «продукт» не проверены ни разу. Рекомендация — не третий круг безопасности, а смена оси контроля (см. дорожную карту §4). Соблазн ещё одного red-team-прогона по v1.2 даст убывающую отдачу при растущей цене откладывания юридического гейта.
