## §0. Решения владельца (brainstorm сессии 62)

1. **Комната рождается по явному действию** — кнопка «Создать событие» на setup-странице. Auto-mount-создание (факт открытия страницы → POST /rooms) умирает.
2. **Источник истины о «моих комнатах» — сервер**, не localStorage. Привязка `mm.host.roomId`/`mm.host.roomCode` упраздняется целиком.
3. **Отдельная страница-перечень «Мои события»** со списком комнат и их состояниями.
4. **Маршрутизация `/host`:** есть ACTIVE → сразу в консоль; иначе → перечень.
5. ~~**Перечень для MVP — только живые комнаты** (DRAFT + ACTIVE). COMPLETED/CANCELLED не показываются (история — не MVP).~~ **ПЕРЕСМОТРЕНО — см. №11.**
6. **Порогов по времени нет.** Первоначальная идея «TTL 30 мин + вопрос» отменена: выбор «удалить или продолжить» всегда за человеком, явно в строке перечня. Никаких env-порогов.
7. **«Продолжить» ведёт в редактор этой комнаты** (не в консоль — консоль DRAFT это тупик Н3).
8. **DRAFT — с наполнением:** редактор сохраняет вопросы в комнату как черновик (configure без activate — сервер уже умеет, `room.service.ts` configure допустим в DRAFT), «продолжить» возвращает форму с наполнением на месте.
9. **Черновик сохраняется явной кнопкой «Сохранить черновик»** (автосейва нет). **Невалидный черновик не сохраняется** — серверная zod-валидация configure не ослабляется.
10. **Удаление DRAFT — мягкое (`deletedAt`)**, с inline-подтверждением в строке (без модалки). Санкционировано REQ-RT-005 («удаление допустимо в статусах DRAFT»). Гости, успевшие войти в удалённую DRAFT, отрезаются — принято (код раздаётся только из консоли активного события, гости в DRAFT экзотика).
11. **(Пересмотр №5, builder-check сессии 62): перечень включает COMPLETED.** COMPLETED-строка — со ссылкой **«В консоль»**: экран итогов с AwardsPanel (вручение/отзыв наград, REQ-RWD-009) обязан переживать перезагрузку и возврат спустя время — иначе вручение наград возможно только внутри живой сессии, что неприемлемо. Основание: снос localStorage-привязки (№2) убил единственный сегодняшний путь обратно в завершённую комнату. CANCELLED не показывается (в UI нет cancel-пути, такие комнаты не рождаются). Удаление в перечне — только у DRAFT; COMPLETED копятся по одной строке за событие.

## §1. Проблема

Три проявления одного дефекта (источник истины о комнате организатора — клиентский localStorage + создание комнаты по факту монтирования):

- **Накопление сирот:** auto-mount setup-страницы создаёт пустую DRAFT при каждом открытии `/host` с живым токеном без привязки (`setup-page.tsx:62-76`). На стенде приёмки — 7 DRAFT-сирот, включая `9945mcgy` (auto-mount при перелогине сессии 61) и призраки от смены LAN-origin (пустой localStorage на новом IP → гарантированная сирота).
- **Маршрутизация в мёртвую комнату (Н3-класс):** стейл-ключи localStorage заводят организатора в консоль DRAFT-тупика или отыгранной комнаты; выход — ручная хирургия `localStorage.removeItem` в консоли браузера (опыт сессий 54/61). Приёмке стенда это стоило прерванных проверок.
- **Невидимость:** сироты нигде не отображаются; владелец узнал о накоплении post factum.

Корневые факты кода: `Room.organizerId` в базе есть (packages/core/prisma/schema.prisma:40) — серверная модель «мои комнаты» осуществима без миграции связок; `Room.deletedAt` существует и REQ-RT-005 легализует удаление DRAFT; join гостей отклоняется только для COMPLETED/CANCELLED (`membership.service.ts:223`), т.е. DRAFT может иметь гостей (экзотика, см. §3.6).

## §2. Цели, не-цели, анти-цели

**Цели:**
1. Ноль пустых DRAFT от auto-mount: комната создаётся только по клику «Создать событие».
2. Невозможность попасть в консоль мёртвой комнаты: привязка серверная, стейл-ключи упразднены как класс.
3. Черновики управляемы с любого устройства и origin: перечень строится сервером.
4. Сироты видимы и удалимы (включая 7 уже существующих на стенде — они станут видны в перечне после выкатки).
5. Наполнение редактора переживает закрытие вкладки (черновик в комнате).

**Не-цели (MVP):**
- CANCELLED в перечне не показывается; глубокая история событий не делается (COMPLETED в перечне — по одной строке за событие, решение №11).
- Удаление COMPLETED из перечня (серверный softDelete это допускает — расширение UI за пределами среза).
- Пороги, TTL, серверная подметалка старых DRAFT (отменены решением №6).
- Автосейв редактора.
- Управление несколькими ACTIVE (фактически одно живое событие; §4).
- Изменения гостевых контуров (play/screen не трогаем).

**Анти-цели:**
- Молчаливое удаление чего-либо (потеря наполнения по таймеру — недопустима).
- Ослабление серверной валидации ради сохранения невалидных черновиков.
- Новый клиентский источник истины взамен localStorage (никаких «кэшей привязки»).

## §3. Дизайн

### 3.1 Сервер и контракт

Новые эндпоинты в transport-слое ядра (конвенции: `rooms.controller.ts` — POST /rooms; `rooms-lifecycle.controller.ts` — POST /rooms/:roomId/configure|activate|complete|cancel):

1. **GET /rooms/mine** — комнаты текущего организатора: `status IN (DRAFT, ACTIVE, COMPLETED) AND deletedAt IS NULL AND organizerId = <caller identity>` (набор статусов — решение №11). Только REGISTERED (гостю 403/типизированный отказ — REQ-ID-005). Элемент ответа: `{ roomId, code, status, appId, manifestVersion, appSettings, createdAt, updatedAt }`. `appSettings` включены сразу (уровень видимости organizer — запрашивающий и есть организатор, REQ-CORE-005/008 не нарушаются) — перечень и resume редактора обходятся одним вызовом.
2. **DELETE /rooms/:roomId** — мягкое удаление (`deletedAt = now()`), только DRAFT (серверный `RoomService.softDelete` существует и покрыт тестами — эндпоинт осознанно сужает `DELETABLE_STATUSES` до DRAFT, потому что UI удаляет только DRAFT). Ошибки: не-DRAFT → типизированный отказ (стиль `ROOM_TRANSITION_INVALID`); чужая/неизвестная/уже удалённая → единообразный NOT_FOUND (не раскрываем существование чужих комнат — дух REQ-ID-013). Событий в лог не эмитит (удаление — не статус, REQ-RT-005). ApiClient web-клиента сегодня умеет только GET/POST — расширение под DELETE + 204 (builder detail).

**SDK (ADR-006):** zod-схемы новых DTO — в `@mymozhem/sdk` (item-схема ответа mine; запросов без тела). Minor-бамп версии. Контрактные тесты из схем (REQ-CTR-005). Без них реализация не начинается (TDD).

**Миграций БД не требуется** — все поля существуют.

### 3.2 Гейт и маршрутизация

`host-gate-flow.ts` становится серверным: после проверки токена (REGISTERED, как сейчас) — GET /rooms/mine.

| Состояние комнат организатора | Цель `/host` |
|---|---|
| Есть ACTIVE (≥1) | консоль |
| Нет ACTIVE | перечень «Мои события» |
| Нет токена / гость | `/` (как сейчас) |
| GET /rooms/mine недоступен (сеть/5xx) | перечень с состоянием ошибки и повтором (fail-open к перечню, НЕ к консоли) |

localStorage-ветка `loadHostRoomId() ? console : new` умирает полностью.

### 3.3 Страница «Мои события» (новая)

Маршрут `/host/rooms` (константа в `routes.ts` по правилу «второй потребитель» — потребители: гейт, setup, COMPLETED-экран консоли). Консольная палитра (console.css), макет по одобренному мокапу (экраны 1–3):

- Полоса: лого + кнопка **«Новое событие»** (primary) → `/host/new`.
- Строка комнаты: бейдж статуса, заголовок («Квиз · N вопросов» для наполненной, «Без наполнения» для пустой; «Лотерея» для lottery), код, «создана/изменена». Действия DRAFT: **«Продолжить»** (secondary) → редактор; **«Удалить»** (danger-outline) → inline-подтверждение в той же строке («Удалить этот черновик? Восстановить будет нельзя.» — «Да, удалить» / «Отмена») → DELETE → строка исчезает.
- ACTIVE-строка в перечне практически недостижима (гейт уводит в консоль) — рендерится для полноты с кнопкой «В консоль».
- **COMPLETED-строка** (решение №11): бейдж «Завершено», заголовок по appId, дата; действие — **«В консоль»** (экран итогов + AwardsPanel; вручение наград после перезагрузки, REQ-RWD-009). Удаления у COMPLETED нет.
- Пустое состояние: «Живых событий нет.» + «Новое событие» (перечень с одними COMPLETED пустым не считается).
- Данные: GET /rooms/mine при монтировании и после каждой мутации; focus-рефетч — переиспользовать `createFocusRefetcher` (дисциплина Н13; см. §4).
- Ошибки — текст в стиле существующих маппингов (`submitErrorText`-прецедент): сеть/5xx → «Не удалось загрузить события. Попробуйте ещё раз.» + кнопка повтора.

### 3.4 Setup-страница и редактор

- **До рождения комнаты:** setup показывает кнопку **«Создать событие»** (и выбор приложения — квиз/лотерея). Клик → POST /rooms → редактор. Эффект auto-create (`setup-page.tsx:62-76`, включая ref-страховку StrictMode) удаляется — StrictMode-дубль перестаёт быть угрозой по построению.
- **Редактор:** два исхода внизу (мокап, экран 4):
  - **«Сохранить черновик»** (secondary) → `configureRoom` без activate. Требует валидной формы (решение №9): невалидно → те же поверхности ошибок, что у submit сегодня. После успеха — строка-статус «Черновик сохранён в HH:MM».
  - **«Сохранить и запустить»** (primary) → `configureRoom` → `activateRoom` → консоль (как сегодня).
  - После первого удавшегося configure выбор приложения блокируется (appId уже задан; смена типа наполненного черновика — не MVP).
- **Resume-режим:** «Продолжить» из перечня ведёт на setup с параметром комнаты (search-param, см. §4). Setup читает GET /rooms/mine, находит комнату, открывает редактор с prefill из `appSettings` (QuizEditor получает initial-settings проп) и зафиксированным appId. Пустая DRAFT → редактор с чистой формой и доступным выбором приложения.
- `useSessionWakeRefresh` на setup сохраняется (дисциплина Н13: токен свежий до submit).

### 3.5 Консоль и снос клиентской привязки

- `console-page.tsx`: комната — от сервера, не из localStorage. Резолв: явный search-param `?room=<id>` (из COMPLETED-строки перечня — решение №11) ИЛИ единственная ACTIVE из GET /rooms/mine; ни параметра, ни ACTIVE → navigate на перечень. Код комнаты — из того же ответа.
- **Умирают как класс:** `SessionStore.{loadHostRoomId, saveHostRoomId, loadHostRoomCode, saveHostRoomCode, clearHostRoom}`; механика T6 стейл-roomId (`isStaleRoomJoinError`, экран «Комната не найдена», однократный effect с clearHostRoom) — стейл-привязка невозможна по построению.
- COMPLETED-экран консоли: «Вернуться к началу — новое событие» теперь ведёт на перечень (было clearHostRoom + `/host/new`).
- Побочное исправление: комментарий `setup-page.tsx:69-72` («endpoint'а room по roomId нет, код не перечитать») перестаёт быть правдой — консоль получает код от сервера.

### 3.6 Гости удалённой DRAFT

Гость может войти в DRAFT (join отклоняет только COMPLETED/CANCELLED). После мягкого удаления: чтения гостя падают на проверках членства/`deletedAt` (REQ-SEC-003 уже требует учёт мягкого удаления комнаты — здесь это регрессионный тест, не новая логика). Отдельного realtime-уведомления гостям удалённой DRAFT нет — принято (решение №10).

### 3.7 Тестовая поверхность (обязательные обновления)

- **SDK/контрактные:** схемы + контрактные тесты (REQ-CTR-005).
- **Core:** unit/int на mine (фильтры статус/deletedAt/чужой организатор) и delete (DRAFT-only, единообразный NOT_FOUND, идемпотентность повторного delete).
- **Web (vitest):** гейт (таблица §3.2), перечень (рендер строк, delete-флоу), setup (нет auto-create; «Создать событие»; resume-prefill; два submit-пути), консоль (roomId от сервера). Паттерн «DOM-тестов нет» сохраняется: чистая оркестрация выносится в тестируемые функции (прецедент `excludeIfStillActive`, `resolveHostGateTarget`).
- **Playwright smoke:** флоу setup меняется (перечень → «Новое событие» → «Создать событие» → редактор → «Сохранить и запустить») — smoke.spec обновляется; добавить проход «черновик сохранён → перечень → продолжить → наполнение на месте».
- **Регрессия REQ-SEC-003:** гость удалённой DRAFT получает отказ (e2e или int).

## §4. Builder-calls (решения агента, не владельца)

1. Один эндпоинт GET /rooms/mine с `appSettings` внутри вместо пары «список + комната по id» (MVP-масштаб, один вызов на перечень и resume).
2. DELETE отвечает 204 без тела (контракт-тест фиксирует).
3. Перечень сортируется `updatedAt` desc.
4. Теоретические несколько ACTIVE: консоль берёт первую по `updatedAt` desc; перечень в это время недоступен через /host (решение №4). Ограничение «одна ACTIVE на организатора» сервером НЕ вводится — вне MVP.
5. Resume-параметр — search-param на существующих маршрутах (`/host/new?room=<id>` для редактора, `/host/console?room=<id>` для COMPLETED-строки перечня), новые wire-пути не плодим.
6. Inline-подтверждение удаления в строке, без модалки (мокап, экран 2).
7. Несколько DRAFT легальны и не ограничиваются — перечень и есть их управление. (Прежний комментарий «одна комната на организатора (MVP)» в host-gate-flow — код-комментарий, не спека.)
8. Focus-рефетч перечня — переиспользование `createFocusRefetcher` с дедупом (как консоль/плей после среза Н1/Н13).
9. «Новое событие» доступна всегда, в т.ч. при существующих DRAFT.
10. Выход из редактора в перечень — тихая ссылка «К моим событиям» на setup-странице (вопрос builder-check №2): черновики персистентны, «сохранил и ушёл» — штатный путь; закрытие вкладки не единственный выход. Минимальное отклонение от одобренного мокапа.
11. COMPLETED-строки не удаляются из перечня в этом срезе (UI-ограничение, не серверное — `softDelete` допускает COMPLETED); копятся по одной за событие.

## §5. Затрагиваемые требования и границы

- **REQ-RT-005** — санкционирует удаление DRAFT через `deletedAt`; машину статусов не трогаем.
- **REQ-SEC-003** — учёт `deletedAt` комнаты в проверках (уже реализовано; добавляется регрессионный тест гостя удалённой DRAFT).
- **REQ-ID-005** — mine/delete только для REGISTERED-организатора.
- **REQ-CTR-005** — контрактные тесты новых DTO из zod-схем SDK.
- **REQ-DEV-001** — boundary-check: web ↔ ядро только REST/SDK; новые эндпоинты — в transport-слое core.
- **ADR-006** — контракт в SDK (zod), minor-бамп версии.
- **ADR не затрагиваются; амендмент пакета не требуется** — новые эндпоинты и страницы в рамках существующих требований. Принятые ADR-001…011 и ADR-012 не переоткрываются.

## §6. Принятые риски и deferred

- Гость удалённой DRAFT узнаёт об удалении по отказу следующего запроса, без уведомления (принято владельцем, №10).
- Невалидный черновик не сохраняется: полусобранная форма живёт только в памяти вкладки (принято владельцем, №9).
- Перечень недоступен, пока есть ACTIVE (следствие решения №4).
- Существующие на стенде 7 сирот удаляются вручную через перечень после выкатки (миграция-зачистка не нужна — они валидные DRAFT).
- Автосейв, история завершённых, GC — deferred за пределами MVP.

## §7. Критерии приёмки среза (для exit-аудита и живой приёмки)

1. Открытие `/host` и `/host/new` с живым токеном не создаёт комнату (в БД ноль новых строк до клика «Создать событие»); StrictMode-двойной mount не плодит дублей.
2. `/host` с ACTIVE → консоль; без ACTIVE → перечень; перечень показывает ровно комнаты этого организатора (DRAFT + ACTIVE + COMPLETED, без чужих и удалённых).
3. «Сохранить черновик» → комната DRAFT с наполнением; закрытие вкладки → «Продолжить» (с ДРУГОГО браузера/origin) → форма с наполнением на месте.
4. «Удалить» с подтверждением → комната исчезает из перечня, в БД `deletedAt` проставлен; повторный DELETE — единообразный NOT_FOUND; DELETE не-DRAFT — типизированный отказ.
4а. COMPLETED-строка → «В консоль» → экран итогов с AwardsPanel; вручение/отзыв награды работает после перезагрузки и на другом устройстве (REQ-RWD-009).
5. Гость удалённой DRAFT получает отказ на следующем чтении (REQ-SEC-003).
6. Консоль работает без `mm.host.*` ключей: roomId/код от сервера; перезагрузка консоли на новом origin не ломается.
7. Класс Н3 закрыт: ни один путь не ведёт в консоль мёртвой комнаты (стейл-ключи упразднены; экран «Комната не найдена» удалён за ненадобностью).
8. Все CI-гейты зелёные: boundary-check, контрактные тесты, lint, type-check; playwright smoke с новым флоу зелёный.
