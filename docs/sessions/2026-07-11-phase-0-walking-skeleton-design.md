## 1. Решения сессии (вход плана)

### 1.1 Организующий принцип плана

**Кратчайший честный путь к первому живому событию.** Продуктовые ставки (§6.2 handoff) фальсифицируются только живым событием; всё, что не лежит на пути к нему, не должно его задерживать. К защитным нормам применяется тот же фильтр задела, что roadmap §0 применяет к платформенным решениям:

> Защита от актора, который не присутствует на текущем этапе, — задел. Задел оправдан, только если его нельзя добавить потом без переписывания.

Несущая конструкция (не режется): CI-граница + контракт + фикстуры (ADR-002/006 — AIDD-инфраструктура, урок v1); лог, server-seq и построение уровней видимости в проекциях ядром (ADR-005, REQ-CORE-005/008 — сам продукт); гостевой вход, код комнаты, членство (ADR-004); дешёвая гигиена безопасности — отсутствие демо-логина в production-образе (REQ-SEC-001), проверка секретов при старте (REQ-SEC-002), проверка членства при любом чтении подресурсов комнаты (REQ-SEC-003), типизированные ошибки без стектрейсов наружу (REQ-SEC-006), отказ действия при недоступности БД вместо «лучшего из возможного» (fail-closed, REQ-DEV-008); Google OAuth организатора; схема identity с `kind` и частичным уникальным индексом; ротация refresh-токенов (REQ-ID-007/016 — защита дешевле обхода, одна из дыр v1).

### 1.2 Гейты

- **Юрист** — до первого события с посторонними людьми или призами. Список вопросов юристу готовится параллельно фазе 0 (задача 8). Допустимость закрытого теста среди знакомых до заключения — вопрос в списке и решение владельца.
- **Первое живое событие** — до тяжёлых вложений в фазу 3 (rewards/лотерея). Квиз фазы 2 считает счёт сам.

### 1.3 Развилка §6.5 — закрыта

**pnpm workspaces + turbo + dependency-cruiser.** Мотивы:

- dependency-cruiser выражает правила уровня файловых путей — например, «socket.io импортируется только из Realtime-модуля» (REQ-RT-006) и «бизнес-логика только в сервисах, не в контроллерах» (REQ-CORE-006); тегов nx для такой гранулярности недостаточно;
- требование к CI (REQ-DEV-001) в самом тексте называет dependency-cruiser либо eslint-boundaries;
- nx окупается на десятках пакетов, у MVP их 4–6; на этом масштабе платим весом, магией и вторым скаффолдером рядом с NestJS CLI;
- миграция turbo → nx при росте штатна, обратная — нет.

Текст §5 пакета уже соответствует («pnpm workspaces + turbo»), правка не нужна.

### 1.5 Заметки реализации (внутри принятых норм)

- **Анти-упреждающий контроль (REQ-RT-013):** для раундов с призом механика обязана выбирать дискретное окно приёма, а не минимальный интервал. Минимальный интервал не достигает цели ADR-009 (бот ждёт порог и всё равно первый; на multiple-choice мгновенный случайный бот имеет высокий EV); окно приёма закрывает вектор.
- **Payload-нейтральность гонки за seq (REQ-RT-007):** делается структурной, а не статистической — seq присваивается в критической секции (advisory lock на roomId), вход в которую происходит после полного приёма и валидации payload; тест тогда проверяет детерминированное свойство (порядок фиксации = порядок входа в секцию), а не отсутствие статистического смещения.
- **Открытый дизайн-вопрос (в brainstorm SDK-контракта перед фазой 1):** как ядро валидирует события активной комнаты замороженной версией схем (пин `(appId, manifestVersion)` при переходе в ACTIVE, REQ-RT-004 × REQ-CTR-008) — снапшот сериализованных схем при регистрации приложения vs дисциплина хранения всех исторических версий схем в коде модуля.
- **SRE (ось §6.3 handoff):** целевое время восстановления живой комнаты после рестарта единственной реплики — в пороги фазы 4 (сейчас там только длительность replay); операционное правило «не деплоить при активных комнатах» — в документацию деплоя.

### 1.6 Открытая опция (не гейт)

Использование прототипа v1 (из его собственного репозитория, без переноса кода) как одноразового инструмента валидации §6.2 — решение владельца, склоняется к «нет».

## 2. Структура репозитория

```
mymozhem/
├── pnpm-workspace.yaml / pnpm-lock.yaml     # один lockfile (REQ-DEV-002)
├── turbo.json                               # build / lint / typecheck / test
├── .dependency-cruiser.cjs                  # правила границ (REQ-CTR-001)
├── eslint.config.js                         # + запрет мутабельных module-level экспортов
├── Dockerfile / docker-compose.yml          # артефакт + postgres, одна команда
├── .github/workflows/ci.yml                 # REQ-DEV-001
├── packages/
│   ├── sdk/        # @mymozhem/sdk — zod-контракт, фикстуры, контрактные тесты
│   └── core/       # @mymozhem/core — NestJS-модули ядра (в фазе 0: health, config)
└── apps/
    └── server/     # композиционный корень: bootstrap, сборка ядра (+модулей позже)
```

`app-quiz`, `rewards` не создаются: пустой каркас под будущее — оверинжиниринг (roadmap §5). Правила границ пишутся сразу целевые:

- `app-*` импортирует только `@mymozhem/sdk` (правило активно, сработает при появлении модулей);
- `core` импортирует `sdk`; `sdk` не импортирует внутренние пакеты;
- только `apps/server` импортирует `core` (композиционный корень);
- импорт `socket.io` — только из Realtime-модуля `core` (сработает в фазе 1).

## 3. Состав работ

Каждая задача несёт явную привязку к REQ-* — стадия spec-compliance двухстадийного ревью сверяется именно с ними.

1. **Каркас монорепо** — pnpm-workspace, turbo, tsconfig.base, eslint (flat config). [REQ-DEV-002]
2. **Граница + самопроверяющийся гейт** — dependency-cruiser с правилами §2; постоянный CI-шаг «гейт проверяет гейт»: скрипт подсаживает во временный файл заведомо запрещённый импорт и мутабельный module-level экспорт и требует ненулевого выхода dep-cruiser/eslint; молча позеленевший забор — красный CI. Анти-паттерн v1 (забор, умерший незаметно) закрывается навсегда, а не разовой проверкой. [REQ-CTR-001, REQ-DEV-001, ADR-002]
3. **SDK: первая схема** — конверт события лога `(roomId, seq, type, payload, actorId, visibility, schemaVersion)` + enum уровней видимости; фикстуры валидные и невалидные (в т.ч. неизвестный уровень видимости, отсутствующий seq); контрактный тест-раннер по фикстурам. Тесты и фикстуры пишутся первыми. [REQ-CTR-003, REQ-CTR-005; форма REQ-RT-001]
4. **Каркас ядра** — NestJS (Fastify-адаптер); zod-конфиг при старте: невалидный конфиг = отказ старта, с тестом; health `live`/`ready` раздельно, ready проверяет фактическую доступность БД. Конфиг минимален (PORT, DATABASE_URL, NODE_ENV): параметры §4 пакета приходят со своими фазами, инварианты не выдумываются раньше данных. [REQ-OPS-001; механизм REQ-OPS-003; REQ-CORE-006 с первого файла]
5. **Prisma** — datasource с `multiSchema`, `migrate deploy` в entrypoint, моделей нет (модели — фаза 1), readiness = `SELECT 1`. Цель — валидировать toolchain до появления схемы. [ADR-006, REQ-OPS-002]
6. **Docker** — multi-stage build; `docker compose up` поднимает postgres + server, ready зелёный. [REQ-CORE-001]
7. **CI** — install с frozen lockfile → turbo lint / typecheck / test / build + шаг 2. [REQ-DEV-001]
8. **Параллельно, не блокирует: список вопросов юристу** → `docs/legal/questions-for-lawyer.md`: 152-ФЗ и анонимизация против неудаляемого лога, согласие гостя, стимулирующие лотереи, налог с выигрыша, локализация, допустимость закрытого теста до заключения. От AI — только вопросы, не заключение. [гейт §6.1]
9. **Амендмент фазовой разметки v1.3** (таблица §1.4) — черновик готовит агент, решение принимает владелец до старта фазы 1.

## 4. Критерии выхода

Из §5 пакета, дословно, плюс уточнение механизма:

- минимум одна схема контракта с парой фикстур: валидная проходит, невалидная отклоняется, намеренная поломка схемы валит CI;
- boundary-check ловит специально внесённое нарушение границы и мутабельный module-level экспорт — у нас постоянным CI-шагом (задача 2), не разовой демонстрацией;
- артефакт собирается и поднимается одной командой;
- дополнительно: список вопросов юристу существует; амендмент v1.3 передан владельцу.
