# Дизайн — сервис регистрации приложения/манифеста (фаза 1, core-side)

**Дата:** 2026-07-18
**Статус:** утверждён владельцем 2026-07-18 (brainstorm-сессия).
**Отношение к другим документам:** реализует точку принуждения #1 из
`docs/sessions/2026-07-16-sdk-contract-core-design.md` §7 («Регистрация приложения»).
Не меняет норм и ADR. Первый настоящий потребитель SDK-контракта на стороне ядра.

---

## 1. Объём

Строится **только регистрация манифеста** — точка #1 из §7 дизайна SDK-контракта. Из пяти
точек принуждения §7 автономна лишь она; остальные (запись `appSettings`, пин
`DRAFT→ACTIVE`, фиксация события, чтение проекции) требуют модуля Rooms, которого ещё нет, —
тянуть их сейчас значит забежать вперёд или валидировать в вакууме.

**Три решения владельца, зафиксированные в этой сессии:**

1. **Граница — только регистрация (#1).** Стоп до Rooms / записи `appSettings` / фиксации
   события.
2. **Boot-time, in-memory, без Prisma.** Приложения регистрируют `defineApp()`-манифест при
   старте процесса; реестр — неизменяемая карта, построенная один раз на буте (REQ-CORE-004),
   детерминированно пересобираемая из вкомпилированного кода. Персистентной таблицы в этой
   задаче нет; она вводится аддитивно, когда появится durable-потребитель (replay комнаты,
   запиненной к версии, которую будущий редеплой убрал из кода) — а его в фазе 1 не существует.
   Это следствие ADR-001: единый артефакт, приложения вкомпилированы, рантайм-загрузки чужих
   манифестов нет (это marketplace/BaaS, отложено).
3. **Lean-поверхность.** Регистрация + `getManifest(appId, version)` + тонкий Nest-модуль с
   пустым DI-токеном-швом. Без event-индекса, без проекций, без Prisma.

**Что задача сознательно НЕ строит:** конверсию/страж (авторская сторона `defineApp`, не ядро —
см. §3); индекс composed-event-type и резолвинг события (композируется позже из
`resolveTypeOwner` + `getManifest`, когда появится фиксация события); запись/валидацию
`appSettings`; пин `(appId, manifestVersion)` при активации комнаты; персистентность; любой
HTTP/рантайм-эндпоинт регистрации.

## 2. Требования, которые задача закрывает

**Прямо реализует:**

- **REQ-CTR-004** — проверка совместимости на регистрации: работающая `CONTRACT_VERSION`
  обязана попадать в объявленный манифестом `contractRange`, иначе типизированный отказ. Эта
  задача — первый потребитель `assertContractRangeSatisfied` (см. комментарий у экспорта в
  `contract-version.ts`).
- **REQ-CORE-004** — реестр строится один раз в конструкторе и дальше immutable; нет
  мутабельного состояния уровня процесса.
- **REQ-CTR-005** — пары валид/невалид фикстур у поверхности регистрации.
- **REQ-DEV-001 / ADR-002** — новый модуль под boundary-check с первого коммита; общение с
  ядром только через SDK-контракт.

**Обслуживает, но ещё НЕ принуждает** (принуждение — в более поздних задачах, где появится
вызывающий):

- **REQ-CTR-008/009** — per-type уровень видимости хранится в манифесте и извлекается;
  отклонение события с заниженной видимостью — задача фиксации события.
- **REQ-RT-004** — реестр ключуется `(appId, manifestVersion)`, поэтому пин резолвится;
  само пиннование при `ACTIVE` — забота Rooms.
- **REQ-DEV-007** — неизменяемость версии: повторная регистрация того же ключа отвергается
  (§4, микро-решение 1).

## 3. Граница SDK ↔ ядро (важно: страж — авторская сторона, не ядро)

Манифест пересекает границу как сериализуемый `AppManifest` — **JSON Schema внутри, не zod**.
Конверсию zod→JSON Schema, страж представимости (`SCHEMA_NOT_REPRESENTABLE`), проверку
аннотаций видимости, дефолт `contractRange = ^CONTRACT_VERSION` и структурную валидацию
(`appManifestSchema`) выполняет **`defineApp` на авторской стороне** (приложение вызывает его,
чтобы произвести манифест). К моменту, когда ядро получает `AppManifest`, конвертировать уже
нечего, а выброшенный рефайнмент уже утрачен — поэтому **страж по построению авторский, ядро
его не вызывает и не может.**

Отсюда уточнение формулировки HANDOFF («первый потребитель… стража конверсии»): страж
**упражняется в тест-сьюте регистрации** через фикстуры, построенные из `.refine()`-схем (они
отвергаются на `defineApp`), но сам сервис ядра его не вызывает. Различимый вклад ядра —
`assertContractRangeSatisfied` (совместимость работающей версии) + повторная валидация
`appManifestSchema` (defense-in-depth против того, кто прислал невалидный манифест мимо
`defineApp`).

## 4. Логика регистрации (поток данных и ошибки)

Чистая логика, без Nest, полностью покрываемая юнит-тестами:

```
registerManifest(input: unknown): AppManifest
  1. appManifestSchema.safeParse(input)
        неуспех → throw ContractError('MANIFEST_INVALID', …)
        (повторно проверяет и структуру, и contractRange-ограниченность-сверху —
         defense-in-depth: ядро не доверяет тому, что отправитель прогнал defineApp)
  2. assertContractRangeSatisfied(parsed.contractRange)
        работающая CONTRACT_VERSION вне диапазона → throw ContractError('CONTRACT_VERSION_INCOMPATIBLE', …)
  3. return parsed.data          — доверенный снапшот

buildAppRegistry(manifests: readonly unknown[]): AppRegistry
  - registerManifest() каждый; key = `${appId}@${manifestVersion}`
  - дубликат ключа → ФАТАЛ (микро-решение 1)
  - return Object.freeze({ getManifest(appId, version): AppManifest | undefined })
```

Ядро **не переконвертирует** и не зовёт страж — конвертировать нечего. Типизированные ошибки
берутся из закрытого набора SDK (§8 дизайна SDK-контракта) — **нового кода ошибки не вводится.**

### Микро-решения (утверждены)

1. **Дубликат `(appId, manifestVersion)` на буте → фатальный `Error`, роняющий старт**
   (не типизированный `ContractError`). Это вкомпилированная мисконфигурация, а не значение,
   возвращаемое через границу; отдельный код ошибки «дубликат» был бы изменением SDK-контракта
   (вне объёма). Fail-closed: громкий отказ на старте вместо тихой перезаписи.
2. **Новых кодов ошибок SDK не вводится** — только существующий закрытый набор.
3. **`getManifest` возвращает `undefined`** на неизвестный ключ (не бросает) — это запрос;
   трактовать промах как `EVENT_UNKNOWN_TYPE` будет будущий потребитель (фиксация события).

## 5. Nest-вайринг и шов фазы 2 (REQ-CORE-004)

```
app-registry/
  app-registry.ts            — registerManifest() + buildAppRegistry() + тип AppRegistry
  app-registry.tokens.ts     — DI-токен APP_MANIFESTS
  app-registry.service.ts    — @Injectable() тонкая обёртка над immutable-реестром
  app-registry.module.ts     — @Module: провайдит APP_MANIFESTS=[] + AppRegistryService
  app-registry.spec.ts       — юнит-тесты (чистая логика + конструкция сервиса)
```

`AppRegistryService` строит реестр **один раз, в конструкторе**, из инъектированного токена
`APP_MANIFESTS`, и дальше он immutable. Мутабельного состояния уровня модуля нет
(REQ-CORE-004 ✓). Плохой манифест бросает в конструкторе → **бут падает громко** (fail-closed).

```ts
@Module({
  providers: [
    { provide: APP_MANIFESTS, useValue: [] },   // шов фазы 2: сюда приложения кладут манифесты
    AppRegistryService,
  ],
  exports: [AppRegistryService],
})
export class AppRegistryModule {}
```

`APP_MANIFESTS = []` сейчас — шов есть, но ноль каркаса под отсутствующие приложения.
`AppRegistryModule` импортируется в `apps/server/src/app.module.ts` (как `HealthModule`),
чтобы модуль оказался под boundary-check и поднимался вместе с артефактом.

**Границы.** Модуль лежит в `packages/core` (уже под boundary-check как пакет); импортирует
только `@mymozhem/sdk` (уже объявлен в `packages/core/package.json`) и `@nestjs/common`. Это
первый импорт `core → sdk`; правила dependency-cruiser (`sdk-is-leaf`, `app-only-through-sdk`,
`apps-only-through-core-entrypoint`) его не запрещают — sdk есть лист, от которого зависят.
Изменения конфигурации границ не требуется.

## 6. Тестирование (TDD первым — REQ-CTR-005)

- **`registerManifest`:** валидный (переиспользовать SDK `manifest.fixtures`) → возвращает;
  малформед → `MANIFEST_INVALID`; диапазон, исключающий работающую версию (напр. `^2.0.0`) →
  `CONTRACT_VERSION_INCOMPATIBLE`; безграничный сверху (`>=1.0.0`) → `MANIFEST_INVALID`
  (ловит `contractRangeSchema` внутри `appManifestSchema`).
- **`buildAppRegistry`:** несколько версий одного/разных приложений резолвятся; неизвестный
  ключ → `undefined`; дубликат ключа → бросает (фатал); пустой список → пустой реестр.
- **`AppRegistryService`:** строится из токена; плохой манифест в токене → конструкция бросает
  (бут падает); `getManifest` делегирует; реестр заморожен.

Валидные и отвергнутые-по-представимости входы берутся из SDK-фикстур; специфичные для
регистрации негативы (несовместимый диапазон, дубликат ключа) строятся инлайн в спеке.

## 7. Точки, которые задача оставляет последующим планам

- **Фиксация события** резолвит владельца типа из `resolveTypeOwner(fullType)` →
  `getManifest(appId, пиненная-версия).events[shortName]`; индекс composed-type не нужен —
  композируется из существующих кусков, когда появится вызывающий.
- **Запись/валидация `appSettings`** (точка #2 §7): скомпилированный валидатор по
  `(appId, manifestVersion)` (REQ-CORE-007) — задача, приходящая с Rooms.
- **Пин `(appId, manifestVersion)` при `ACTIVE`** (REQ-RT-004) — задача Rooms.
- **Персистентность реестра** — аддитивно, когда появится durable-replay-потребитель.

---

## 8. Заметки

- Формулировка HANDOFF о «потребителе стража конверсии и проекций» уточнена §3: страж
  авторский; проекций у этой задачи потребителя нет (нужны Rooms). Различимый вклад ядра —
  `assertContractRangeSatisfied` + повторная валидация манифеста.
- Задача остаётся чисто-логической и полностью fixture-тестируемой: ни БД, ни рантайма, ни
  Rooms. Это и есть «первый настоящий потребитель SDK-контракта» в минимальной честной форме.
