# Smoke-чеклист первого события (UI-срез)

**Дата:** 2026-09-24
**Назначение:** ручной прогон перед первым живым событием. Каждая строка — наблюдаемый результат (что именно должно быть видно), не «проверить, что работает». Прогоняется против локального/LAN-стенда, НЕ против production.
**Блокер приёмки среза:** ~~строка 1 (OAuth с реальными Google-кредами)~~ — **ПРОГНАНА 2026-09-24** (фикс приёмки `54da914`; протокол того прогона — в git-истории файла, строки с тех пор переписаны). Критерий §8.1 дизайна верифицирован, exit-аудит финализирован.

**Ревизия ADR-012 (2026-10-12):** OAuth-вход удалён; §0.1 и §1 переписаны под setup-токен инстанса (zero-PII дефолт); §9 размечен по `PRIZE_MODE` (при дефолте off — безпризовой розыгрыш 9.5). §0.2 и §0.3 сохранены без изменений механики.

**Стенд для прогона:** `ORGANIZER_SETUP_TOKEN=<токен стенда, ≥32 байта> docker compose up -d --build` из корня репозитория (web-статика раздаётся тем же контейнером, same-origin). Для прогона с телефонов стенд поднимается на машине в общей Wi-Fi сети, участники ходят на `http://<ip-машины>` (см. §0.3).

## 0. Предусловия (проверить ДО прогона)

### 0.1. Setup-токен стенда

Значение задано в env стенда (`ORGANIZER_SETUP_TOKEN`, ≥32 байта; compose-директива `:?` — без него стенд не стартует, `docker-compose.yml`). Это единственная креденшала организатора инстанса (ADR-012 §2): сервер сравнивает её timing-safe и ограничивает попытки rate-limit'ом.

**Наблюдаемый результат:** `curl -s -X POST http://<origin>/auth/organizer -H 'content-type: application/json' -d '{"setupToken":"…"}'` → `200` + заголовок `Set-Cookie: mm_refresh` (и JSON с accessToken). С неверным токеном — `401` с телом `{"code":"ORGANIZER_SETUP_INVALID"}`.

### 0.2. Хост и тест-игрок — разные браузеры/профили

Refresh-кука одна на origin (`mm_refresh`, path `/auth`): вход организатора по setup-токену затирает гостевую куку участника и наоборот. **Правило прогона:** консоль ведущего — в одном браузере (или профиле), тест-игрок с десктопа — в другом браузере/профиле/окне инкогнито; телефоны — отдельные устройства, там проблемы нет. Нарушение правила выглядит как «участника внезапно разлогинило / консоль потеряла сессию» — это не баг, а следствие shared-куки.

**Наблюдаемый результат:** после входа организатора вкладка участника в другом браузере продолжает получать события; в том же браузере — не проверяем.

### 0.3. LAN по plain HTTP — известное ограничение розыгрыша

`crypto.randomUUID()` — secure-context-only API: на `http://<ip>` (не localhost) кнопка розыгрыша («Разыграть участника», а при `PRIZE_MODE=on` и «Разыграть») не сможет сгенерировать drawId. Клиент показывает честную ошибку «Действие не выполнено: браузер не даёт сгенерировать идентификатор розыгрыша (нужен HTTPS или localhost)» (`apps/web/src/pages/host/prizes-panel.tsx:31-32`), а не мёртвую кнопку. **Если событие планируется по LAN по plain HTTP — это норма платформы, решение о fallback (TLS-терминатор / иной источник drawId) принимает владелец до события**, не ведущий в моменте.

**Наблюдаемый результат (контрольный прогон):** консоль по `http://<ip>` → «Разыграть участника» → текст ошибки в панели призов; по `http://localhost:3000` на машине стенда — розыгрыш проходит (строка 9).

### 0.4. Стенд на событие — bare-run сервера (находка №7)

docker NAT скрывает реальные IP клиентов (exclusion по IP банит всех, rate-limit
общий — воспроизведено на репетиции 2026-10-13). На событие сервер запускается
НА ХОСТЕ, в контейнере остаётся только БД:

1. `docker compose up postgres` (только БД).
2. `pnpm build` из корня.
3. Сервер на хосте: `DATABASE_URL=postgresql://mymozhem:mymozhem@localhost:5432/mymozhem JWT_SECRET=... ORGANIZER_SETUP_TOKEN=... PRIZE_MODE=off COOKIE_SECURE=false pnpm --filter @mymozhem/server start`.
   ВНИМАНИЕ: compose по умолчанию НЕ публикует порт 5432 на хост — для bare-run
   добавить в docker-compose.override.yml или пробросить порт одноразово
   (`docker compose run`-стиль не подходит; см. комментарий в docker-compose.yml).
4. Web отдаётся тем же сервером (WEB_STATIC_DIR) — один origin на LAN-IP хоста.
5. COOKIE_SECURE=false — ТОЛЬКИ для plain-HTTP LAN (находка №2): иначе телефоны
   не примут refresh-куку и сессия будет с 15-минутным потолком.
6. Контрольная строка: участник с телефона исключается → ROOM_JOIN_DENIED
   получает ТОЛЬКО он, остальные продолжают. Вторая контрольная: вход 5+
   устройств подряд без 429.
7. Перед гостями: LAN-smoke — `LAN_BASE_URL=http://<IP-хоста>:3000 pnpm --filter @mymozhem/web test:e2e:lan`.

## 1. Вход организатора по setup-токену

Playwright-smoke проходит этот путь целиком (`apps/web/e2e/smoke.spec.ts`, шаг 1); здесь — ручная проверка с токеном стенда.

**Прогон:**
1.1. Открыть лендинг → «Войти по токену организатора».
**Результат:** переход на `/host/login` (router-навигация, без перезагрузки), форма с полем «Токен организатора».
1.2. Ввести setup-токен стенда → «Войти».
**Результат:** bootstrap ставит refresh-куку, гейт молча делает refresh → переход на `/host/new` (комнаты ещё нет). Повторный заход на `/host` — сразу в `/host/*` без ввода токена (refresh-кука жива).
1.3. Негатив: ввести неверный токен → «Войти».
**Результат:** ошибка «Неверный токен организатора.» (role=alert), перехода нет; токен нигде не сохраняется (после протухания refresh-сессии вводится заново).

---

## 2. Create → editor → configure → activate

2.1. `/host/new`: выбрать приложение «Квиз», заполнить редактор: 2+ вопроса, у каждого 2+ варианта, отметить правильные, сохранить.
**Результат:** кнопка «Сохранить и запустить» активна только при валидной форме; после нажатия — переход на `/host/console`, статус комнаты ACTIVE, код комнаты крупно + копируемая ссылка.
2.2. Контроль backend-контура (не UI-действие, проверка шва): комната активирована через HTTP lifecycle-контур, не сервисным вызовом — после spectator-join экран показывает статус/ведение, выведенный из snapshot комнаты (производный статус через deriveRoomStatus, `apps/web/src/pages/screen/screen-page.tsx:123`, — не литеральные имена core-событий): комната не в состоянии «ожидание настройки», после открытия вопроса — его текст.

## 3. Два телефона-участника

3.1. Телефон 1: открыть ссылку `/play/<code>` → ввести имя → «Присоединиться».
**Результат:** лобби «Игра идёт. Ждём вопрос…» (комната уже ACTIVE); ростер в консоли показывает имя после ближайшего события/рефетча (join не эмитит событий — интерпретация I-3, мгновенной видимости join не требуем).
3.2. Телефон 2: то же с другим именем.
**Результат:** оба участника в ростере консоли; у каждого своё имя в лобби.
3.3. Негатив: несуществующий код на `/play`.
**Результат:** понятная ошибка «проверьте код» (маппинг `ROOM_NOT_FOUND`), не технический JSON и не белый экран.

## 4. Экран (проектор)

4.1. Третье устройство/окно: `/screen/<code>`.
**Результат:** spectator-view без форм и кнопок ответа; виден статус комнаты/ожидание вопроса; auth-контур не запрашивается.

---

## 5. Ведение квиза

5.1. Консоль: «Открыть вопрос 1».
**Результат:** у обоих телефонов — вопрос с вариантами (кнопки); на экране — текст вопроса крупно. Кнопка «Открыть вопрос» в консоли disabled, пока вопрос accepting.
5.2. Телефон 1 отвечает верно, телефон 2 — неверно.
**Результат:** у каждого мгновенный ack «Ответ принят.» (без вердикта до reveal); счётчик ответов в консоли показывает 2.
5.3. Консоль: «Закрыть вопрос».
**Результат:** у телефона 1 — «Верно!» и начисленные очки, у телефона 2 — «Неверно.»; табло у обоих и на экране сходится (имена и баллы одинаковые на всех трёх клиентах); на экране — «Правильный ответ: …».

---

## 6. Обрыв Wi-Fi у участника (перефолд)

6.1. Открыть вопрос 2, на телефоне 1 выключить Wi-Fi на ~10 секунд, включить обратно.
**Результат:** во время обрыва у телефона 1 — явный индикатор «нет соединения» (`apps/web/src/components/connection-banner.tsx`); после восстановления — автоматический reconnect → re-subscribe → полный перефолд: актуальный вопрос/статус на месте, отвечать можно, баллы за вопрос 1 не потеряны. Без ручного F5.

---

## 7. Reload консоли mid-event

7.1. В разгар вопроса перезагрузить страницу консоли (F5).
**Результат:** после reload консоль показывает ту же комнату: код комнаты и ссылки на месте, ведение продолжается с текущего состояния (roomId/code переживают перезагрузку в localStorage — `apps/web/src/state/session.ts:71-83`, `apps/web/src/pages/host/console-page.tsx:31`).

## 8. Пауза > 15 минут (silent refresh)

8.1. Оставить консоль бездействовать дольше access TTL (15 мин), затем нажать любую команду (например, «Закрыть вопрос»).
**Результат:** команда проходит без повторного ввода setup-токена и без видимой ошибки — клиент молча обновил access-токен через refresh (`apps/web/src/api/api-client.ts:34-35`: 401 → один refresh → один retry).

## 9. Приз + розыгрыш + fulfill/revoke

**Режим прогона (ADR-012 §4):** строки 9.1–9.4 прогоняются при `PRIZE_MODE=on` (стенд поднят с `PRIZE_MODE=on` в env — призовой режим это юридическая ответственность организатора). При задокументированном дефолте (`PRIZE_MODE=off`) 9.1–9.2 непроходимы: создание приза и розыгрыш приза сервер отклоняет (`PRIZES_DISABLED` → «Призовой режим выключен на этом сервере.») — вместо них прогоняется 9.5; 9.3–9.4 без приза не имеют объекта и пропускаются.

9.1. Консоль, панель призов: создать приз «Главный приз», quantity 1.
**Результат:** приз в списке с остатком 1.
9.2. «Разыграть» (в lottery-комнате; в quiz-комнате кнопка не рисуется — одна комната = одно приложение, I-5: для события «квиз + розыгрыш» создаётся вторая комната, участники заходят по второму коду).
**Результат:** на клиентах (участники + экран) появляется победитель из числа участников; остаток приза в консоли уменьшился до 0.
9.3. fulfill: отметить вручение.
**Результат:** награда переходит в FULFILLED в списке awards; повторный fulfill — no-op без ошибки.
9.4. revoke (на втором призе/награде): отозвать.
**Результат:** награда в REVOKED, остаток фонда приза вернулся (+1).
9.5. Дефолтный режим (`PRIZE_MODE=off`): «Разыграть участника» в lottery-комнате, без создания приза.
**Результат:** на клиентах (участники + экран) появляется победитель из числа участников — строка без «приз …» (prizeId null); остатки не меняются (фонда нет). Контроль гейта: попытка создать приз → «Призовой режим выключен на этом сервере.».

## 10. Конец колоды

10.1. Пройти все вопросы до конца.
**Результат:** когда вопросы кончились, «Открыть вопрос» disabled (`apps/web/src/pages/host/quiz-controls.tsx:59,114`); «Завершить квиз» спрашивает confirm «Завершить квиз? Это действие необратимо.» (`quiz-controls.tsx:128-140`) — отмена confirm не завершает игру.

---

## 11. Exclude игрока

11.1. Консоль, ростер: «Исключить» телефон 2.
**Результат:** клиент телефона 2 дисконнектится и теряет доступ к комнате (REQ-SEC-003: exclude → revokeRoomAccess → disconnect всех сокетов identity — `packages/core/src/realtime/realtime.gateway.ts:253`); повторный join телефона 2 тем же устройством отклонён. Исключённый пропадает из ростера консоли; телефон 1 и экран продолжают работать.

---

## 12. Завершение

12.1. «Завершить квиз» → confirm принять.
**Результат:** у участников и на экране — «Игра завершена» + итоговое табло; у участника — «Ваши очки: N». Команды ведения в консоли больше недоступны (терминальный статус).
12.2. После завершения: участник обновляет страницу.
**Результат:** видит финальное состояние (табло/итоги), а не ошибку и не «ожидание вопроса».
