## 0. Предусловия (проверить ДО прогона)

### 0.1. Пара env↔UI: allowlist редиректа

`OAUTH_REDIRECT_ALLOWLIST` обязан содержать `<origin>/host` **ровно в том виде**, что шлёт лендинг. Лендинг строит absolute URL из `window.location.origin` (`apps/web/src/pages/landing.tsx:31-38`), сервер сверяет точным совпадением строки (`packages/core/src/oauth/oauth.service.ts:124-136`; схема парсит значения как URL — `packages/core/src/config/config.schema.ts:62`).

- localhost-стенд: дефолт compose `http://localhost:3000/host` (`docker-compose.yml:37`) — совпадает, ничего не делаем.
- LAN-стенд: `OAUTH_REDIRECT_ALLOWLIST=http://<ip>/host` (например `http://192.168.1.50:3000/host`). Без порта, со слэшом в конце, с https вместо http — не совпадёт: сервер ответит `OAUTH_REDIRECT_INVALID` ещё до ухода в Google.

**Наблюдаемый результат:** `curl -s -o /dev/null -w "%{http_code} %{redirect_url}" "http://<origin>/auth/google?redirect=<urlencoded http://<origin>/host>"` → `302`, `redirect_url` на `https://accounts.google.com/...`.

### 0.2. Хост и тест-игрок — разные браузеры/профили

Refresh-кука одна на origin (`mm_refresh`, path `/auth`): OAuth-логин организатора затирает гостевую куку участника и наоборот. **Правило прогона:** консоль ведущего — в одном браузере (или профиле), тест-игрок с десктопа — в другом браузере/профиле/окне инкогнито; телефоны — отдельные устройства, там проблемы нет. Нарушение правила выглядит как «участника внезапно разлогинило / консоль потеряла сессию» — это не баг, а следствие shared-куки.

**Наблюдаемый результат:** после входа организатора вкладка участника в другом браузере продолжает получать события; в том же браузере — не проверяем.

### 0.3. LAN по plain HTTP — известное ограничение розыгрыша

`crypto.randomUUID()` — secure-context-only API: на `http://<ip>` (не localhost) кнопка «Разыграть» не сможет сгенерировать drawId. Клиент показывает честную ошибку «Действие не выполнено: браузер не даёт сгенерировать идентификатор розыгрыша (нужен HTTPS или localhost)» (`apps/web/src/pages/host/prizes-panel.tsx:30-31`), а не мёртвую кнопку. **Если событие планируется по LAN по plain HTTP — это норма платформы, решение о fallback (TLS-терминатор / иной источник drawId) принимает владелец до события**, не ведущий в моменте.

**Наблюдаемый результат (контрольный прогон):** консоль по `http://<ip>` → «Разыграть» → текст ошибки в панели призов; по `http://localhost:3000` на машине стенда — розыгрыш проходит (строка 9).

## 1. OAuth с реальными Google-кредами — ДЕЙСТВИЕ ВЛАДЕЛЬЦА

Playwright-smoke проверяет только 302-шов (`apps/web/e2e/smoke.spec.ts:55-64`); полный круг Google → callback → сессия ручной.

**Подготовка (владелец):**
1. Google Cloud Console → APIs & Services → Credentials → Create OAuth client ID (Web application). Authorized redirect URI: `http://<origin>/auth/google/callback` (серверный callback — `packages/core/src/transport/oauth.controller.ts:37`).
2. Передать стенду реальные значения: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `OAUTH_REDIRECT_URI=http://<origin>/auth/google/callback` (все три обязаны быть заданы вместе — all-or-none, иначе 503 `OAUTH_NOT_CONFIGURED`).
3. Проверить §0.1 (allowlist содержит `http://<origin>/host`).

**Прогон:**
1.1. Открыть лендинг → «Войти через Google».
**Результат:** полная перезагрузка на `accounts.google.com` с client_id стенда (не dummy), выбор аккаунта, возврат на `http://<origin>/host` без экрана ошибки.
1.2. После callback — гейт консоли.
**Результат:** молчаливый refresh → переход на `/host/new` (комнаты ещё нет). Повторный заход на `/` → «Войти через Google» → сразу в `/host/*` без выбора аккаунта (refresh-кука жива).
1.3. Негатив: открыть `/host` в чистом профиле без куки.
**Результат:** редирект на лендинг `/` (гейт не пускает гостя/анонима в консоль).

## 2. Create → editor → configure → activate

2.1. `/host/new`: выбрать приложение «Квиз», заполнить редактор: 2+ вопроса, у каждого 2+ варианта, отметить правильные, сохранить.
**Результат:** кнопка «Сохранить и запустить» активна только при валидной форме; после нажатия — переход на `/host/console`, статус комнаты ACTIVE, код комнаты крупно + копируемая ссылка.
2.2. Контроль backend-контура (не UI-действие, проверка шва): комната активирована через HTTP lifecycle-контур, не сервисным вызовом — после spectator-join экран показывает статус/ведение, выведенный из snapshot комнаты (производный статус через deriveRoomStatus, `apps/web/src/pages/screen/screen-page.tsx:123`, — не литеральные имена core-событий): комната не в состоянии «ожидание настройки», после открытия вопроса — его текст.

## 3. Два телефона-участника

3.1. Телефон 1: открыть ссылку `/play/<code>` → ввести имя → «Присоединиться».
**Результат:** лобби «Игра идёт. Ждём вопрос…» (комната уже ACTIVE); ростер в консоли показывает имя после ближайшего события/рефетча (join не эмитит событий — интерпретация I-3, мгновенной видимости join не требуем).
3.2. Телефон 2: то же с другим именем.
**Результат:** оба участника в ростере консоли; у каждого своё имя в лобби.
3.3. Негатив: несуществующий код на `/play`.
**Результат:** понятная ошибка «проверьте код» (маппинг `ROOM_NOT_FOUND`), не технический JSON и не белый экран.

## 5. Ведение квиза

5.1. Консоль: «Открыть вопрос 1».
**Результат:** у обоих телефонов — вопрос с вариантами (кнопки); на экране — текст вопроса крупно. Кнопка «Открыть вопрос» в консоли disabled, пока вопрос accepting.
5.2. Телефон 1 отвечает верно, телефон 2 — неверно.
**Результат:** у каждого мгновенный ack «Ответ принят.» (без вердикта до reveal); счётчик ответов в консоли показывает 2.
5.3. Консоль: «Закрыть вопрос».
**Результат:** у телефона 1 — «Верно!» и начисленные очки, у телефона 2 — «Неверно.»; табло у обоих и на экране сходится (имена и баллы одинаковые на всех трёх клиентах); на экране — «Правильный ответ: …».

## 6. Обрыв Wi-Fi у участника (перефолд)

6.1. Открыть вопрос 2, на телефоне 1 выключить Wi-Fi на ~10 секунд, включить обратно.
**Результат:** во время обрыва у телефона 1 — явный индикатор «нет соединения» (`apps/web/src/components/connection-banner.tsx`); после восстановления — автоматический reconnect → re-subscribe → полный перефолд: актуальный вопрос/статус на месте, отвечать можно, баллы за вопрос 1 не потеряны. Без ручного F5.

## 7. Reload консоли mid-event

7.1. В разгар вопроса перезагрузить страницу консоли (F5).
**Результат:** после reload консоль показывает ту же комнату: код комнаты и ссылки на месте, ведение продолжается с текущего состояния (roomId/code переживают перезагрузку в localStorage — `apps/web/src/state/session.ts:71-83`, `apps/web/src/pages/host/console-page.tsx:31`).

## 8. Пауза > 15 минут (silent refresh)

8.1. Оставить консоль бездействовать дольше access TTL (15 мин), затем нажать любую команду (например, «Закрыть вопрос» или создать приз).
**Результат:** команда проходит без повторного OAuth-логина и без видимой ошибки — клиент молча обновил access-токен через refresh (`apps/web/src/api/api-client.ts:34-35`: 401 → один refresh → один retry).

## 9. Приз + розыгрыш + fulfill/revoke

9.1. Консоль, панель призов: создать приз «Главный приз», quantity 1.
**Результат:** приз в списке с остатком 1.
9.2. «Разыграть» (в lottery-комнате; в quiz-комнате кнопка не рисуется — одна комната = одно приложение, I-5: для события «квиз + розыгрыш» создаётся вторая комната, участники заходят по второму коду).
**Результат:** на клиентах (участники + экран) появляется победитель из числа участников; остаток приза в консоли уменьшился до 0.
9.3. fulfill: отметить вручение.
**Результат:** награда переходит в FULFILLED в списке awards; повторный fulfill — no-op без ошибки.
9.4. revoke (на втором призе/награде): отозвать.
**Результат:** награда в REVOKED, остаток фонда приза вернулся (+1).

## 11. Exclude игрока

11.1. Консоль, ростер: «Исключить» телефон 2.
**Результат:** клиент телефона 2 дисконнектится и теряет доступ к комнате (REQ-SEC-003: exclude → revokeRoomAccess → disconnect всех сокетов identity — `packages/core/src/realtime/realtime.gateway.ts:253`); повторный join телефона 2 тем же устройством отклонён. Исключённый пропадает из ростера консоли; телефон 1 и экран продолжают работать.

---

## 12. Завершение

12.1. «Завершить квиз» → confirm принять.
**Результат:** у участников и на экране — «Игра завершена» + итоговое табло; у участника — «Ваши очки: N». Команды ведения в консоли больше недоступны (терминальный статус).
12.2. После завершения: участник обновляет страницу.
**Результат:** видит финальное состояние (табло/итоги), а не ошибку и не «ожидание вопроса».
