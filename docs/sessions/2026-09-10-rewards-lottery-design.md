## §0. Решения владельца (brainstorm 2026-09-10)

1. **Гейт 2 («первое живое событие — до тяжёлых вложений в фазу 3»):** дизайн выполняется сейчас при открытом гейте; **старт реализации — отдельное решение владельца после первого живого события**. Проектирование ≠ тяжёлая реализация.
2. **Декомпозиция:** один дизайн-документ на всю фазу 3 (rewards + лотерея + перевод квиза + TTL-свип). Реализация — батчами по 3 задачи, каждый батч новой сессией (правило владельца 2026-09-09).
3. **Механика лотереи MVP:** один приз → один розыгрыш → один победитель. Организатор конфигурирует призовой фонд (призы с quantity), для конкретного приза запускает розыгрыш; повторные розыгрыши — до исчерпания фонда. Мульти-победители за одно действие и взвешенный розыгрыш по билетам — НЕ в MVP.
4. **Пул розыгрыша:** активные PARTICIPANT-членства комнаты; организатор, зрители (SPECTATOR), исключённые и soft-deleted не участвуют. При `drawEligibility: 'verified'` дополнительно отсекаются GUEST-identity (REQ-RWD-014). Разные призы одному участнику выигрывать можно; тот же приз дважды — нельзя (индекс REQ-RWD-003).
5. **TTL-свип гостей входит в фазу 3.** Вскрытый факт: свип анонимизации (REQ-ID-003/014) фазой 1 реализован не был — есть `deletedAt` и кап refresh-сессии ≤ `guest_ttl`, но джобы нет; без него REQ-RWD-013 не на чем работать. Фаза 3 догоняет свип и добавляет приостановку.
6. **Архитектурная развилка 1 — награждение app-модулем:** подход **A — награда как эффект коммита** (`AppEffect`, исполняется в той же транзакции `outbox.run` до коммита событий). Отклонены: B (реактор post-commit — расходит лог и таблицы, отказ не вернуть в ack, против REQ-RWD-003) и C (сервис rewards в `AppHostContext` — живой объект через границу, против REQ-CTR-002).
7. **Архитектурная развилка 2 — случайность и пул:** вариант **A2 — хост-примитивы**: `randomInt` над node:crypto CSPRNG + снапшот пула от диспетчера; логика выбора — в модуле (winnerSelection остаётся делегированным приложению, REQ-RWD-005). Отклонён B2 (розыгрыш целиком в rewards — против делегирования winnerSelection приложению).
8. **Интерпретации (подтверждены по секциям):** вручение/отзыв — только ORGANIZER (REQ-RWD-004 упоминает модератора, но в MVP модератор прав сверх PARTICIPANT не имеет — амендмент v1.3, перенос REQ-ID-018 в ф.4); `draw_eligibility` — настройка в appSettings лотереи, замораживается при ACTIVE, изменение = переконфигурация в DRAFT; TTL гостя считается от `createdAt` (поля активности не вводим); итоговых начислений за место в квизе нет (начисления — по раундам); события `rewards.*` в логе — публичные; транспорт действий организатора над фондом и наградами — REST.

## §1. Объём и закрываемые требования

Срез четырёхслойный: (а) SDK-дельта (capabilities, эффекты, хост-примитивы) — контракт 1.5.0 → **1.6.0**; (б) модуль `core/src/rewards`; (в) `packages/app-lottery`; (г) перевод квиза на начисления + TTL-свип с приостановкой.

- **REQ-RWD-001** — rewards опционален, capability манифеста; ядро не импортирует rewards (boundary-правило, связка через DI-токен в composition root). Без `capabilities: ['rewards']` эффекты награждения отклоняются на commit-гейте.
- **REQ-RWD-002a/b** — призы (сущность с quantity) и начисления (баллы без сущности приза); фиксация победителя/начисления не требует приза (`Award.prizeId` nullable).
- **REQ-RWD-003** — награждение атомарно (одна транзакция: декремент + insert); единичность победителя — частичный уникальный индекс `(roomId, prizeId, winnerId)` по активным записям, SQL-миграцией с автотестом наличия (REQ-DEV-006); конфликт по индексу → типизированный no-op.
- **REQ-RWD-004 + ADR-007** — только очное вручение: `AWARDED → FULFILLED | REVOKED` явным действием организатора. Без CLAIMED, claim_window, контактов победителя.
- **REQ-RWD-005** — делегирование `prizeFund`/`winnerSelection` приложению оформлено capability и контрактом rewards (эффекты + хост-примитивы).
- **REQ-RWD-007** — автомат с БД-ограничением перехода (условный UPDATE); повторное вручение — типизированный no-op; двойной отзыв не возвращает quantity дважды; REVOKED транзакционно возвращает quantity.
- **REQ-RWD-009** — при COMPLETED организатору видны оставшиеся AWARDED, вручить/отозвать можно каждую (REST работает и после завершения комнаты).
- **REQ-RWD-010** — `CHECK (quantity >= 0)` + атомарный ограниченный декремент; K > quantity конкурентных наград разным identity без перевыпуска и минуса.
- **REQ-RWD-011 + ADR-010** — розыгрыш на хост-примитиве `randomInt` (node:crypto CSPRNG); сид вне наблюдаемого по построению. VRF не делаем (REQ-RWD-012 отложен).
- **REQ-RWD-013** — приостановка TTL гостя при открытой `AWARDED` через hook-гарды анонимизации (см. §5).
- **REQ-RWD-014** — `draw_eligibility ∈ {guests_allowed | verified}`, дефолт guests_allowed, verified = REGISTERED; атрибут розыгрыша в appSettings лотереи.
- **REQ-ID-003/014 (догон)** — свип анонимизации гостей по `guest_ttl`.
- **REQ-CTR-004/005** — контракт 1.6.0; фикстуры на всё новое (манифест с capabilities, эффекты, payload'ы лотереи, REST DTO rewards).
- **REQ-CORE-004** — без глобального мутабельного состояния: состояние rewards — в БД; проекция лотереи — in-memory кэш + replay (как квиз).
- **REQ-SEC-009** — PII не в логе: события несут только id; отображаемое имя клиент берёт из membership-проекции.
- **REQ-RT-004** — пин `(appId, manifestVersion)`: квиз v2 и лотерея — через существующий механизм.

**Вне объёма (явно):** CLAIMED/claim-автомат, контакт победителя, VRF/commit-reveal (REQ-RWD-006/008/012 — отложены), взвешенный розыгрыш/билеты, фильтр пула по начислениям, права MODERATOR на вручение (ф.4), UI клиентов, HTTP-эндпоинт `configure` (остаётся service-уровнем, как в ф.2). Задел — только словами: статусная модель награды допускает аддитивное CLAIMED (REQ-DEV-007), nullable-полей под claim нет.

## §2. Архитектура

**Размещение rewards.** Каталог `packages/core/src/rewards/` — логический модуль по ADR-003 (свой каталог, свой контракт, CI-граница, без отдельной инфраструктуры). PostgreSQL-схема `rewards` (multiSchema, ADR-006). Это НЕ app-модуль: он вызывается ядром, а не стоит за `app-only-through-sdk`. «Ядро не зависит от rewards» (REQ-RWD-001) принуждается: app-runtime знает только интерфейс исполнителя эффектов — DI-токен `AWARD_EFFECT_HANDLER` (объявлен в `core/src/app-runtime/effects.ts`, импорт разрешён обеим сторонам: реализация в rewards, потребитель в app-runtime); boundary-правило dependency-cruiser запрещает остальным доменам ядра импорт `core/rewards`. Без подключённого rewards-модуля эффект награждения → типизированный отказ `CAPABILITY_UNAVAILABLE`.

**Эффекты в коммит-пайплайне (подход A).** `AppCommit` не меняется; добавляется `AppEffect`; `handlePublish` возвращает `{ commits: AppCommit[], effects: AppEffect[] }` (старая форма «голый массив» читается как `{ commits, effects: [] }` — обратная совместимость для квиза v1). Диспетчер внутри `outbox.run`: **сначала эффекты** (через `AWARD_EFFECT_HANDLER`: декремент фонда + insert награды / ledger-записи начислений), **затем коммит событий** пакетом. Отказ эффекта → откат транзакции целиком, publish-ack несёт типизированный код. Порядок «эффекты до событий»: событие «победитель определён» не должно попасть в лог, если награждение не состоялось.

Виды эффектов (zod-схемы в SDK, REQ-CTR-005):
- `{ kind: 'award.prize', prizeId, winnerId }` — списание 1 единицы фонда + фиксация победителя (лотерея).
- `{ kind: 'award.points', identityId, points, reason? }` — начисление без приза (квиз, REQ-RWD-002b); без фонда и декремента, в той же транзакции с событиями.

**Хост-примитивы (вариант A2).** `AppHostContext` += :
- `randomInt(boundExclusive: number): number` — над `crypto.randomInt` (node:crypto). CSPRNG по построению; сид не выводится из наблюдаемого (REQ-RWD-011). У модуля нет иного санкционированного источника случайности; `Math.random`/`Date.now`-сид в `packages/app-*` отсекаются ревью (кандидат lint-правила).
- `drawPool: DrawPoolEntry[]` (`{ identityId, kind }`) — JSON-снапшот: активные PARTICIPANT-членства комнаты (переиспользует `findActiveMembership`-логику: без SPECTATOR, без soft-deleted; организатор в пул не входит — его членство не PARTICIPANT). Наполняется диспетчером **только для модулей с capability `rewards`** — publish'и квиза не грузят membership.

Оба поля — расширение трактовки REQ-CTR-002, зафиксированное решением §0.7: сетевая форма сохранена (при переносе на сеть — RPC/данные), прецедент функций в контракте — `reduce`/`handlePublish`.

**Capability-гейт.** Манифест += `capabilities?: string[]` — точка расширения, заложенная в ф.2 (strictObject сознательно отвергал поле). Значения — enum (`'rewards'`); неизвестное → отказ валидации манифеста. Диспетчер: эффект при отсутствии capability → типизированный отказ до исполнения.

**Транспорт организатора (REST, в rewards-модуле):**
- `POST /rooms/:id/prizes` — создать приз `{ name, quantity }` (ORGANIZER, не-терминальный статус комнаты; на живом событии призы добавляют на ходу — это не appSettings, заморозка REQ-RT-004 не применима).
- `GET /rooms/:id/rewards` — список наград комнаты (ORGANIZER видит все, включая оставшиеся AWARDED при COMPLETED — REQ-RWD-009).
- `POST /rooms/:id/awards/:awardId/fulfill`, `POST /rooms/:id/awards/:awardId/revoke` — переходы автомата (§3), идемпотентные типизированные no-op'ы (REQ-RWD-007).

Почему REST, а не realtime-команды: это cross-app управляющие действия платформенного контура («призовой фонд события», ADR-003), не внутриигровые команды механики; идемпотентность и авторизация проще на HTTP с существующими гардами.

**События `rewards.*` в логе.** Награждение/вручение/отзыв эмитируются публичными событиями неймспейса `rewards.*` (коммитит rewards-модуль через существующий `EventOutbox.run`-путь в той же транзакции) — участники видят вручение по realtime, таблицы остаются источником состояния, лог — нотификация и аудит (ADR-005). Payload — только id (REQ-SEC-009).

## §3. Модель данных rewards

Новая PostgreSQL-схема `rewards`; одна новая миграция (замороженные не трогаются). Таблицы:

**`Prize`** — приз и остаток фонда: `id` uuid PK; `roomId` FK → core.Room (RESTRICT); `name` text; `quantityTotal` int (исходный фонд, для «раздано X из Y»); `quantity` int (остаток) с **`CHECK (quantity >= 0)`** (REQ-RWD-010); `createdAt/updatedAt`.

**`Award`** — награждение с автоматом: `id` uuid PK; `roomId` FK → core.Room (RESTRICT); `prizeId` FK → Prize **NULLABLE** (REQ-RWD-002b: победитель без сущности приза); `winnerId` FK → identity.Identity (RESTRICT); `status` enum `AWARDED | FULFILLED | REVOKED` default AWARDED; `sourceAppId` text (`'lottery'`, `'quiz'`); `createdAt/fulfilledAt/revokedAt`.

Инварианты:
- **Частичный уникальный индекс** `(roomId, prizeId, winnerId) WHERE status IN ('AWARDED','FULFILLED')` — SQL-миграцией с автотестом наличия (REQ-DEV-006, REQ-RWD-003). «Активная» = не отозванная: отзыв освобождает место (приз можно переразыграть), вручённая — нет. Сетевой повтор того же награждения → конфликт индекса → типизированный no-op.
- **Переходы** — условный UPDATE `SET status=…, <переход>At=now() WHERE id=? AND status='AWARDED'`; 0 затронутых строк → типизированный no-op (REQ-RWD-007). Отзыв — одна транзакция: условный UPDATE награды, затем `UPDATE Prize SET quantity = quantity + 1` только если первый затронул строку → двойной отзыв не возвращает quantity дважды.
- **Списание** — ограниченный декремент `UPDATE Prize SET quantity = quantity - 1 WHERE id=? AND quantity >= 1`; 0 строк → отказ `PRIZE_FUND_EXHAUSTED`; одна транзакция с insert Award (REQ-RWD-003/010). Конкуренция разрешается БД: K > quantity → ровно `quantity` успехов.

**`PointsGrant`** — ledger начислений, append-only: `id` uuid PK; `roomId` FK; `identityId` FK → identity.Identity; `points` int (только положительные в MVP); `reason` text? (`'quiz.round'`, …); `sourceAppId` text; `createdAt`. Без автомата (нечего вручать) и без фонда. Агрегат «баллы участника» — проекция по ledger'у, не хранимый счётчик.

**Задел под отложенную фазу (форма, не код):** добавление `CLAIMED` в enum статуса — аддитивная эволюция (REQ-DEV-007); claim-поля появятся с активацией фазы, сейчас не создаются.

## §4. Лотерея как app-модуль

**Пакет** `packages/app-lottery` (`@mymozhem/app-lottery`), импортирует только `@mymozhem/sdk` (то же boundary-правило `app-only-through-sdk`). Манифест через `defineApp`, `capabilities: ['rewards']`.

**appSettings** (заморозка при ACTIVE): `{ "drawEligibility": "guests_allowed" }` — public; `"verified"` = вес только у REGISTERED (REQ-RWD-014).

**События** (dotted-lowercase, неймспейс `lottery.`):

| Тип | Эмитент | Ceiling | Назначение |
|---|---|---|---|
| `draw.run` | клиент-организатор | public | команда `{ drawId, prizeId }` — разыграть приз |
| `draw.completed` | модуль (actorId=null) | public | результат `{ drawId, prizeId, winnerId }` |

`drawId` — клиентский uuid: **идемпотентность команды розыгрыша**. Повтор `draw.run` с тем же `drawId` → типизированный no-op с прежним результатом (иначе retry после успешного коммита разыграл бы приз повторно и списал вторую единицу фонда — «сетевой повтор той же награды» REQ-RWD-003 на уровне app-команды). Использованные `drawId` хранятся в проекции.

**Поток `handlePublish('draw.run')`:**
1. Гейт модуля: роль ORGANIZER, иначе `AppRejection`. ACTIVE — гейт диспетчера (наследуется).
2. Повтор `drawId` → typed no-op до розыгрыша.
3. Пул: `ctx.drawPool`; при `drawEligibility: 'verified'` модуль отбрасывает `kind: 'GUEST'`. Из пула исключаются прежние победители этого приза (по проекции — UX; индекс остаётся страховкой).
4. Пустой пул → отказ `DRAW_POOL_EMPTY` до коммита.
5. Победитель: `pool[ctx.randomInt(pool.length)]` (REQ-RWD-011).
6. Возврат: эффект `{ kind: 'award.prize', prizeId, winnerId }` + событие `draw.completed`; диспетчер исполняет и коммитит одной транзакцией (§2). Фонд исчерпан → `PRIZE_FUND_EXHAUSTED`, событие в лог не попадает.

**Проекция:** список розыгрышей `{ drawId, prizeId, winnerId }` — чистый редьюсер по `draw.completed`, replay из лога (REQ-CORE-004). Своих таблиц нет: состояние наград — в rewards, история — в логе.

**Конкурентность.** Per-room сериализация диспетчера (RoomSerializer, ф.2) делает однокомнатные `draw.run` последовательными; инвариант REQ-RWD-010 держится не на ней, а на DB-декременте (§7, тест 2).

**Связь с квизом:** отсутствует. «Разыграть среди набравших N очков» — фильтр пула по начислениям, задел будущей механики, в MVP не проектируется (YAGNI).

## §5. Перевод квиза на начисления + TTL-свип

**Квиз → начисления rewards:**
- Манифест квиза: `manifestVersion` 1 → **2**, `capabilities: ['rewards']`, `contractRange` под SDK 1.6.0. Пин `(appId, manifestVersion)` (REQ-RT-004) работает штатно; миграция контента не нужна (активных квиз-комнат нет).
- Точка начисления — `question.closed`: модуль считает очки раунда и в том же возврате, что и `question.revealed`, добавляет эффекты `{ kind: 'award.points', identityId, points, reason: 'quiz.round' }` на каждого ответившего с points > 0. Одна транзакция: reveal-событие и ledger-записи коммитятся или откатываются вместе.
- **Табло остаётся проекцией квиза**; rewards-ledger — платформенная запись (задел под «мои выигрыши»). Дублирование осознанное; инвариант «менять вместе»: изменение скоринга трогает обе записи; сходимость контролируется тестом (сумма очков reveal == сумма points в ledger по комнате).
- Идемпотентность: повторный `question.closed` гасится существующим гейтом «раунд уже закрыт» до эффектов.
- Итоговых начислений за место нет (решение §0.8); `game.finished` эффектов не несёт.

**TTL-свип гостей (REQ-ID-003/014 + REQ-RWD-013):**
- Джоба в `identity`-модуле на `@nestjs/schedule`, интервал — существующий параметр `cleanup_interval` (дефолт 1 ч, §4 пакета). Одна реплика (REQ-OPS-005) — дублей джобы нет.
- Анонимизация (одна транзакция): `UPDATE identity SET displayName = NULL, email = NULL, deletedAt = now() WHERE kind='GUEST' AND deletedAt IS NULL AND createdAt < now() - guest_ttl AND <нет приостановки>` + отзыв живых сессий гостя (`revokedAt`) — по прецеденту среза исключения. База TTL — `createdAt` (решение §0.8).
- **Приостановка через hook, не импортом:** identity объявляет DI-токен `ANONYMIZATION_GUARDS` (массив) с `hasOpenAwards(identityIds): Promise<Set<string>>`; rewards регистрирует guard (запрос по `Award.status='AWARDED'`). Identity про rewards не знает — REQ-RWD-001 сохранён; без подключённого rewards приостановки нет. Паттерн — по прецеденту `onAccessRevoked`.
- Гость под приостановкой: сессия истекает по своему капу как обычно (войдёт заново по коду — identity та же); анонимизация — только после разрешения награды.

## §7. Тестирование и критерии выхода (фаза 3, пакет §5)

TDD: контрактные фикстуры SDK первыми, затем int (testcontainers), затем e2e на проводе.

1. **e2e лотереи** (`lottery.e2e-spec.ts`, реальный socket.io): гости входят → приз создан (REST) → `draw.run` → `draw.completed`, победитель из пула → награда AWARDED; fulfill и revoke (с возвратом quantity) через REST; публичность событий live + replay.
2. **Транзакционные тесты (int):** конкурентный дубль одного награждения → один победитель, quantity −1 ровно раз (REQ-RWD-003); **K > quantity конкурентных награждений разным identity → ровно `quantity` успехов, без минуса (REQ-RWD-010)** — на RewardsService + e2e-версия K параллельных `draw.run`; повторное вручение → no-op; двойной отзыв → quantity возвращён один раз (REQ-RWD-007); отзыв освобождает место под индексом, вручённая — нет.
3. **Непредсказуемость (REQ-RWD-011):** контрактный тест `randomInt` (node:crypto, границы bound); статистический sanity распределения; отсутствие сида из наблюдаемого — конструкцией + ревью-чеклист.
4. **Eligibility (REQ-RWD-014):** `verified` → гости вне пула (e2e: гости + один REGISTERED → победитель всегда REGISTERED); дефолт `guests_allowed` → гость может выиграть.
5. **Приостановка TTL (REQ-RWD-013):** int свипа: гость с истёкшим TTL и открытой AWARDED не анонимизирован; после fulfill/revoke — анонимизирован следующим проходом; сессии отозваны; REGISTERED не тронут.
6. **REQ-RWD-009:** комната → COMPLETED; `GET /rooms/:id/rewards` показывает оставшиеся AWARDED; fulfill/revoke после завершения работают.
7. **Границы и контракт:** boundary-check (ядро-мимо-токена → rewards; app-lottery → core); commit-гейт отклоняет эффект без capability; заниженная visibility `draw.*` отклоняется (REQ-CTR-009); PII-тест payload'ов (REQ-SEC-009); автотест наличия частичного индекса (REQ-DEV-006).
8. **Квиз-начисления:** e2e — после reveal ledger-записи появляются, суммы сходятся с табло; квиз v1 (без capability) эффекты эмитить не может (гейт).

## §8. Риски и открытые пункты

- **Гейт 2:** старт реализации — после первого живого события, отдельным решением владельца (§0.1).
- **Дублирование счёта квиза** (проекция vs ledger): осознанное; инвариант «менять вместе» + тест сходимости (§5).
- **Латентность draw:** `drawPool` грузит membership на розыгрыш — редкая организаторская команда, оптимизаций не надо.
- **`randomInt` в ctx** — зафиксированное расширение трактовки REQ-CTR-002 (§2); не считать дрейфом на ревью.
- **AJV `format: "uuid"`** (отложенный кандидат ф.2): в ф.3 появляются новые uuid-поля на commit-гейте (`drawId`, `prizeId`). Предложение — решить в этой фазе подключением `ajv-formats` на commit-гейте; решение владельца, первая задача-развилка плана.
- **Кандидат lint-правила:** запрет `Math.random` в `packages/app-*` — поднимется в плане как опциональная задача усиления REQ-RWD-011.
