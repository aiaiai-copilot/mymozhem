## §2. Сервер: №2 — флаг `COOKIE_SECURE`

**Проблема:** `setRefreshCookie` выставляет `secure: config.NODE_ENV === 'production'` (`packages/core/src/transport/refresh-cookie.ts:20`). LAN-стенд в compose идёт под `NODE_ENV=production` по plain HTTP → браузер не принимает Secure-куку → у телефонов 15-минутный потолок сессии (access-токен умирает, refresh невозможен), перезаход = новая identity = очки сгорают.

**Дизайн:**
- `AppConfig += COOKIE_SECURE: z.enum(['auto', 'true', 'false']).default('auto')` (config.schema.ts; `TEST_CONFIG` синхронно).
- `setRefreshCookie`: `auto` → текущее поведение (`NODE_ENV === 'production'`); `'true'`/`'false'` → явно. Три состояния, а не boolean: дефолт обязан сохранять существующую семантику «prod = Secure» без вычитывания NODE_ENV вызывающим.
- Compose-стенд и bare-run регламент (§3) получают `COOKIE_SECURE=false` с комментарием «только plain-HTTP LAN/self-hosted».
- Дефолт нетронут: hosted/prod-деплой без переменной ведёт себя как сейчас.

**Тесты (сначала, TDD):**
- unit `refresh-cookie.spec.ts`: атрибут `secure` при `auto`+production / `auto`+development / `'true'` / `'false'` (4 кейса, ReplyLike-фейк по существующему образцу).
- int конфиг-парсинга: дефолт `auto`, невалидное значение → отказ загрузки конфига (fail-fast, образец JWT_SECRET).

## §3. Регламент: №7 — bare-run сервера на событие

**Проблема:** docker NAT на compose-стенде показывает серверу всех клиентов под IP gateway'я: exclusion по IP банит всех (воспроизведено curl → ROOM_JOIN_DENIED), join rate-limit (`JoinRateLimiter`, membership) — общая касса.

**Решение владельца:** код не меняем; на событие сервер запускается на хосте. В чеклист первого события (`docs/sessions/2026-09-23-ui-slice-smoke-checklist.md`) добавляется блок «Стенд на событие»:

1. `docker compose up postgres` — в контейнере остаётся только БД.
2. Сервер на хосте: `pnpm build` + `pnpm --filter @mymozhem/server start` (или `node apps/server/dist/main.js`), env: `DATABASE_URL` на localhost-порт compose-postgres, `ORGANIZER_SETUP_TOKEN`, `PRIZE_MODE=off` (дефолт ADR-012), `COOKIE_SECURE=false`.
3. Web — собранный SPA отдаётся тем же сервером (`WEB_STATIC_DIR`), как в compose: один origin на LAN-IP хоста.
4. **Контрольная строка приёмки стенда:** участник с телефона исключается → ROOM_JOIN_DENIED получает **только он**, остальные продолжают (доказательство реальных IP). Вторая контрольная: массовый вход 5+ устройств без 429.

Страховка логики — e2e A1 (§6.1). Класс «браузер × топология» в целом — LAN-smoke A2 (§6.2).

## §4. Клиент: №4 — single-flight refresh

**Проблема:** strict-ротация refresh + параллельные refresh с одной кукой. На загрузке /host refresh дёргают до трёх производителей почти одновременно: HostGate (silent refresh), ApiClient (401 → refresh → retry), RoomConnection (refresh-хук на handshake-отказ). Все шлют **одну и ту же** refresh-куку; первый запрос ротирует токен, второй с тем же токеном = «rotation race lost» → сервер гасит семью → сессия мертва. На репетиции — 3 убитые сессии консоли за день.

**Дизайн (`apps/web/src/state/session.ts`):**
- `SessionStore.refresh()` мемоизирует in-flight промис: первый вызов запускает `refreshFn()`, параллельные вызовы получают тот же промис; после settle (успех ИЛИ провал) мемо сбрасывается — следующий refresh разрешён (провал не блокирует навсегда).
- Одна точка в SessionStore покрывает всех производителей: все они идут через `SessionStore.refresh()` (hostSession и per-page гостевые экземпляры — каждый свой, что корректно: у них разные refreshFn/области).
- Подписчикам промиса отдаётся одно и то же settle-значение — семантика «ровно один сетевой refresh на окно конкуренции».

**Принятый остаточный риск:** истинный обрыв ответа ротации перезагрузкой страницы (F5 ровно в полёте refresh → новая кука потеряна, старая инвалидирована) single-flight НЕ закрывает — окно сужается до доли секунды на один запрос вместо шторма, но не исчезает. Лечение — grace-окно прежнего токена на сервере; это смягчение strict-ротации (security-семантика) — **отдельное решение владельца, в пакет не входит**. Триггер возврата к вопросу: воспроизведение «rotation race lost» после фикса.

**Тесты (сначала, TDD; они же — пин A3):**
- Параллельные `refresh()` ×3 → `refreshFn` вызван ровно 1 раз, все три промиса resolved с одним токеном.
- После успешного settle следующий `refresh()` вызывает `refreshFn` снова.
- После провала settle следующий `refresh()` разрешён (retry не заблокирован).

## §5. Клиент: №5 — автоперезаход при мёртвой сессии

**Проблема:** RoomConnection при провале refresh-хука (мёртвая refresh-кука) переводит состояние в общий `'disconnected'` — страница показывает «Переподключаемся…», а fallback в перезаход существует только на загрузке страницы (play-page §5 авто-вход). Участник не понимает, что надо перезагрузить.

**Ключевое ограничение:** `'disconnected'` — также и состояние обычного обрыва сети (onDisconnect), по которому перезаходить НЕЛЬЗЯ (socket.io сам ретраит, re-subscribe самолечится). Триггером автоперезахода является строго «refresh провалился».

**Дизайн:**
- `RoomConnection` получает колбэк `onSessionDead?: () => void` (опциональный, как refresh-хук): стреляет ровно из ветки провала `refreshAccessToken()` в onConnectError — там, где сейчас `stateCb?.('disconnected')`. Состояние 'disconnected' сохраняется (баннер остаётся корректным на время перезахода).
- `useRoomBinding` пробрасывает `onSessionDead` от потребителя.
- `play-page`: rejoin-ветка авто-входа (joinRoom по сохранённым code/displayName → setRejoined(true) → баннер «вы вошли заново») выделяется в функцию `rejoin()`; вызывается из двух мест: mount-effect (как сейчас, когда silent refresh провалился) и `onSessionDead`. Гард от двойного перезахода: rejoin уже в полёте/состоялся → повторный onSessionDead no-op (started-ref по образцу существующего StrictMode-гарда).
- `screen-page` (spectator): тот же перезаход по onSessionDead (join role 'spectator' displayName 'Экран', БЕЗ saveGuest — существующий контракт страницы сохраняется).

**Не делаем:** счётчик «N неуспешных refresh» — дозировка «один refresh на стрик обрыва» уже есть в RoomConnection (refreshAttempted); провал этого одного = терминальное состояние сессии, автоперезаход сразу.

**Тесты (сначала, TDD):**
- RoomConnection: провал refresh-хука → `onSessionDead` вызван; обычный `onDisconnect` → `onSessionDead` НЕ вызван; повторный стрик после успешного connect → снова имеет право на refresh (существующее поведение не сломано).
- play-page (unit на выделенной rejoin-функции): onSessionDead → joinRoom с сохранёнными code/displayName; двойной onSessionDead → один join.

## §6. Клиент: №6 — рефетч в момент действия + по фокусу

**Проблема:** join не эмитит событий (интерпретация I-3 UI-среза — сознательная), перезаходы участников невидимы ведущему до ближайшего события; «Исключить» из MembersPanel бьёт по старой identity (перезашедший продолжает играть). Замечание владельца: поллинг с задержкой 15–30 с неприемлем.

**Дизайн:**
1. **Рефетч перед exclude (members-panel.tsx):** клик «Исключить» → `listMembers(hostClient, roomId)` → сверка identityId со свежим активным ростером:
   - identity активна → `excludeMember` по свежему списку (прежний путь);
   - identity исчезла (перезаход) → exclude НЕ отправляется; `onChanged()` (обновить ростер в UI) + ошибка «Участник перезашёл — список обновлён, выберите заново» (`role="alert"`, стиль существующего excludeErrorText).
   - TOCTOU-окно между рефетчем и exclude — миллисекунды, принимаем (это UX-гарда, не инвариант; серверный exclude по мёртвой identity остаётся типизированным no-op/ошибкой).
2. **Рефетч по фокусу (use-room-feed.ts):** `visibilitychange → visible` (и `focus` для браузеров без visibilitychange на вкладках) → `refetchMembers()`, дедуп: не чаще одного рефетча в 2 с (timestamp-гард). Без интервального поллинга.

**Не делаем:** событие join в realtime — трогает контракт ядра и I-3; для закрытия находки не нужно. Кандидат на продуктовое обсуждение будущих фаз (вместе с device-cookie, §9-шов).

**Тесты (сначала, TDD):**
- members-panel: stale identity → listMembers вызван, excludeMember НЕ вызван, показан alert, onChanged вызван; свежая identity → excludeMember вызван (порядок: listMembers ДО excludeMember).
- use-room-feed: visible-событие → refetchMembers; два visible подряд в пределах 2 с → один рефетч.

## §7. Клиент: №3 — стейл-roomId в консоли

**Проблема:** консоль читает roomId из `mm.host.roomId` (localStorage); комната из прошлой БД → join/subscribe отказывает `ACTOR_NOT_MEMBER`; use-room-binding тонет отказ в `'disconnected'` без кода → консоль висит на «Нет соединения». Обход известен (`localStorage.clear()`), но недиагностируем ведущим.

**Дизайн:**
- `useRoomBinding` дополнительно возвращает `joinError: string | null` — wire-код из ApiError стартового join (`join().catch`), null при успехе/не-ApiError (сетевые отказы остаются 'disconnected' без кода).
- `console-page`: `joinError === 'ACTOR_NOT_MEMBER' || joinError === 'NOT_FOUND'` → `localStorage.removeItem` обоих ключей (`mm.host.roomId`, `mm.host.roomCode`) + экран «Комната не найдена» со ссылкой на `/host/setup` (создать новую). Прочие коды — прежний баннер «Нет соединения» (поведение не меняется).
- Очистка ключей — однократно при показе экрана (не на каждый рендер): effect по joinError.

**Тесты (сначала, TDD):**
- use-room-binding: join-отказ ApiError(ACTOR_NOT_MEMBER) → joinError = код, состояние 'disconnected'; сетевой отказ (не ApiError) → joinError = null.
- console-page: joinError ACTOR_NOT_MEMBER → ключи очищены, показано «Комната не найдена»; прочий код → ключи на месте.

## §8. Автоматика

### §8.1 (A1) e2e exclusion/rate-limit через XFF (apps/server, обычный CI)

TRUST_PROXY существует (`config.schema.ts:48`, FastifyAdapter в `main.ts:21`) — нового конфига не надо. Новый e2e-сьют (образец — существующие server e2e на реальном AppModule): boot с `TRUST_PROXY=true`, запросы через inject с разными `x-forwarded-for`.

Сценарии:
1. **Exclusion per-IP:** два клиента с XFF A и B входят в комнату; организатор исключает клиента A → повторный join с XFF A → ROOM_JOIN_DENIED; join с XFF B (новый клиент) → 201. (Класс №7: бан ровно одного, не всех.)
2. **Rate-limit per-IP:** N входов с XFF A до потолка → 429/ROOM_JOIN_RATE_LIMITED; вход с XFF B — разрешён. (Класс №7: касса не общая.)
3. **Fail-closed пин:** boot с `TRUST_PROXY=false` (дефолт TEST_CONFIG) → XFF игнорируется, req.ip — peer (inject-адрес). Запирает семантику main.ts.

### §8.2 (A2) LAN playwright-smoke (apps/web/e2e)

Существующий `playwright.config.ts` зашит на localhost:3000 намеренно (защита от прогона по продy). LAN-вариант — отдельный `playwright.lan.config.ts` рядом:
- `baseURL` из env `LAN_BASE_URL`;
- **fail-closed валидация до старта тестов:** хост обязан быть `localhost`/`127.0.0.1` или RFC1918-IP (10/8, 172.16–31/12, 192.168/16), схема — только `http`; любой другой хост или схема → throw с текстом причины. Интент «никогда не production» сохранён машинно.
- Сьют тот же (`smoke.spec.ts`), workers/retries/timeout наследуются.
- Скрипт `test:e2e:lan` в apps/web/package.json; строка в чеклисте первого события: «LAN-smoke прогнан против стенда по IP» (рядом с блоком §3).

Ловит класс «браузер × топология» (№1 CSP, №2 Secure-кука) до события. Не в GitHub Actions (раннер вне LAN) — ручной ритуал перед репетицией/событием, что соответствует природе класса.

### §8.3 (A3) Пин single-flight

Тесты §4 — они и есть пин (одна задача, не две). Дополнительно пин RoomConnection на onSessionDead (§5) — предохранитель от регрессии «всё снова тонет в disconnected».

## §9. Тест-стратегия и приёмка

- **TDD по правилам репо:** тесты первыми в каждой задаче; контрактные не задеты (wire-контракты/SDK не меняются — все фиксы внутри границ модулей).
- **Гейты CI:** lint, typecheck, unit, int, server e2e (включая новый XFF-сьют), boundary-check — зелёные на каждом батче. LAN-smoke — не в CI (§8.2).
- **Ручная приёмка пакета:** повторный прогон строк 7.1 (reload консоли — сессия жива), 11.1 (exclude бьёт ровно одного; стейл-ростер — alert «участник перезашёл»), 12.2 (reload участника на LAN → сессия восстановлена; протухание → автоперезаход без перезагрузки) против bare-run/compose-стенда с `COOKIE_SECURE=false`; протокол — в таблице чеклиста.
- **Батчи:** исполнение по правилу «3 задачи на сессию», каждый батч — новая сессия; в конце пакета финревью (spec-compliance по REQ-разметке §10 → code-quality) + HANDOFF.

## §11. Принятые остаточные риски (фиксируются, не закрываются)

1. Истинный обрыв ответа ротации перезагрузкой (№4-остаток) — окно сужено, не закрыто; триггер возврата — воспроизведение после фикса (тогда grace-окно отдельным решением).
2. TOCTOU-окно рефетч-перед-exclude (миллисекунды) — UX-гарда, не инвариант.
3. docker NAT при compose-деплое остаётся (№7 закрыт регламентом; device-cookie/пересмотр IP-фич — шов §9 будущих фаз, решение владельца №1).
4. LAN-smoke — ручной ритуал; ценность зависит от дисциплины прогона перед событием (строка чеклиста — напоминание).
