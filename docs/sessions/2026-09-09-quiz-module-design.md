## §0. Решения владельца (brainstorm 2026-09-09)

1. **Игровая модель:** раунды на скорость + очки. Серия раундов «вопрос → приём ответов → закрытие», победитель по сумме очков.
2. **Формат ответа:** выбор из вариантов по индексу (`optionIndex`); правильный ответ — `correctIndex`, хранится module-private. Свободный текст — не в MVP.
3. **Ход раундов:** ручной драйв ведущим. Серверных таймеров и автопереходов нет; организатор открывает и закрывает вопросы явными командами.
4. **Очки:** скоростная шкала — k-й правильный ответ в раунде получает `max(base − (k−1)·step, 0)`; порядок — по seq лога.
5. **Рантайм-модель app-модулей — подход A «командный хост»:** ядро диспетчерит app-publish в модуль **до коммита**; модуль возвращает события или типизированный отказ. Отклонены: B (реактор после коммита — отказ REQ-RT-013 превращается в void-событие, publish-ack не отвечает «отклонено», лог загрязняется, арбитраж фильтрует void'ы) и C (сетевой сервис — против ADR-001/REQ-OPS-005).
6. **SPECTATOR:** флаг в join-запросе (`role: 'participant' | 'spectator'`, дефолт participant); зритель не может publish'ить app-события (гейт ядра в диспетчере).

## §1. Объём и закрываемые требования

Срез двухслойный: (а) рантайм-поверхность app-модулей в SDK+ядре (переиспользуемая лотереей и дегустациями), (б) квиз на ней.

- **REQ-CTR-001/002/003** — модуль общается с ядром только через SDK-интерфейсы, сетевая форма (JSON DTO), zod как источник истины контракта. Рантайм-интерфейс `AppRuntimeModule` — часть SDK.
- **REQ-CTR-004** — версия контракта 1.4.0 → **1.5.0** (аддитивно, minor); манифест квиза объявляет диапазон.
- **REQ-CTR-005** — контрактные фикстуры на всё новое (валидные/невалидные payload'ы событий квиза, join с ролью, рантайм-DTO).
- **REQ-CTR-008/009** — квиз регистрирует zod-схемы событий с per-type visibility ceiling через существующий `defineApp`; ядро отклоняет заниженную visibility (наследуется, перепроверяется на app-типах).
- **REQ-CORE-004/005/008** — состояние модуля — пересоздаваемая проекция, не глобальное мутируемое; проекции наружу строит ядро; `correctIndex` module-private.
- **REQ-RT-004** — активная комната валидируется пином `(appId, manifestVersion)`; диспетчер выбирает версию модуля по пину.
- **REQ-RT-007** — payload-нейтральность гонки за seq на app-событиях (тест).
- **REQ-RT-009** — actorId только из аутентифицированного контекста; app-сообщения валидируются схемами владельца типа (наследуется, проверяется на квизе).
- **REQ-RT-013** — анти-бот: отказ при `now − openedAt < minAnswerIntervalMs`; параметр в appSettings; 0 = окно вместо интервала.
- **REQ-ID-011 (часть SPECTATOR)** — роль получает путь назначения (join-флаг) и правовой гейт (чтение public-проекции без publish).

**Критерии выхода фазы 2 (пакет §5)** — см. §7.

**Вне объёма (явно):** rewards и начисления (фаза 3), MODERATOR-права и аудит (фаза 4), UI клиентов, таймеры/автозакрытие раундов, свободный текст ответов, лотерея, HTTP-эндпоинт для `configure` (остаётся service-уровнем; e2e конфигурирует комнату через сервис/сид, как в фазе 1). Задел под фазу 3 — только словами: `game.finished` несёт финальный счёт в форме, пригодной для начислений rewards.

## §2. Архитектура: командный хост

**Пакеты.** Новый `packages/app-quiz` (`@mymozhem/app-quiz`), импортирует только `@mymozhem/sdk` — boundary-правило `app-only-through-sdk` в dependency-cruiser уже вооружено и проверяет это в CI. Ядро квиз не импортирует; связывание — только в `apps/server` (composition root).

**SDK (v1.5.0).** Новые контрактные элементы:
- `AppRuntimeModule` — интерфейс модуля: `handlePublish(ctx, msg) → AppCommit[]` (отказ — брошенный `AppRejection` с типизированным кодом) и редьюсер `reduce(state, event) → state`.
- `AppHostContext` — что ядро передаёт модулю: `roomId`, `actorId` (из аутентифицированного контекста, REQ-RT-009), роль актора, текущая проекция состояния, серверное время. Никаких живых объектов ядра (сервисов, ORM) — только JSON-сериализуемые DTO (REQ-CTR-002).
- `AppCommit` — `{ type, payload, visibility }` (payload валидируется ядром схемой владельца при коммите — модуль не обходит гейты).
- Поле `role` в `join-request` (см. §5).
- Манифест: пометка клиентских команд — типы, открытые для клиентского publish (`question.opened`, `answer.submitted`, `question.closed`, `game.finish`); производные типы (`answer.accepted`, `question.revealed`, `game.finished`) клиенту закрыты, эмиссия только модулем с `actorId = null`. Явное поле в манифесте (машинно проверяемо), не вывод из сигнатур.

**Ядро: новый модуль `core/src/app-runtime/`.**
- Диспетчер на пути `publish` в `RealtimeGateway`: тип app-неймспейса → (а) роль SPECTATOR → типизированный отказ до вызова модуля (матрица REQ-ID-011 — правило ядра, не квиза); (б) проверка «тип — клиентская команда» по манифесту; (в) загрузка/пересоздание проекции комнаты для appId; (г) `handlePublish` модуля; (д) возвращённые `AppCommit[]` коммитятся через существующие `EventOutbox.run` + `commitAppEvent` — все гейты фазы 1 (Ajv-валидация, visibility ceiling REQ-CTR-009, per-actor rate-limit REQ-RT-014, status ACTIVE, запечатывание REQ-RT-016) работают без дублирования. Отказ модуля → типизированный reject в publish-ack (синхронно — то, ради чего выбран подход A).
- Регистрация рантайм-модулей — DI-токен `APP_RUNTIME_MODULES` по образцу `APP_MANIFESTS`; версия модуля выбирается пином комнаты (REQ-RT-004).
- Серверный replay-API для модулей: чтение событий комнаты на уровне module-private (внутренний путь, не клиентский канал). Основа пересоздания проекций.
- `APP_MANIFESTS`-seam переезжает из `AppRegistryModule` (сейчас зашит `useValue: []`) в composition root — туда же `APP_RUNTIME_MODULES`.

**Состояние.** Проекция модуля — in-memory кэш `roomId → state`, пересоздаваемый replay'ем лога (ADR-005, REQ-CORE-004). Тёплый путь — O(1). Таблиц у квиза нет: вопросы — appSettings (заморожены при ACTIVE), счёт и ход раунда — из лога.

## §3. Модель данных квиза

**appSettings** (замораживаются при ACTIVE, REQ-RT-004; поле-уровневая видимость через `x-visibility`, REQ-CORE-008):

```jsonc
{
  "questions": [{ "text": "…", "options": ["…", "…"] }],  // public (x-visibility)
  "correctAnswers": [2, 0, …],        // БЕЗ аннотации → module-private (fail-safe); i-й элемент — correctIndex i-го вопроса
  "minAnswerIntervalMs": 800,         // public; arbitration_min_answer_interval, REQ-RT-013; 0 = окно
  "scoring": { "base": 1000, "step": 100 }  // public; скоростная шкала
}
```

Отсутствие аннотации = module-private (fail-safe встроен в фазу 1). Даже organizer-проекция не отдаёт `correctAnswers` до закрытия вопроса: раскрытие — отдельным событием `question.revealed`.

*Почему два ключа, а не `correctIndex` внутри объекта вопроса:* проекция видимости ядра (`appSettingsVisibilityMap`, фаза 1) работает по верхнему уровню `properties`; смешанная видимость внутри одного свойства невыразима без расширения ядра. Раскладка на два ключа даёт ту же защиту существующим механизмом. Цена — инвариант `correctAnswers.length === questions.length` невыразим в JSON Schema без `.refine` (запрещён conversion guard'ом defineApp); модуль трактует отсутствующий `correctAnswers[i]` как «у вопроса нет правильного ответа» (все ответы неверные), конфиг-ошибка не открывает утечку.

**События** (короткие имена, ядро префиксует `quiz.`):

> **Erratum 2026-09-09 (батч 3, ruling контролёра):** имена типов переведены из camelCase (`questionOpened`…) в dotted-lowercase (`question.opened`…) — `shortEventNameSchema` (контракт, `sdk/src/events/event-type.ts:27`) принимает только dotted-lowercase; ослаблять схему контракта ради нейминга одного приложения нельзя. Семантика таблицы не изменена.

| Тип | Эмитент | Ceiling (REQ-CTR-009) | Назначение |
|---|---|---|---|
| `question.opened` | клиент-организатор | public | открыть вопрос `{ questionIndex }`, старт окна приёма |
| `answer.submitted` | клиент-участник | module-private | `{ questionIndex, optionIndex }` |
| `answer.accepted` | модуль (actorId=null) | public | «игрок X ответил», без optionIndex — живое табло |
| `question.closed` | клиент-организатор | public | закрыть приём |
| `question.revealed` | модуль | public | раскрытие: correctIndex + очки раунда по игрокам |
| `game.finish` | клиент-организатор | public | завершить игру (команда) |
| `game.finished` | модуль | public | итоговое табло (форма пригодна для начислений rewards в фазе 3) |

## §4. Состояние, проекция, счёт, арбитраж

**Проекция модуля:** `currentQuestionIndex | null`, «приём открыт», `openedAt` (committedAt события `question.opened` — серверное), множество ответивших на текущий вопрос (с их optionIndex и seq), накопленный счёт. Редьюсер чистый, юнит-тесты без БД.

**Счёт:** при `question.closed` модуль ранжирует правильные ответы по seq и эмитит `question.revealed` с очками раунда: k-й правильный → `max(base − (k−1)·step, 0)`; неправильный — 0 и «сгорает» (повторный ответ на вопрос отклоняется). Табло клиентов ничего не вычисляет — получает готовое из лога.

**Арбитраж:** порядок ответов = порядок фиксации (seq, ADR-005); гонку разрешает ядро (`appendLocked`, advisory lock), модуль гонок не видит.

**Анти-бот (REQ-RT-013):** в `handlePublish(answer.submitted)`: `now − openedAt < minAnswerIntervalMs` → отказ `ANSWER_TOO_FAST` до коммита. Время — только серверное; клиентские timestamp — телеметрия. `minAnswerIntervalMs = 0` — контроль выключен (режим окна).

**Отказы модуля (все до коммита, типизированные, в publish-ack):** раунд не открыт; уже отвечал на этот вопрос; ответ на неоткрытый/несуществующий вопрос; нет такого optionIndex; слишком быстро; не та роль (SPECTATOR — гейт ядра; не-ORGANIZER для управляющих команд — гейт модуля по роли из ctx).

**Late-join / reconnect:** snapshot публичной проекции (механизм фазы 1) — текущий вопрос, варианты, табло; отвечать можно сразу. Module-private события недоступны ни в snapshot, ни live, ни replay — наследуется из фазы 1, перепроверяется чит-тестом (§7).

## §5. SPECTATOR и дельты контракта

- `join-request` += необязательное `role: 'participant' | 'spectator'` (дефолт participant). Схема отсекает иные значения — ORGANIZER/MODERATOR через флаг не получить.
- Membership при join создаёт членство с запрошенной ролью. Единообразие отказов REQ-ID-013 не трогается — роль влияет только на успешную ветку.
- Права: (1) гейт ядра в диспетчере — publish от SPECTATOR → типизированный отказ; (2) проекция — тот же уровень public, что участник (organizer-уровень только у ORGANIZER, как сейчас).

## §6. Сборка дельт по пакетам

- **`sdk`:** `AppRuntimeModule` / `AppHostContext` / `AppCommit` / `AppRejection`; `role` в join-request; манифест += клиентские команды; контракт → 1.5.0; фикстуры на всё новое (REQ-CTR-005).
- **`core`:** модуль `app-runtime` (диспетчер, replay-API, кэш проекций); гейт SPECTATOR; membership принимает роль из join; `APP_MANIFESTS` из composition root.
- **`app-quiz`:** манифест через `defineApp`; zod-схемы событий и appSettings; редьюсер; handlers команд; скоринг.
- **`apps/server`:** провайдеры `APP_MANIFESTS` + `APP_RUNTIME_MODULES`, импорт квиз-модуля.

## §7. Тестирование и критерии выхода (фаза 2, пакет §5)

TDD: контрактные фикстуры SDK первыми, затем int/e2e.

1. **Приёмочные e2e квиза** (база — TS-Q из appendix): вход гостей; полная игра (открытие → ответы → закрытие → reveal → табло); late-join участника и зрителя в ACTIVE. `quiz.e2e-spec.ts` через реальный socket.io.
2. **Чит-тест (расширенный):** `correctIndex` недоступен участнику ни через REST, ни live, ни snapshot/replay, ни через appSettings-проекцию, ни по метаданным seq; до `question.revealed` недоступен и organizer-проекции. Чужие `answer.submitted` не видны участникам ни по одному каналу.
3. **Анти-бот (REQ-RT-013):** ответ раньше `minAnswerIntervalMs` → отказ; после — принят. Конкурентный тест: два одновременных ответа одного участника → один отклонён, в логе ровно один.
4. **Payload-нейтральность гонки за seq (REQ-RT-007)** на app-событиях (харнесс фазы 1, смешанные размеры payload).
5. **Ролевые гейты:** SPECTATOR publish → отказ; не-ORGANIZER `question.opened`/`question.closed`/`game.finish` → отказ.
6. **Пересоздание состояния:** инвалидация кэша проекции (или рестарт в int-тесте) → состояние восстанавливается replay'ем, счёт сходится.

## §8. Риски и открытые пункты

- **Латентность publish:** диспетчер добавляет hop «проекция → модуль → коммит». На холодную комнату — replay. Под профиль «100 участников, всплеск в секунду» меряем нагрузочным тестом фазы 4; в фазе 2 — только кэш (тёплый путь O(1)). Оптимизации (предзагрузка при subscribe) — не делать упреждающе.
- **Итоговая форма счёта** в `game.finished`/`question.revealed` фиксируется в плане реализации так, чтобы фаза 3 (rewards) могла начислять из неё без миграций — аддитивная эволюция контракта (REQ-DEV-007).
