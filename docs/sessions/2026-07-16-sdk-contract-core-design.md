**Статус:** одобрен владельцем в сессии, ожидает ревью файла
**Основание:** нормативный пакет v1.2 (§5 фаза 1, §6.1), амендмент v1.3, ADR-002/003/005/005a/006/008/009

## 1. Объём

**В объёме — ядро контракта:** конверт события лога и проекция наружу, уровни видимости,
манифест приложения, реестр app-схем событий, версионирование и пин.
Артефакт кода — только `packages/sdk` (схемы + фикстуры).

**Сверх схем спека фиксирует точки принуждения** (§7) — кто, что и когда валидирует.
Это не код этой спеки, а ограничения для последующих планов фазы 1: контракт,
который нечем принудить, бесполезен, поэтому места принуждения проектируются вместе
с формой.

**Вне объёма:**

- **DTO identity / room / membership** — механичны, выводятся однозначно после того,
  как решён этот узел. Отдельной спекой.
- **Сервисы ядра** (App-registry, построитель проекций, конвейер фиксации) — отдельный план.
- **Контракт rewards** — §6.1 включает его в SDK-контракт, но §5 кладёт Rewards в фазу 3,
  а гейт 2 запрещает тяжёлые вложения в фазу 3 до первого живого события. Расхождение внутри
  пакета разрешено в пользу §5. Безопасно по фильтру задела: ADR-003 даёт rewards собственный
  контракт, подключаемый через capability манифеста, то есть аддитивный по конструкции.

## 3. Эмпирические находки (проверены на zod 4.4.3, не взяты из памяти)

Четыре факта, на которых держатся решения §4–§6. Проверялись запуском, а не документацией;
воспроизводятся пробой на `z.toJSONSchema` из контекста пакета `packages/sdk`.

1. **`z.toJSONSchema` молча теряет `.refine()`.** Схема `{a, b}` с правилом `a < b`
   конвертируется без следа правила: ни ошибки, ни предупреждения. Вложенный `.refine()`
   теряется так же.
2. **Непредставимые типы, наоборот, бросают:** `date`, `bigint`, `.transform()` →
   исключение. Флаг `unrepresentable: 'throw'` на refine **не** срабатывает — он про типы,
   не про проверки. Обычные проверки (`.min(1)` → `minLength: 1`) доезжают штатно.
3. **`.refine()` детектируется — но признак не «лежит в `_zod.def.checks`».** Туда же ложится
   и `.min(1)`, поэтому страж, написанный по этому признаку, отверг бы почти любую легальную
   схему. Дискриминатор — **`check === 'custom'`**: так помечены `.refine()`/`.superRefine()`,
   тогда как штатные проверки несут `min_length` / `greater_than` / `string_format`. Обход
   дерева даёт **хук `override`** — он вызывается на каждом подузле, включая вложенные и внутри
   массивов; ручная рекурсия не нужна и пропустила бы формы. Значит fail-closed страж
   строится (§6).
4. **`.meta()` переживает конверсию.** `z.string().meta({ 'x-visibility': 'public' })` даёт
   в JSON Schema свойство с `x-visibility: "public"`; неразмеченное свойство не получает
   аннотации вообще. Модель ADR-008 ложится нативно.

**Следствие из 1–3:** конверсия fail-open ровно там, где приложение уверено, что ядро принуждает
его правило. Это тот же класс дефекта, против которого написан ADR-008, только про ограничения
payload, а не про видимость. Отсюда страж §6.

## 4. Решения

### 4.1 Владение типом события — структурное

Тип события несёт пространство имён владельца: `core.*` (например `core.room.activated`) —
владеет ядро, валидирует zod-схемой SDK; `<appId>.*` (например `quiz.answer.submitted`) —
владеет приложение, валидирует снапшот из реестра. Владелец резолвится разбором имени,
без таблицы соответствий, которую можно рассинхронизировать.

В реестре событие объявляется **коротким** именем, полный тип ядро собирает как
`<appId>.<имя>`. Приложение структурно не может объявить тип в чужом пространстве — нечем
выразить.

### 4.2 Три оси версий

| Ось | Что версионирует | Источник |
|---|---|---|
| Версия контракта (semver SDK) | контракт ядро↔модуль | REQ-CTR-004; манифест объявляет `contractRange`, ядро проверяет при регистрации |
| `manifestVersion` | манифест приложения целиком | приложение; пинится при ACTIVE (REQ-RT-004) |
| `schemaVersion` в событии | схему, провалидировавшую этот payload | ядро проставляет при фиксации |

`schemaVersion` значит одно и то же для обоих владельцев — «версия схемы, провалидировавшей
payload», — но берётся из разных мест: для `core.*` это объявленная версия схемы события ядра,
для `<appId>.*` — запиненный `manifestVersion`.

**Типы событий ядра объявляются в SDK** (`events/core-events.ts`) реестром той же формы, что
и app-реестр: короткое имя → `{ schema (zod), visibility (потолок), version }`. Так конвейер
фиксации (§7, шаги 5–7) работает единообразно для обоих владельцев — меняется только источник
реестра, не логика. Реестр ядра — статический zod, без конверсии и снапшота: ядро версионируется
контрактом, а не манифестом, и его схемы не пересекают границу. Lifecycle-события REQ-RT-010
живут здесь.

**Диапазон `contractRange`** — строка semver-диапазона (например `^1.2.0`), сверяемая с
`contract-version.ts` при регистрации.

**Отдельной оси версий на тип события не вводится.** REQ-RT-004 пинит комнату на манифест
целиком, второй оси MVP не требует — это был бы забег вперёд (CLAUDE.md §2.3). Лог при этом
остаётся самоописывающимся: по событию видно, чем оно провалидировано, без join'а к комнате
(важно для архивации по REQ-RT-008).

### 4.3 Два конверта

- **`logEventSchema`** — внутренний конверт `(roomId, seq, type, payload, actorId, visibility,
  schemaVersion)` по REQ-RT-001. Живёт в ядре и в контракте ядро↔модуль: модуль — наш код
  в том же деплойменте, RT-011 защищает от участника, не от модуля.
- **`projectedEventSchema`** — то, что уходит клиенту: `(type, payload, actorId)`. Без `seq`,
  без `visibility`, без курсора.

Существующая с фазы 0 схема несёт `seq` и потому наружу непригодна — отсюда разделение.

### 4.4 Курсора в MVP нет; replay отдаёт полную видимую проекцию

Курсор, закодированный из глобального `seq` в base64, **не годится**: это косметическая
непрозрачность, участник его декодирует и увидит дыры — RT-011(a) нарушен. Настоящая
непрозрачность требует шифрования курсора серверным ключом, а сплошная per-level нумерация —
это часть (b), отложенная амендментом в ф.4.

**Решение:** в MVP курсора нет, replay всегда отдаёт полную видимую проекцию с начала.
REQ-RT-003 это прямо разрешает («допустима схема снапшот + хвост» — допустима, не обязательна).
RT-011(a) тогда выполняется структурно: наружу не уходит ни `seq`, ни курсор, потому что их
нет. Ноль криптографии, ноль per-level счётчиков.

**Цена:** каждый reconnect — полный replay, что удорожает reconnect-шторм. Это ровно риск,
ради которого амендмент вернул потолок RT-015 в ф.1.

**Почему цена приемлема — и на чём именно это держится.** Не на малости лога: при профиле
§6.2 (100 участников) 20 раундов дают ~2000 событий ответов, и проекция, включающая их все,
измерялась бы сотнями килобайт, а не десятками. Держится на **разметке видимости**: ответы
квиза `module-private`, поэтому проекция участника — это открытия раундов, раскрытия и таблица,
десятки событий; полный лог видит только сам модуль, а он не переподключается по wifi.
Второй слой — потолок RT-015: даже 100 идентичностей по 10 реконнектов в минуту дают ~17
replay/сек, что для Postgres пустяк.

Оба числа — оценки, не замеры, и профиль нагрузки §6.2 помечен владельцем как невалидированный
(«цифра из головы или замер?»). Первое живое событие их и проверит.

**Условие пересмотра (важнее самих чисел):** решение опирается на то, что **проекция участника
мала**, а не лог. Механика с крупной публичной проекцией (много `public`-событий на участника)
обрушит это основание, не меняя ни одной нормы. Появится такая — пересматривать §4.4, а не
считать вопрос закрытым.

**Почему downside ограничен:** симптом ошибки — медленные переподключения, то есть
производительность, а не корректность: ни потери данных, ни утечки, ни расхождения состояния.

**Почему это проходит фильтр задела:** добавить курсор потом аддитивно — опциональное поле
в проекции плюс опциональный параметр `since`; старый клиент игнорирует и продолжает получать
полный replay. Обратный порядок (отдать `seq` сейчас, убрать потом) был бы и ломающим, и
утечкой всё время до починки.

### 4.5 Видимость — упорядоченная решётка

По экспозиции: `public` > `organizer` > `module-private`. Порядок записывается в SDK явно —
без него REQ-CTR-009 нечем принудить.

Задекларированный в реестре уровень — **потолок экспозиции**. Событие отклоняется, если его
фактическая видимость экспонированнее потолка. Тип с потолком `organizer`: пришло `public` —
отказ; пришло `module-private` — прошло (защищённее потолка всегда допустимо).

### 4.6 Пин схем — снапшот JSON Schema при регистрации

Приложение **пишет** схемы на zod (типы, DX); при регистрации SDK-хелпер конвертирует их
в JSON Schema и реестр хранит сериализованный снапшот под ключом `(appId, manifestVersion)`.
При переходе в ACTIVE комната пинится на этот ключ и валидируется сохранённым снапшотом.

**Главное следствие:** REQ-RT-004 становится инвариантом ядра, обеспеченным **данными**.
Снапшот лежит в БД — модуль не может его сломать, удалив старый код.

**Разделение, которое это наводит:** ядро валидирует **форму**, приложение — **семантику**.
Потеря `.refine()` на стороне ядра не дыра, а нужный шов: почти все осмысленные refine в
событиях требуют состояния комнаты («индекс ответа меньше числа вариантов раунда») и статической
схемой невыразимы. REQ-RT-013 уже так устроен — субчеловеческий темп отклоняется на
app-валидации.

**Отклонённые альтернативы:**

- *Живые zod-объекты в процессе + все исторические версии в коде модуля.* Полная выразительность
  zod, но REQ-RT-004 держался бы на дисциплине: модуль обязан вечно хранить каждую историческую
  версию. Ничто не мешает автору удалить v1 — активная комната, запиненная на v1, либо падает,
  либо (хуже) начинает валидироваться v2. Это «граница по соглашению», отвергаемая ADR-002 и
  CLAUDE.md §2.2. Плюс живой объект через границу — против буквы REQ-CTR-002 и против опциона
  сетевой формы (ADR-002).
- *Гибрид: zod для валидации, снапшот для пина.* DRAFT-комната валидировалась бы zod (строго),
  ACTIVE — снапшотом (слабее): одно событие получает разный вердикт в зависимости от статуса
  комнаты.

**Прочтение ADR-006, которое это предполагает:** ADR-006 говорит «app-модуль экспортирует
zod-схемы своих типов событий в App-registry». Здесь это читается как «zod — поверхность
авторства, JSON Schema — регистрируемый артефакт». Букве не противоречит, намерению
соответствует («истина для контракта приложения — его манифест и зарегистрированные схемы»).
Нового ADR не требует; прочтение зафиксировано явно, чтобы не быть тихим допущением.

## 5. Манифест

```
appId           — slug, он же пространство имён событий
manifestVersion — int, пинится при ACTIVE (REQ-RT-004)
contractRange   — совместимый диапазон версий контракта (REQ-CTR-004)
appSettings     — JSON Schema с per-property x-visibility (REQ-CORE-008)
events          — { "<короткое имя>": { schema: JSONSchema, visibility: <потолок> } }
```

Сам манифест валидируется zod (ADR-006), включая вложенные JSON Schema и аннотации.

**Разметка видимости `appSettings`** пишется в zod через `.meta({ 'x-visibility': ... })` и
переживает конверсию (§3.4). Отсутствие аннотации ядро трактует как `module-private` — fail-safe
ADR-008 получается сам собой: чтобы данные утекли, автор должен явно написать `public`;
забывчивость закрывает, а не открывает.

**Поля `capabilities` нет.** ADR-003 подключает rewards через capability манифеста, но rewards —
фаза 3; по CLAUDE.md §2.3 точка расширения фиксируется словами в ADR, не пустым полем. В фазе 3
добавляется аддитивно.

## 6. Страж конверсии

При регистрации манифеста SDK **отклоняет манифест типизированной ошибкой**
(`SCHEMA_NOT_REPRESENTABLE`), если схема несёт конструкцию, которая не доедет до JSON Schema:
custom `.refine()`, `.transform()`, `date`, `bigint`. Обычные проверки (`.min(1)` → `minLength`)
доезжают штатно и не трогаются — страж бьёт только по тому, что теряется молча.

Признак custom-проверки — `check === 'custom'`, не сам факт наличия в `_zod.def.checks` (§3.3):
штатные проверки лежат там же, и страж по факту наличия закрыл бы ворота перед легальными схемами.

**Хрупкость и её лечение:** страж опирается на `_zod.def.checks` — внутреннее API zod.
Лечится принципом самого проекта: **страж проверяется фикстурой** — схема с `.refine()` обязана
быть отклонена. Обновление zod, сломавшее детекцию, уронит CI громко, вместо того чтобы тихо
открыть ворота. Гейт проверяет гейт, как в фазе 0.

## 7. Точки принуждения (ограничения для последующих планов)

**Регистрация приложения:** манифест валидируется zod → проверка совместимости `contractRange`
(REQ-CTR-004) → конверсия zod→JSON Schema со стражем (§6) → снапшот под ключом
`(appId, manifestVersion)`.

**Запись `appSettings`:** валидация JSON Schema из манифеста; скомпилированный валидатор
кэшируется по `(appId, manifestVersion)` (REQ-CORE-007). Повторно при `DRAFT → ACTIVE`.

**`DRAFT → ACTIVE`:** перевалидация настроек → пин `(appId, manifestVersion)` и заморозка
`appSettings` (REQ-RT-004) → lifecycle-событие уровня `public` (REQ-RT-010).

**Фиксация события — порядок шагов обязателен:**

1. комната не терминальна, иначе отказ (REQ-RT-016 — инвариант ядра, не обязанность приложения);
2. размер payload в пределах `max_event_payload` (REQ-RT-012);
3. per-actor rate-limit эмиссии (REQ-RT-014);
4. `actorId` — из аутентифицированного контекста соединения, не из payload (REQ-RT-009);
5. владелец типа резолвится из пространства имён → zod ядра либо снапшот реестра **на
   запиненной версии**;
6. payload валидируется схемой владельца (REQ-CTR-008);
7. видимость не экспонированнее потолка типа (REQ-CTR-009);
8. **и только теперь** — вход в критическую секцию (advisory lock на `roomId`), присвоение
   `seq`, штамп `schemaVersion`, append.

Шаги 1–7 обязаны стоять **до** входа в секцию: это делает payload-нейтральность (REQ-RT-007)
структурной, а не статистической. Вся приёмка и валидация завершены до захвата лока, поэтому
исход гонки определяется порядком входа в секцию, а размер payload на него не влияет; тест
проверяет детерминированное свойство, а не отсутствие статистического смещения. Решение
зафиксировано дизайн-доком фазы 0 §1.5; здесь оно становится порядком шагов.

**Чтение проекции:** строит ядро по уровню запрашивающего (REQ-CORE-005/008), включая
per-property проекцию `appSettings`. Наружу уходит `projectedEventSchema` без `seq` (§4.3).
Ручная фильтрация в обработчиках запрещена нормой — значит у обработчика не должно быть доступа
к непроецированному виду, иначе запрет держится на дисциплине.

## 8. Типизированные ошибки

Коды экспортирует SDK — модуль обязан уметь их разбирать. Наружу без стектрейсов (REQ-SEC-006).

`MANIFEST_INVALID`, `CONTRACT_VERSION_INCOMPATIBLE`, `SCHEMA_NOT_REPRESENTABLE`,
`EVENT_UNKNOWN_TYPE`, `EVENT_PAYLOAD_INVALID`, `EVENT_VISIBILITY_WEAKER_THAN_DECLARED`,
`EVENT_PAYLOAD_TOO_LARGE`, `EVENT_RATE_LIMITED`, `ROOM_LOG_SEALED`, `ROOM_SETTINGS_FROZEN`.

## 9. Фикстуры (REQ-CTR-005)

Пары валид/невалид у каждой поверхности. Ключевые невалидные бьют в критерии выхода фазы 1:

- событие с видимостью экспонированнее потолка → отказ (REQ-CTR-009);
- манифест со схемой, несущей `.refine()` → отказ (тест стража, §6);
- манифест с непредставимым типом (`date` / `bigint` / `transform`) → отказ;
- `appSettings` с неразмеченным свойством → **отсутствует** в проекции участнику (fail-safe
  ADR-008);
- несовместимый `contractRange` → отказ при регистрации;
- проекция события наружу не несёт `seq` (RT-011a).

## 10. Состав пакета

```
packages/sdk/src/
  contract-version.ts              — версия контракта (semver)
  visibility/visibility.ts         — уровни + порядок экспозиции + сравнение
  events/log-event.schema.ts       — внутренний конверт (есть с фазы 0)
  events/projected-event.schema.ts — проекция наружу (новое)
  events/core-events.ts            — реестр типов событий ядра, включая lifecycle (REQ-RT-010)
  manifest/manifest.schema.ts      — zod-схема манифеста
  manifest/define-app.ts           — хелпер авторства + страж конверсии
  errors/error-codes.ts            — коды типизированных ошибок
```

Фикстуры — рядом с каждой поверхностью, по образцу `log-event.fixtures.ts` фазы 0.

## 11. Заметки

- До фазы 2 реального приложения нет: реестр в фазе 1 тестируется **фикстурным** манифестом.
- Prisma-схема ядра (§6.2 задания) — вне этой спеки; снапшот реестра и пин комнаты дадут ей
  требования к таблицам App-registry и Room.
