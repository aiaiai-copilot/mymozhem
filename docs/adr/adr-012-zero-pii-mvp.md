# ADR-012 — MVP без ПДн и без материальных призов по умолчанию (юридическая минимизация)

**Статус:** принят (владельцем 2026-10-12)
**Дата:** 2026-10-12
**Пересматривает:** ADR-004 в части способа появления REGISTERED-identity (не модель identity);
приостанавливает REQ-ID-004, REQ-ID-009, REQ-ID-015, REQ-ID-017, verified-ветку REQ-RWD-014.
**Не затрагивает:** ADR-001, 002, 003, 005, 005a, 006, 007, 008, 009, 010, 011; тексты прочих REQ.

---

## Контекст

Гейт «юрист» (roadmap §4.1, HANDOFF «Два гейта над фазами») — потенциально терминальный класс риска: вопросы `docs/legal/questions-for-lawyer.md` (152-ФЗ против неудаляемого лога, согласие гостя, стимулирующие лотереи, налог с выигрыша, локализация хостинга, закрытый тест) решаются живым юристом, а заключение может вернуть требования, меняющие спецификацию задним числом.

Разбор показал: весь юридический риск стоит на четырёх носителях, и каждый убирается упрощением, а не усложнением продукта:

1. **Аккаунты с email и OAuth-провайдером** (актив A2 модели угроз). Реализованный OAuth-контур (~580 строк ядра `packages/core/src/oauth` + транспорт, cookie `mm_oauth_*`, allowlist редиректов, rate-limit'ы, web-флоу лендинга) обслуживает сценарий, которого в продуктовой ставке MVP нет: по ADR-004 доминирующий кейс — доверенное очное событие, а единственный REGISTERED на практике — сам организатор. Контур не тянет свою цену: он одновременно главный источник ПДн и заметная доля поверхности безопасности (REQ-ID-009, REQ-SEC-007).
2. **Реальные имена участников.** Система требует имя при входе (REQ-ID-003), но механикам нужен любой устойчивый идентификатор для отображения — не обязательно настоящее имя.
3. **IP-адреса** (`joinIp` в Membership и Exclusion) — нужны анти-накрутке и блоку rejoin только на жизни события, а хранятся дольше.
4. **Материальные призы** — весь блок «лотерея + налог» возникает только из них; механикам (честный CSPRNG-розыгрыш, баллы квиза) материальность приза не нужна.

Что изменилось относительно момента принятия ADR-004/REQ-ID-015 (основание для пересмотра по REQ-DEV-004): при проектировании пакета юридическая ось была известным, но неоценённым риском; теперь она измерена списком вопросов и оценена как потенциально терминальная (roadmap §4 ставит её контролем №1). Цена OAuth-контура стала сравнимой с ценой всего гейта — а его полезная нагрузка на MVP (multi-organizer, привязка аккаунтов гостей, verified-розыгрыши) относится к сценариям следующих этапов.

## Решение

Четыре части, принимаемые как один пакет.

### 1. Self-hosted — норма позиционирования MVP

Продукт распространяется как софт (единый Docker-артефакт), который организатор запускает сам — на своём ноутбуке на площадке или своём VPS. Владелец платформы не обрабатывает чужие ПДн; каждый организатор — сам себе оператор своего события. Вопрос локализации хостинга (152-ФЗ) становится делом организатора, а не платформы. Код не меняется (архитектура уже такая: REQ-OPS-005); меняются документация деплоя, дефолты compose (локальный origin, без публичных предположений) и позиционирование.

### 2. REGISTERED без OAuth: локальный bootstrap организатора

Модель identity **не меняется**: `kind ∈ {REGISTERED, GUEST}` (REQ-ID-001), организатор — только REGISTERED (REQ-ID-005), единый токен-механизм (REQ-ID-016) — всё сохраняется. Меняется способ появления REGISTERED:

- Вместо OAuth Google — **bootstrap по setup-токену**: параметр конфигурации `organizer_setup_token` (проверка минимальной длины при старте, по образцу REQ-SEC-002). `POST /auth/organizer` с этим токеном создаёт (первый вызов) или находит единственную REGISTERED-identity инстанса с `email = NULL` и выдаёт токен-пару по правилам REGISTERED.
- Один инстанс = один организатор (self-hosted норма, ч.1). Multi-organizer и приглашения организаторов — отложены вместе с аккаунтами.
- **OAuth-контур удаляется из кода физически** (модуль `oauth`, контроллеры/транспорт, cookie `mm_oauth_*`, параметры `OAUTH_*`/allowlist редиректов, web-флоу лендинга «войти через Google») — git-история сохраняет его для возврата; мёртвого кода под отложенное в дереве не держим (правило «не забегать вперёд» распространяется и на «отставать сзади»: недействующий контур в prod-артефакте — та же пустая схема). Таблица identity-provider удаляется новой миграцией.
- Web: вместо OAuth-лендинга — ввод setup-токена организатором; гостевой вход (`/play`, `/screen`) не меняется вообще.

### 3. Псевдонимы участников и сокращение жизни IP

- `displayName` при гостевом входе становится **необязательным**: не задан — сервер назначает псевдоним («Лиса-42», генерация из словаря + discriminator). Свободный ввод имени остаётся (выбор организатора/участника), но система не требует реального имени ни в одном сценарии.
- TTL-свип гостей (REQ-ID-014) расширяется: вместе с анонимизацией identity обнуляется `joinIp` членств и удаляются записи `Exclusion`, привязанные к свипнутым identity. Инвариант «IP живёт не дольше события + guest_ttl» фиксируется тестом. В живом контуре события `joinIp` сохраняется — анти-накрутка и блок rejoin (REQ-ID-006) не ослабляются.
- REQ-SEC-009 (ПДн вне payload'ов лога) сохраняется как сторожевой инвариант; при псевдонимах и отсутствии аккаунтов он становится тривиально выполнимым.

### 4. Призовой режим — явная опция, по умолчанию выключена

- Новый параметр конфигурации `prize_mode: off | on`, дефолт `off`. При `off`: `POST /rooms/:id/prizes` отклоняется типизированной ошибкой `PRIZES_DISABLED`; сущность приза с фондом/quantity недоступна.
- **Лотерея остаётся**: `prizeId` в `draw.run` становится необязательным (аддитивная эволюция контракта, REQ-DEV-007; прямо разрешено REQ-RWD-002b — контракт не требует сущности приза для фиксации победителя). Розыгрыш без приза — «выбор победителя» (честный CSPRNG-пик участника): механика, UX проектора и консоли сохраняются, юридический факт выигрыша — нет.
- Баллы (`award.points`) разрешены в обоих режимах — нематериальны.
- При `prize_mode: on` UI явно предупреждает: призовой режим — юридическая ответственность организатора (лотереи, налоги). Включение = осознанный выбор, при котором консультация юриста возвращается на стол.

## Мотивация

- **Асимметрия цены.** Юрист нужен для оценки носителей риска; убрать носители дешевле, чем легализовать их. Каждая из четырёх частей — удаление или сужение, а не добавление: совокупный diff продукта отрицательный (OAuth-контур и web-флоу уходят; добавляются setup-token endpoint, генератор псевдонимов, флаг-гейт и расширение свипа).
- **Соответствие ставке MVP.** ADR-004 (фрикция пропорциональна ставке) уже нацелен на доверенное очное событие; аккаунты и призы — фрикция и риск ради сценариев, которые на этом этапе отсутствуют. Первое живое событие по смыслу и так «закрытый тест среди знакомых» (вопрос 6 юристу) — пакет делает это конфигурацией по умолчанию, не требующей разрешения.
- **Сохранение инвестиции.** Возврат аккаунтов — восстановление OAuth-контура из git + новая миграция; модель identity, токены, индексы, роли не ломаются пакетом, поэтому путь обратно не является переписыванием (критерий задела из roadmap §2 выдержан в обе стороны).

## Следствия

### Требования

| Норма | Эффект |
|---|---|
| REQ-ID-001, REQ-ID-005, REQ-ID-016 | **Сохраняются без изменений** (модель, организатор=REGISTERED, единые токены) |
| REQ-ID-003 | Уточняется: имя гостя необязательно; псевдоним назначает сервер (оформить амендментом текста при принятии) |
| REQ-ID-004, REQ-ID-017 (привязка аккаунта гостём, переиздание токенов) | **Приостановлены** — нет аккаунтов, к которым привязывать; активируются возвратом аккаунтов |
| REQ-ID-009 (OAuth state/allowlist), REQ-ID-015 (регистрация через Google OAuth) | **Приостановлены** вместе с контуром; OAuth-часть REQ-SEC-007 — с ними |
| REQ-ID-014 | Реализация свипа расширяется (joinIp, Exclusion); текст нормы не меняется |
| REQ-RWD-014, verified-ветка (`draw_eligibility: verified` = REGISTERED) | **Приостановлена**: REGISTERED — только организатор, verified-розыгрыш вырождается в пустой пул; `guests_allowed` остаётся единственным действующим значением |
| REQ-SEC-004 | Остаётся в силе; объект (PII) сокращается до временного `joinIp` — норма становится поглощающей |
| REQ-ID-012 (админ-контур, уже в ф.4 по амендменту v1.4) | Переформулируется при ф.4: allowlist identity-id уступает место self-hosted норме (админ = владелец инстанса); точную форму — фазовое проектирование |
| REQ-ID-006, REQ-ID-013, REQ-ID-019, SEC/RT/CORE/CTR/DEV/OPS группы | Не затрагиваются |

### Код

- **Удаляется:** `packages/core/src/oauth/**`, OAuth-эндпоинты и rate-limit'ы транспорта, `mm_oauth_*` куки, `OAUTH_*`/allowlist параметры конфига и compose (вопрос «dummy Google-тройка» из follow-up снимается), Google-флоу лендинга web, provider-схема и int-спеки провижининга; таблица identity-provider (новая миграция). Заодно снимается открытый «шов registered-join» (D-12.1) — JoinController-всегда-GUEST становится единственной нормой.
- **Добавляется (малое):** `POST /auth/organizer` + `organizer_setup_token` в конфиг-схему; генератор псевдонимов в membership-join; `prize_mode` + гейт в rewards-контроллере; необязательный `prizeId` в `draw.run` (SDK-манифест lottery, аддитивно); расширение guest-sweep на joinIp/Exclusion; страница ввода setup-токена в web.
- **Не меняется:** токен-сервис, комнатный lifecycle, realtime, app-runtime, quiz, sweep-автоматика в остальной части, метрики/логи, boundary-правила.

### Процесс и документы

- При принятии — амендмент v1.5 к нормативному пакету: пометки «приостановлено (ADR-012)» в REQ-ID-004/009/015/017 и REQ-RWD-014, уточнение REQ-ID-003, новый параметр `prize_mode` и `organizer_setup_token` в §4, маркер у REQ-ID-012.
- Список вопросов юристу **сохраняется**: при активации `prize_mode: on`, возврате аккаунтов или сборе реальных имён как обязательных пакет перестаёт покрывать вопросы 1–4 — юрист возвращается до включения, не после.
- Гейт 1 в формулировке «до первого события с посторонними или призами» фактически снимается для событий в дефолтной конфигурации (самохост, псевдонимы, без призов): посторонние на таком событии не создают регулируемой поверхности.

## Отклонено

- **«Пойти к юристу как планировалось»** — цена и сроки консультации оплачивают легализацию носителей, которых продуктовая ставка MVP не требует; вопрос возвращается при активации призового режима, когда есть что легализовывать.
- **Сохранить OAuth-контур выключенным за флагом** — мёртвый код в prod-артефакте: поверхность безопасности (state/PKCE/allowlist/куки) без пользователей, плюс нарушение правила «нет пустых каркасов». Git — достаточное хранилище спящего кода.
- **Организатор как гость с секретом (без REGISTERED)** — ломает REQ-ID-005, room-scoped гостевые токены умирают с комнатой (консоль организатора живёт дольше), гостевой свип анонимизировал бы организатора; bootstrap-REGISTERED сохраняет все нормы ценой одного endpoint'а.
- **Локальные аккаунты логин/пароль вместо OAuth** — сохраняет ПДн-риск минимальным, но добавляет контур хэширования/сброса пароля ради одного пользователя инстанса; setup-токен из конфигурации дешевле и соответствует self-hosted норме.
- **Запрет свободного ввода имени** — избыточное сужение: организатору закрытого события удобны реальные имена; норма — «система не требует», не «система запрещает».
- **Отключать лотерею при `prize_mode: off`** — сужает продукт сильнее необходимого: REQ-RWD-002b уже разрешает победителя без сущности приза; честный рандом-пик участника полезен и без призов («кто отвечает», «кому приз от организатора лично»).

## Триггеры пересмотра (возврат вопроса)

- Включение `prize_mode: on` на любом событии с посторонними → юрист до включения.
- Потребность в multi-organizer / привязке аккаунтов гостей / verified-розыгрышах → возврат аккаунтного контура (восстановление OAuth или новый ADR о локальных аккаунтах) + юрист.
- Выход из self-hosted нормы (hosted-сервис для чужих организаторов) → весь пакет пересматривается: оператором ПДн становится владелец платформы.
