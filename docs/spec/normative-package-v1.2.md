# MyMozhem v2 — нормативный пакет перепроектирования

**Версия:** v1.2
**Статус:** проект, направлен на проверку
**Дата:** 2026-07-11
**Авторы:** Александр Лапыгин, Claude

Ключевые слова MUST / MUST NOT / SHOULD / MAY трактуются по RFC 2119. Документ самодостаточен: контекст, необходимый для оценки решений, приведён в самих ADR.

---

## 0. Резюме и терминология

Проектируется платформа для приложений-конкурсов (лотереи, квизы, дегустации и подобные механики живых и асинхронных событий). Платформа предоставляет приложениям общие примитивы — идентичность участников, комнаты-события, членство, realtime-взаимодействие, реестр приложений — и поставляется как единый развёртываемый артефакт. Пакет фиксирует архитектурные решения (ADR-001…011, включая ADR-005a), реестр требований, модель угроз, фазовый план и задание для проектной сессии.

**Терминология.**
- **Ядро** — платформенная часть системы.
- **App-модуль (приложение)** — реализация конкретной конкурсной механики.
- **Комната** — экземпляр события с участниками, имеющий жизненный цикл (§ ADR-005, REQ-RT-005).
- **Членство (membership)** — связь identity с комнатой, несущая роль.
- **Роль** — значение из ролевой модели: `ORGANIZER | MODERATOR | PARTICIPANT | SPECTATOR` (REQ-ID-011).
- **Организатор** — членство с ролью ORGANIZER; создатель и владелец комнаты.
- **Участник** — обобщённо любое членство; в узком смысле — роль PARTICIPANT, соревнующаяся сторона.
- **Зритель** — членство с ролью SPECTATOR: вошёл в комнату, но не соревнуется.
- **Админ-контур** — платформенный администратор; не роль членства и не значение `kind`, а отдельный механизм авторизации (REQ-ID-012).
- **Манифест** — декларация приложения: метаданные, capabilities, схема настроек, схемы типов событий (с уровнями видимости, REQ-CTR-009).
- **SDK** — пакет, содержащий контракт ядро↔модуль (схемы, версия, фикстуры).
- **Проекция** — воссоздаваемое из лога текущее состояние комнаты (ADR-005); не является источником истины.
- **Уровень видимости** — атрибут состояния, события и свойств `appSettings`: `public | organizer | module-private` (REQ-CORE-005, REQ-CORE-008).
- **Eligibility розыгрыша** — атрибут `draw_eligibility` (`guests_allowed | verified`), определяющий, чья identity имеет вес в `winnerSelection` (REQ-RWD-014).
- **Claim** — заочное востребование награды победителем; в MVP отсутствует (ADR-007), термин сохранён для отложенной фазы.
- **Событие лога** — запись append-only лога комнаты `(roomId, seq, type, payload, actorId, visibility, schemaVersion)` (REQ-RT-001).

## 1. Архитектурные решения

### ADR-001 — Продуктовая рамка
**Статус:** принят.
**Решение:** первичный продукт — платформа для собственных приложений-конкурсов, поставляемая единым Docker-артефактом. PostgreSQL — внешняя относительно артефакта управляемая зависимость (REQ-CORE-001). Мультитенантный BaaS — не цель MVP; перспектива сохраняется как опцион через требования групп CTR и CORE, не как функциональность.
**Следствия:** тенантность не проектируется. Путь к BaaS при необходимости — control plane, разворачивающий managed-инстансы того же артефакта по одному на клиента, без переписывания ядра.
**Отклонено:** BaaS как первичный продукт — нет спроса, подтверждённого выручкой; издержки мультитенантности легли бы на продукт до появления её потребителя.

### ADR-002 — Модель исполнения: модульный монолит
**Статус:** принят.
**Решение:** ядро и app-модули — один деплоймент, ровно одна реплика процесса (REQ-OPS-005). App-модуль взаимодействует с ядром исключительно через SDK-контракт; граница охраняется автоматическими проверками в CI.
**Опционные требования (сохраняют путь к распределённой топологии):** контракт сетевой формы (request/response + события, сериализуемые payload'ы); запрет доступа модуля к данным ядра в обход контракта; версионирование контракта с первого дня; запрет глобального синглтон-состояния процесса.
**О стоимости версионирования с первого дня:** semver контракта и контрактные фикстуры вводятся уже в фазе 0 не как подготовка к будущему сетевому потребителю, а как сам механизм CI-принуждения границы (REQ-CTR-005, REQ-DEV-001) и как колея для AI-агентов. Их отсрочка «до второго потребителя» устранила бы забор, ради которого выбран монолит. Стоимость принята осознанно.
**Отклонено:**
- *Приложения с собственными бэкендами с первого дня* — сетевая топология умножает деплойменты, межсервисную аутентификацию и версионирование до появления платящего потребителя. Протокол валидируется формой контракта, а не физической сетью; граница, охраняемая только соглашением, эрозирует под давлением сроков при любой топологии.
- *Монолит с CI-границами, но без полного SDK-церемониала до второго потребителя* — рассмотрен и отклонён: фикстуры и semver суть механизм принуждения, а не издержка ожидания (см. выше).
- *Sandboxed-плагины в рантайме ядра* — объём R&D не соответствует бюджету MVP.

### ADR-003 — Домен ядра и модуль rewards
**Статус:** принят.
**Решение:** ядро = Identity, Room, Membership, Realtime, App-registry. Награды (призы, победители, начисления) выносятся в опциональный модуль `rewards`, подключаемый через capability манифеста. Делегирование функций `prizeFund` / `winnerSelection` приложению адресуется модулю rewards. В фазе 1 модуль логический: свой каталог, свой контракт, CI-граница — без отдельной инфраструктуры.
**Сопутствующий примитив ядра:** состояние, события комнаты и свойства `appSettings` имеют уровни видимости `public` / `organizer` / `module-private`; проекции наружу строит ядро по уровню запрашивающего (REQ-CORE-005, REQ-CORE-008). Уровень типа события декларируется и принуждается ядром при фиксации (REQ-CTR-009). Совокупно эти нормы закрывают отдачу скрытых данных механики по всем каналам (состояние, события, конфигурация), не полагаясь на разметку эмитента.
**Отклонено:**
- *Призы и победители в ядре* — механики без материальных призов (квиз на скорость, дегустация с рейтингами) не ложатся на модель «приз достался участнику» без фиктивных сущностей; ядро навсегда несло бы домен одной механики.
- *Полностью generic-ядро без наград* — теряется единый пользовательский опыт «призовой фонд события / мои выигрыши», отличающий платформу от голого pub/sub.

### ADR-004 — Гостевой доступ и модель identity
**Статус:** принят.
**Решение:** политика входа — атрибут комнаты: `guests | registered | invite_only`, значение по умолчанию `guests` (вход по коду комнаты + имя, без регистрации). Единая таблица identity с `kind: REGISTERED | GUEST`; привязка аккаунта гостём — смена kind без миграции внешних ключей.
**Мотивация:** основной сценарий — живое событие в кругу знакомых (компания за столом, корпоратив): десятки участников со смартфонами и десятки секунд на подключение; обязательная OAuth-регистрация каждого участника — прямой удар по конверсии входа. «Кто может войти» — по природе настройка комнаты, покрывающая и открытые праздники, и корпоративные события с поимённым доступом.
**Принцип продуктовой рамки (фрикция пропорциональна ставке):** дефолты фрикции и верификации настроены под доминирующий сценарий — доверенное очное событие с низкими состязательными ставками, — где технические барьеры избыточны, а физическое присутствие и социальный контроль уже ограничивают злоупотребление. Усиление против недоверенного/удалённого/денежного сценария доступно как явный выбор организатора (`registered` / `invite_only`, `draw_eligibility: verified`), а не как дефолтный налог на доминирующий кейс. Остаточные риски дефолта фиксируются в соответствующих требованиях явно, а не замалчиваются.
**Следствия:** анти-накрутка (REQ-ID-006) — обязательное требование; правила вручения наград гостям регулируются ADR-007; вес гостя в розыгрыше — ADR-011/REQ-RWD-014. Код комнаты становится барьером доступа и требует стойкости к перебору (REQ-ID-013, REQ-ID-019).
**Отклонено:**
- *Регистрация для всех* — потеря конверсии в ядре ценности продукта.
- *Отдельная таблица гостей / полиморфные связи Participant → (User | Guest)* — усложнение каждого join и миграция всей истории при привязке аккаунта; единая таблица с partial unique index даёт то же поведение без этих издержек.

### ADR-005 — Состояние игры: event log комнаты
**Статус:** принят.
**Решение:** append-only лог событий комнаты `(roomId, seq, type, payload, actorId, visibility)`; `seq` назначается сервером при фиксации, `unique(roomId, seq)`. Runtime-состояние — воссоздаваемая из лога проекция с областью «комната». `appSettings` — только конфигурация, замораживается при активации комнаты. Порядок конкурирующих действий («кто первый») определяется порядком фиксации в логе; клиентские timestamp — телеметрия. Late-join и reconnect — replay проекции соответствующего уровня видимости. Переходы жизненного цикла комнаты эмитируются в лог как события уровня `public` (REQ-RT-010) — один канал синхронизации для состояния и статуса.
**Мотивация:** один примитив закрывает арбитраж конкурирующих действий (порядок назначает БД, а не клиентские часы), восстановление после рестарта, синхронизацию опоздавших, разбор спорных результатов по логу и естественно ложится в событийную поверхность контракта ядро↔модуль.
**Отклонено:**
- *Мутабельное состояние в БД как единственная модель* — конкурентные обновления требуют внешнего арбитража, история отсутствует, споры о результате неразрешимы.
- *Полный event sourcing всех сущностей* — избыточен для CRUD-доменов (комнаты, членство, реестр приложений).

### ADR-005a — Транспорт realtime
**Статус:** принят (выделен из ADR-005 для независимого пересмотра).
**Решение:** транспорт — Socket.io, скрытый за Realtime-контрактом ядра (`publish / subscribe / projection`). Смена транспорта — деталь реализации, не затрагивающая event log (ADR-005) и контракт.
**Следствие:** при переходе к нескольким репликам (снят REQ-OPS-005) потребуется внешний адаптер Socket.io и sticky-маршрутизация по roomId — предмет будущего ADR, не MVP.

### ADR-006 — Стек и механизм контракта
**Статус:** принят.
**Решение:** NestJS (Fastify-адаптер) + Prisma (PostgreSQL, `multiSchema`: схема на модуль). Контракт описывается zod-схемами в SDK-пакете — единственный источник истины для TS-типов (inference), runtime-валидации на границах и трёх поверхностей контракта: REST DTO, payload'ы событий лога, манифест. OpenAPI генерируется из zod как артефакт. Версия SDK = версия контракта; манифест приложения объявляет совместимый диапазон.
**Оговорка о схемах appSettings и app-событий:** схемы настроек и типов событий конкретного приложения по природе динамичны и не выразимы статическими zod-схемами ядра. Они переносятся как сериализуемая JSON Schema внутри манифеста; сам манифест (включая эти вложенные схемы и аннотации видимости REQ-CORE-008/REQ-CTR-009) валидируется zod. App-модуль дополнительно экспортирует zod-схемы своих типов событий в App-registry; ядро валидирует payload события схемой владельца типа до фиксации в лог (REQ-CTR-008, REQ-RT-009). Это не нарушает «единственный источник истины»: истина для контракта ядра — zod; истина для контракта приложения — его манифест и зарегистрированные схемы.
**Оговорка о границе:** Nest-модули не охраняют границу на уровне компилятора — dependency-cruiser / eslint-boundaries в CI обязательны (REQ-DEV-001).
**Мотивация:** Nest-модули — воплощение ADR-002 на языке фреймворка: границы выражены конструкциями imports/exports, DI делает контракт инъектируемым интерфейсом (in-process транспорт заменяем сетевым без изменения потребителей). Разработка ведётся в AIDD-режиме: сильные конвенции сужают пространство решений агента — штатные места для валидации, авторизации и границ делают отклонение видимым на ревью немедленно. Стек соответствует профильной экспертизе владельца, ускоряя ревью — узкое место AIDD.
**Отклонено:**
- *Fastify без каркаса* — не сопротивляется эрозии структурных границ.
- *OpenAPI-first + кодогенерация* — покрывает одну поверхность из трёх; событийная требует отдельного стандарта со слабым тулингом; кодоген — трение в цикле агента.
- *tRPC* — замыкает контракт на TypeScript-клиентов, противореча опциону открытия.
- *ts-rest* — лишний слой поверх тех же zod-схем; событийную поверхность не покрывает.

### ADR-007 — Вручение наград: только очное в MVP
**Статус:** принят.
**Решение:** MVP поддерживает только очное вручение: организатор явным действием переводит награду `AWARDED → FULFILLED` (вручена) либо `AWARDED → REVOKED` (отзыв с транзакционным возвратом quantity в фонд). Сценарий «победитель получает материальный приз, не присутствуя на событии» — вне MVP: заочный claim (сбор контакта победителя, окно востребования, автоматический claim при привязке аккаунта, возврат невостребованного) отложен в опциональную фазу, активируемую подтверждённым спросом.
**Мотивация:** узел «материальный приз × победитель-гость × заочность» — самое концентрированное место сложности пакета: наиболее острые риски корректности концентрируются именно здесь. При этом ядро ценности продукта — живое событие, где награда вручается в зале; заочная доставка не входит в ставку первых продаж. Очное присутствие также ограничивает выигрыш накрутки: собрать физический приз способен один присутствующий человек.
**Следствия:** из MVP исключаются: состояние CLAIMED и claim-автомат, контакт победителя как категория PII, параметр `claim_window`, инвариант `guest_ttl ≥ claim_window`, приостановка TTL гостя под claim, автоматический возврат невостребованного. Нормы REQ-RWD-006/008 помечены отложенными, не удалены. Контракт и схема rewards проектируются расширяемыми: добавление состояния CLAIMED и claim-полей при активации отложенной фазы — аддитивная эволюция контракта (REQ-DEV-007, REQ-CTR-004), не перепроектирование.
**Отклонено:** заочное вручение в составе MVP — оплата существенной сложности за сценарий вне продуктовой ставки.

### ADR-008 — Видимость данных, определяющих исход механики
**Статус:** принят.
**Контекст:** уровни видимости (ADR-003) охраняют состояние и события лога, проецируя их ядром по уровню запрашивающего. Два канала отдачи данных остаются вне этого механизма, если его не расширить: (1) `appSettings` — категория конфигурации, отдельная от состояния и событий; (2) уровень `visibility` конкретного события проставляется эмитентом-приложением, а ядро без дополнительной нормы валидирует лишь форму payload, не соответствие типа события допустимому уровню. Оба канала способны вынести наружу данные, определяющие исход механики (правильные ответы, скрытые веса, пороги).
**Решение:**
1. `appSettings` получают **поле-уровневую** видимость: JSON Schema настроек в манифесте несёт для каждого свойства уровень (`public | organizer | module-private`); отсутствие аннотации трактуется как `module-private` (fail-safe). Ядро проецирует `appSettings` по уровню запрашивающего тем же механизмом, что состояние и события. Данные, определяющие исход, MUST быть `module-private` и MUST NOT проецироваться участнику.
2. Реестр схем событий приложения несёт для каждого типа события обязательный (максимально допустимый) уровень видимости. Ядро при фиксации отклоняет событие типизированной ошибкой, если фактический `visibility` слабее задекларированного для его типа.
**Мотивация:** переносит инвариант «скрытое не утекает» с доверия к разметке приложения на структурную проверку ядра по всем каналам отдачи — конфигурация, состояние, события. Мислейбл уровня ловится на фиксации, а не на проекции.
**Следствия:** схема манифеста расширяется per-property visibility и per-type visibility реестра событий; чит-тест первого приложения проверяет недоступность `module-private` `appSettings` и отказ фиксации при заниженном уровне.
**Отклонено:**
- *Норма-запрет «не класть исход в appSettings» без структурной проекции* — неверифицируема: тест не отличит корректную конфигурацию от той, что содержит исход.
- *Полный запрет механической конфигурации в appSettings* — ломает легитимные публичные настройки (тайминги, тексты), плодит фиктивные сущности.

### ADR-009 — Семантика «первого» и стойкость арбитража к автоматизации
**Статус:** принят.
**Контекст:** порядок конкурирующих действий определяется порядком фиксации в логе. Механизм корректен для восстановления и разбора споров, но как арбитр награды имеет два зазора: (1) присуждение по «первому закоммитившему» вознаграждает субчеловеческую скорость автоматизированного клиента, а не знание; (2) под контентией при стратегии retry латентность транзакции — а с нею и исход гонки за `seq` — зависит от размера payload, что даёт упреждающему клиенту с минимальным payload преимущество над более ранним человеком.
**Решение:**
1. Ядро предоставляет примитив **окна приёма**: приложение MAY объявить приём ответов раунда в дискретном окне с фиксированной или рандомизированной задержкой открытия; внутри окна порядок клика не даёт преимущества упреждающему скрипту.
2. Механика, присуждающая награду по признаку «первый», MUST задать анти-упреждающий контроль: минимальный интервал «открытие раунда → приём ответа», ниже которого ответ отклоняется, либо дискретное окно приёма (REQ-RT-013).
3. Стратегия разрешения конкуренции за `seq` обеспечивает payload-нейтральность: исход присвоения определяется порядком поступления, не размером payload (REQ-RT-007).
**Мотивация:** приводит защищаемое свойство «честность арбитража» в соответствие с механизмом; «порядок по логу» остаётся арбитром факта и восстановления, но перестаёт быть эксплуатируемым арбитром награды.
**Отклонено:**
- *«Первый по логу» как единственный арбитр награды* — вознаграждает автоматизацию, не знание.
- *Proof-of-humanity (CAPTCHA) на каждый ответ* — непропорциональный удар по конверсии живого события (ADR-004); окно приёма закрывает вектор без фрикции для человека.

### ADR-010 — Стойкость и верифицируемость розыгрыша
**Статус:** принят.
**Контекст:** `winnerSelection` делегируется приложению (REQ-RWD-005). Без нормы на источник случайности предсказуемый ГПСЧ (сид от времени/`seq`/счётчика) или клиентское влияние на сид позволяют предсказать или сместить победителя; для конкурса с материальным призом это подмена результата. «Честность арбитража» как актив (A3) требует, чтобы источник случайности розыгрыша был отдельно защищён (A7).
**Решение:**
1. `winnerSelection` MUST использовать серверный CSPRNG; сид не выводится из наблюдаемых или контролируемых участником величин (время, `seq`, клиентский ввод). Исход не предсказуем из состояния, доступного участнику (REQ-RWD-011).
2. Публично-верифицируемый розыгрыш (commit-reveal / VRF), позволяющий участнику проверить честность исхода постфактум, — вне MVP (REQ-RWD-012, отложено); вводится аддитивной эволюцией контракта rewards при подтверждённом спросе на удалённые розыгрыши между взаимно-недоверяющими сторонами.
**Мотивация:** непредсказуемость — необходимый минимум для любого розыгрыша. Публичная верифицируемость отвечает на недоверие между чужими сторонами, что не входит в продуктовую ставку MVP (живое событие в кругу знакомых); спекулятивная реализация оплачивала бы сложность за сценарий вне ставки (ср. ADR-007).
**Следствия:** приёмочный тест лотереи проверяет непредсказуемость исхода из наблюдаемого состояния. Остаточно: без верифицируемости инсайдер, контролирующий `winnerSelection`, технически способен сместить исход незаметно — принимается для доверенного очного контекста, закрывается вместе с активацией верифицируемой фазы.
**Отклонено:** *доверять источнику случайности приложения без нормы* — розыгрыш на деньги без гарантии непредсказуемости неоспорим только до первого спора.

### ADR-011 — Привилегированный инсайдер в модели угроз
**Статус:** принят.
**Контекст:** роль MODERATOR наделена правом исключения участника (REQ-ID-006, REQ-ID-011) с немедленным разрывом его подписок (REQ-SEC-003). Модель угроз, ограниченная внешними и рядовыми акторами, считала носителя делегированной власти благонамеренным. Скомпрометированный или сговорный модератор может устранить конкурентов перед развязкой «первый побеждает» либо сорвать событие изнутри — концентрируя влияние на честность (A3), доступность (A5) и членство (A6) в руках не-владельца.
**Решение:** вводится актор T5 (§ 2); против него — контроли REQ-ID-018: аудит действий модератора, rate-limit исключений, запрет/задержка исключения в критическом окне арбитража, право организатора откатить исключение.
**Мотивация:** делегированная роль ниже доверия владельца комнаты; система защищает организатора и участников от привилегированного инсайдера, не только от рядового участника.
**Отклонено:** *считать модератора доверенным* — концентрация трёх активов у не-владельца без контроля и аудита.

## 2. Модель угроз

Раздел фиксирует активы, акторов и каналы, к которым трассируются требования групп SEC и ID. Не является исчерпывающим анализом безопасности; служит основанием для проверяемости защитных норм.

**Защищаемые активы:**
- A1 — скрытые данные механики (правильные ответы квиза, невыявленные оценки, скрытые веса и пороги — в состоянии, событиях **и конфигурации** `appSettings`): утечка обесценивает конкурс.
- A2 — персональные данные (email, provider-данные; контакт победителя добавится при активации отложенной фазы claim, ADR-007).
- A3 — честность арбитража (кто первый, кто победитель): подмена искажает результат конкурса с призами.
- A4 — призовой фонд (quantity призов, факт и единичность выдачи): двойная выдача, перевыпуск сверх фонда и потеря наград — прямой материальный ущерб.
- A5 — доступность живого события: отказ во время мероприятия необратим во времени.
- A6 — целостность членства (кто в комнате, с какой ролью): обход даёт доступ и подсаживает накрутку.
- A7 — источник случайности розыгрыша: предсказуемость или смещаемость исхода обесценивает конкурс с призом наравне с утечкой данных механики.

**Акторы угроз:**
- T1 — злонамеренный участник/гость (в комнате по праву, стремится к нечестному преимуществу, накрутке, чтению скрытого).
- T2 — посторонний (не в комнате, перебирает коды, ищет незащищённые ресурсы).
- T3 — исключённый участник (был в комнате, членство отозвано).
- T4 — компрометированный клиент (украден токен, XSS).
- T5 — привилегированный инсайдер (член с делегированной властью — MODERATOR; скомпрометированный или сговорный: устранение конкурентов, срыв события, злоупотребление правами роли).
- T6 — враждебное или дефектное приложение и его supply-chain (app-модуль сам или через скомпрометированную зависимость мислейблит `visibility`, помещает исход в проецируемую конфигурацию, использует слабый розыгрыш — актор внутри доверенной границы приложения).
- T7 — автоматизированный клиент (скриптовый участник в субчеловеческом темпе, упреждающий открытие раунда, размножающий гостевые identity).

**Каналы:** REST, realtime-соединение, replay при late-join, OAuth-редирект, форма входа гостя.

**Трассировка (актив × актор → требование):**
- A1 × T1/T6 через любой канал (состояние, событие, конфигурация) → REQ-CORE-005, REQ-CORE-008, REQ-CTR-009, REQ-RT-003, REQ-RT-011 (метаданные seq).
- A2 × T1/T4 → REQ-SEC-004, REQ-SEC-008, REQ-SEC-009 (PII не в логе).
- A3 × T1/T7 через realtime payload и тайминг → REQ-RT-002, REQ-RT-007, REQ-RT-009, REQ-RT-013; × T5 инсайдер → REQ-ID-018; × T6 розыгрыш → REQ-RWD-011.
- A4 × T1 через гонку → REQ-RWD-003, REQ-RWD-007 (идемпотентность), REQ-RWD-010 (бюджет фонда); × T7 накрутка розыгрыша → REQ-RWD-014.
- A5 × T1 через объём → REQ-RT-012, REQ-RT-014, REQ-RT-015 (эмиссия и reconnect), REQ-SEC-007; × T5 → REQ-ID-018.
- A6 × T2 перебор кода → REQ-ID-013, REQ-ID-019; × T3 возврат → REQ-ID-006; × T3 живое соединение → REQ-SEC-003; × T5 инсайдер → REQ-ID-018.
- A7 × T6/T1 → REQ-RWD-011 (CSPRNG); публичная верифицируемость — REQ-RWD-012 (отложено).

## 3. Реестр требований

Параметры конфигурации, на которые ссылаются требования, сведены в §4 (таблицу параметров) с дефолтами и диапазонами; их согласованность валидируется единой конфиг-схемой (REQ-OPS-003, уровень MUST).

### CTR — контракт и границы

- **REQ-CTR-001 (MUST)** Взаимодействие app-модуля с ядром — только через интерфейсы SDK. Импорт кода или типов ядра в обход SDK запрещён и обнаруживается CI (boundary-check).
- **REQ-CTR-002 (MUST)** Контракт имеет сетевую форму: request/response DTO и события; payload'ы сериализуемы в JSON. Передача через границу живых объектов, функций, ORM-моделей запрещена.
- **REQ-CTR-003 (MUST)** Схемы контракта ядра описываются zod в пакете SDK. TS-типы выводятся из схем; runtime-валидация на границах использует те же схемы.
- **REQ-CTR-004 (MUST)** Версия SDK = версия контракта (semver). Манифест приложения объявляет совместимый диапазон версий контракта; ядро проверяет совместимость при регистрации приложения.
- **REQ-CTR-005 (MUST)** SDK содержит контрактные тесты (фикстуры валидных и невалидных payload'ов), обязательные к прохождению ядром и каждым модулем в CI.
- **REQ-CTR-006 (SHOULD)** OpenAPI-спецификация генерируется из zod-схем как артефакт сборки; ручное редактирование сгенерированного артефакта запрещено.
- **REQ-CTR-007 (MAY)** Событийная поверхность может дополнительно публиковаться AsyncAPI-артефактом, генерируемым из тех же схем.
- **REQ-CTR-008 (MUST)** App-модуль экспортирует zod-схемы своих типов событий; схемы регистрируются в App-registry вместе с манифестом. Ядро валидирует payload события схемой владельца его типа до фиксации в лог; несоответствие — отказ фиксации типизированной ошибкой.
- **REQ-CTR-009 (MUST)** Реестр схем событий приложения (REQ-CTR-008) несёт для каждого типа события обязательный (максимально допустимый) уровень видимости. Ядро при фиксации отклоняет событие типизированной ошибкой, если фактический `visibility` слабее задекларированного для его типа. *Мислейбл уровня приложением или его зависимостью не проходит в лог.*

### CORE — ядро

- **REQ-CORE-001 (MUST)** Система собирается в единый Docker-артефакт. PostgreSQL — внешняя относительно артефакта зависимость. Состав включённых app-модулей определяется конфигурацией запуска, не пересборкой.
- **REQ-CORE-002 (MUST)** Домены ядра: Identity, Room, Membership, Realtime, App-registry. Добавление домена в ядро — только через новый ADR.
- **REQ-CORE-003 (MUST)** Каждый модуль владеет своими таблицами в отдельной PostgreSQL-схеме (Prisma `multiSchema`). Выполнение DML над таблицами чужого модуля запрещено. Декларативный внешний ключ (DDL) из таблицы модуля на таблицу ядра (`identity`, `room`) допускается без каскадов; на таблицы других app-модулей — запрещён. Компенсация целостности при отсутствии FK — проверки в сервисах.
- **REQ-CORE-004 (MUST)** Глобальное мутабельное состояние процесса запрещено. Допустимо воссоздаваемое из персистентного первоисточника состояние с областью «комната» (проекции по ADR-005). Проверка: eslint-правило против мутабельных module-level значений в составе REQ-DEV-001 плюс пункт чек-листа ревью; остаточная непроверяемость признаётся явно.
- **REQ-CORE-005 (MUST)** Состояние и события комнаты имеют уровень видимости `public | organizer | module-private`. Проекции наружу строит ядро по уровню запрашивающего. Область видимости распространяется на `appSettings` (REQ-CORE-008): конфигурация проецируется по уровню запрашивающего наравне с состоянием и событиями. Ручная фильтрация чувствительных полей в обработчиках как механизм сокрытия запрещена.
- **REQ-CORE-006 (MUST)** Бизнес-логика размещается в сервисах модулей. Контроллеры и гейтвеи содержат только транспортную обвязку: валидацию DTO, маппинг, коды ответов.
- **REQ-CORE-007 (SHOULD)** `appSettings` валидируются по JSON Schema из манифеста при каждой записи и повторно при переходе `DRAFT → ACTIVE`; скомпилированные валидаторы кэшируются по ключу `(appId, manifestVersion)`.
- **REQ-CORE-008 (MUST)** `appSettings` имеют поле-уровневую видимость (`public | organizer | module-private`), декларируемую в JSON Schema настроек манифеста; отсутствие аннотации трактуется как `module-private` (fail-safe). Ядро проецирует `appSettings` по уровню запрашивающего (REQ-CORE-005). Данные, определяющие исход механики (правильные ответы, скрытые веса, пороги), MUST быть `module-private` и MUST NOT проецироваться участнику ни по одному каналу.

### ID — identity, доступ, роли

- **REQ-ID-001 (MUST)** Единая таблица identity с `kind ∈ {REGISTERED, GUEST}`; `email` nullable; уникальность email — частичный уникальный индекс по условию `kind = REGISTERED AND deletedAt IS NULL`. Реализация индекса — см. REQ-DEV-006.
- **REQ-ID-002 (MUST)** Политика входа — атрибут комнаты: `guests | registered | invite_only`; значение по умолчанию — `guests`.
- **REQ-ID-003 (MUST)** Гость создаётся по коду комнаты и имени; идентичность гостя имеет TTL (параметр `guest_ttl`, §4); истечение реализуется анонимизацией (REQ-ID-014).
- **REQ-ID-004 (MUST)** Привязка аккаунта гостём изменяет `kind` и добавляет provider-данные; внешние ключи (участия, события, награды) не мигрируют. Токен-сессия переиздаётся (REQ-ID-017).
- **REQ-ID-005 (MUST)** Организатором комнаты может быть только REGISTERED-identity.
- **REQ-ID-006 (MUST)** Анти-накрутка, минимум: лимит участников комнаты (`room_participant_limit`, §4); rate-limit на вход в комнату по IP (§4); исключение участника организатором или модератором. Исключение блокирует повторный вход по признакам device-cookie + IP; ограничение обходимо сменой устройства/сети — для комнат, где это критично, штатный ответ — политика `registered` или `invite_only` (см. модель угроз, A6 × T3). Вес размноженных гостевых identity в розыгрыше ограничивается отдельно (REQ-RWD-014).
- **REQ-ID-007 (MUST)** Refresh-токены хранятся только хэшированными и ротируются при каждом refresh. Повторное предъявление уже ротированного токена инвалидирует всё семейство сессий (детекция кражи).
- **REQ-ID-008 (MUST)** Для браузерных клиентов refresh-токен передаётся только в httpOnly cookie. Передача любых токенов в URL (query или fragment) запрещена.
- **REQ-ID-009 (MUST)** OAuth-флоу использует `state` с одноразовым nonce, проверяемым на сервере (double-submit httpOnly cookie или серверное хранилище). Цель redirect после входа валидируется по allowlist.
- **REQ-ID-010 (SHOULD)** Очистка просроченных сессий и записей отзыва — регламентный job (интервал — параметр `cleanup_interval`, §4). Сроки жизни access-токена, записей отзыва и значения `expiresIn` в ответах вычисляются из одной точки конфигурации.
- **REQ-ID-011 (MUST)** Ролевая модель членства: `role ∈ {ORGANIZER, MODERATOR, PARTICIPANT, SPECTATOR}`. Права каждой роли фиксируются матрицей доступа; MODERATOR наделяется правом исключения участника (REQ-ID-006) под контролями REQ-ID-018, SPECTATOR — правом чтения публичной проекции без участия в соревновании.
- **REQ-ID-012 (MUST)** Платформенный админ-контур — отдельный механизм авторизации (allowlist identity-id в конфигурации), не значение `kind` и не роль членства. Доступ админ-контура к PII (REQ-SEC-004) предоставляется этим механизмом.
- **REQ-ID-013 (MUST)** Код комнаты — криптослучайный, длиной не менее `room_code_min_len` символов безопасного алфавита (§4). Ответ на попытку входа единообразен и не раскрывает существование комнаты **до установления членства**, независимо от политики входа: ветки «неверный код» и «верный код + закрытая политика (`registered` / `invite_only`)» отдают неотличимый результат. Различие политики сообщается только уже аутентифицированному приглашённому/зарегистрированному участнику. Перебор ограничивается rate-limit входа (REQ-ID-006) и глобальным backoff (REQ-ID-019).
- **REQ-ID-014 (MUST)** Истечение TTL гостя реализуется как анонимизация строки identity (обнуление PII, сохранение id), а не физическое удаление — внешние ключи и actorId в логе остаются валидными. Приостановка при открытой награде — REQ-RWD-013.
- **REQ-ID-015 (MUST)** Регистрация REGISTERED-identity поддерживается через внешнего OAuth-провайдера; первый и единственный в MVP провайдер — Google. Provider-данные хранятся в отдельной таблице/полях identity и подпадают под PII (REQ-SEC-004).
- **REQ-ID-016 (MUST)** Гость и REGISTERED используют единый токен-механизм (access JWT + httpOnly refresh, REQ-ID-007/008). Гостевой refresh живёт не дольше `guest_ttl`; в JWT-claims гостя фиксируется scope конкретной комнаты (roomId). Завершение комнаты или истечение TTL инвалидирует гостевые сессии этой комнаты.
- **REQ-ID-017 (MUST)** Привязка аккаунта гостём (смена `kind` GUEST → REGISTERED, REQ-ID-004) переиздаёт токен-пару: room-scoped гостевой access/refresh инвалидируется, выдаётся токен по правилам REGISTERED (scope и TTL). После переиздания завершение комнаты более не инвалидирует сессию бывшего гостя как гостевую. *Устраняет неопределённость жизненного цикла токена на стыке kind-флипа.*
- **REQ-ID-018 (MUST)** Действия MODERATOR над членством (исключение, мягкое удаление участия) записываются в аудит с `actorId` и основанием; частота исключений одним модератором ограничена rate-limit (`moderator_action_rate_limit`, §4); исключение в критическом окне арбитража раунда запрещено либо отложено до закрытия окна; организатор вправе откатить исключение, выполненное модератором.
- **REQ-ID-019 (MUST)** Перебор кода комнаты ограничивается глобальным (per-room и платформенным) счётчиком неудачных попыток входа с экспоненциальным замедлением, независимым от IP; per-IP лимит (REQ-ID-006) сохраняется как дополнительный слой. Замедление применяется к неудачным попыткам и **не препятствует входу по верному коду**: предъявление корректного кода не подпадает под backoff, вызванный чужими неудачными попытками (исключает превращение backoff в вектор отказа в обслуживании).

### RT — realtime и состояние

- **REQ-RT-001 (MUST)** События комнаты пишутся в append-only лог `(roomId, seq, type, payload, actorId, visibility, schemaVersion)`; `seq` назначается сервером при фиксации; `unique(roomId, seq)`.
- **REQ-RT-002 (MUST)** Порядок конкурирующих действий определяется порядком фиксации в логе. Клиентские timestamp принимаются только как телеметрия и не участвуют в арбитраже.
- **REQ-RT-003 (MUST)** Подключившийся или переподключившийся клиент восстанавливает состояние replay'ем проекции своего уровня видимости; допустима схема «снапшот + хвост лога».
- **REQ-RT-004 (MUST)** При переводе комнаты в ACTIVE замораживаются `appSettings` **и** пара `(appId, manifestVersion)`. Валидация app-событий активной комнаты ведётся версией схем, зафиксированной на момент ACTIVE; последующая перерегистрация манифеста не изменяет семантику валидации активной комнаты. Изменение конфигурации активной комнаты запрещено.
- **REQ-RT-005 (MUST)** Переходы статуса комнаты ограничены явной машиной состояний: `DRAFT → ACTIVE → COMPLETED`, `DRAFT → CANCELLED`, `ACTIVE → CANCELLED`; иные переходы запрещены. Мягкое удаление — ортогональный атрибут `deletedAt`, допустимый в статусах `DRAFT`, `COMPLETED`, `CANCELLED` (не в `ACTIVE`); удаление не является статусом.
- **REQ-RT-006 (MUST)** Транспорт realtime скрыт за контрактом ядра (`publish / subscribe / projection`). Прямое использование Socket.io вне Realtime-модуля запрещено.
- **REQ-RT-007 (MUST)** Стратегия разрешения конкуренции при вставке `seq` (retry по конфликту либо advisory lock на комнату) фиксируется в реализации и обеспечивает **payload-нейтральность**: исход присвоения `seq` определяется порядком поступления, не размером payload. Покрывается конкурентным тестом и тестом отсутствия payload-смещения.
- **REQ-RT-008 (SHOULD)** Логи завершённых комнат архивируются по регламенту (интервал/условие — параметр `log_archive_policy`, §4; проектируется в фазе 4; схема лога не должна этому препятствовать).
- **REQ-RT-009 (MUST)** Входящие realtime-сообщения валидируются zod-схемами наравне с REST DTO: сообщения ядра — схемами SDK, app-события — зарегистрированными схемами владельца типа (REQ-CTR-008). Идентификатор актора берётся только из аутентифицированного контекста соединения, не из payload.
- **REQ-RT-010 (MUST)** Переходы жизненного цикла комнаты эмитируются в лог как события уровня `public`. Клиенты узнают смену статуса через тот же канал (realtime + replay), что и прочие события; отдельный канал синхронизации статуса не вводится.
- **REQ-RT-011 (MUST)** Проекция уровня видимости не раскрывает метаданные скрытых событий (наличие, количество, моменты) через дыры в нумерации seq: наружу отдаётся сплошная нумерация видимой проекции (per-level cursor), глобальный seq не экспонируется участнику.
- **REQ-RT-012 (MUST)** Размер входящего realtime-сообщения и payload события ограничен сверху (`max_event_payload`, §4); превышение — отказ типизированной ошибкой.
- **REQ-RT-013 (MUST)** Механика, присуждающая награду по признаку «первый», задаёт анти-упреждающий контроль: минимальный интервал «событие открытия раунда → приём ответа», ниже которого ответ отклоняется (`arbitration_min_answer_interval`, §4), либо дискретное окно приёма (примитив окна предоставляется ядром, ADR-009). Ответы в субчеловеческом темпе отклоняются на app-валидации.
- **REQ-RT-014 (MUST)** Эмиссия событий в комнату ограничена per-actor хард rate-limit (`event_emit_rate_limit`, §4); превышение — отказ типизированной ошибкой, не алерт. Мягкий предел числа событий на комнату (`soft_room_event_cap`, §4) сопровождается алертом (SHOULD) и переводится в жёсткий режим отказа для чувствительных комнат (`room_event_cap_mode`, §4).
- **REQ-RT-015 (MUST)** Переподключение и форсированный replay одной identity ограничены rate-limit с бэкоффом (`reconnect_rate_limit`, §4); reconnect-шторм одной identity не удорожает восстановление для остальных участников.
- **REQ-RT-016 (MUST)** После перехода комнаты в терминальный статус (`COMPLETED` / `CANCELLED`) ядро отклоняет фиксацию любых не-lifecycle доменных событий комнаты. Запечатывание лога — инвариант ядра, не обязанность приложения.

### RWD — модуль rewards

- **REQ-RWD-001 (MUST)** Rewards — опциональный модуль, подключаемый через capability манифеста. Ядро не зависит от rewards.
- **REQ-RWD-002a (MUST)** Модуль поддерживает два типа наград: призы (единицы с quantity) и начисления (баллы/очки) без сущности приза.
- **REQ-RWD-002b (MUST NOT)** Контракт rewards не требует создания сущности приза для фиксации победителя или начисления.
- **REQ-RWD-003 (MUST)** Награждение атомарно: списание quantity и фиксация победителя — одна транзакция. **Единичность победителя** (один участник не получает один приз дважды) обеспечивается частичным уникальным индексом по активным записям `(roomId, prizeId, winnerId)` (REQ-DEV-006); индекс обеспечивает и идемпотентность повтора (сетевой повтор той же награды конфликтует по индексу — типизированный no-op). **Ограниченность фонда** — отдельный инвариант (REQ-RWD-010), не следствие уникальности.
- **REQ-RWD-004 (MUST)** Вручение награды — очное: организатор или модератор переводит награду в FULFILLED явным действием. Заочное востребование (claim) в MVP отсутствует (ADR-007).
- **REQ-RWD-005 (SHOULD)** Делегирование `prizeFund` / `winnerSelection` приложению оформляется как capability и проходит через контракт rewards.
- **REQ-RWD-006 — ОТЛОЖЕНО (ADR-007).** Норма о claim-контакте как PII активируется вместе с отложенной фазой заочных наград; до этого контакт победителя системой не собирается.
- **REQ-RWD-007 (MUST)** Награда — конечный автомат `AWARDED → FULFILLED | REVOKED` с уникальным ограничением на переход в БД; переходы идемпотентны: повторное вручение — типизированный no-op, повторный отзыв не возвращает quantity дважды. Отзыв (`REVOKED`) транзакционно возвращает quantity в фонд. Расширение автомата состоянием CLAIMED — аддитивная эволюция контракта (ADR-007). Покрывается конкурентными тестами фазы 3.
- **REQ-RWD-008 — ОТЛОЖЕНО (ADR-007).** Норма об исходе невостребованного (возврат в фонд по истечении `claim_window`) активируется вместе с отложенной фазой.
- **REQ-RWD-009 (SHOULD)** При переводе комнаты в COMPLETED организатору видны награды, оставшиеся в состоянии AWARDED (не вручённые), с возможностью вручить или отозвать каждую.
- **REQ-RWD-010 (MUST)** Ограниченность призового фонда — DB-инвариант: выдача выполняется атомарным ограниченным декрементом (`UPDATE ... SET quantity = quantity - n WHERE ... AND quantity >= n`; ноль затронутых строк → отказ) под ограничением `CHECK (quantity >= 0)`, в одной транзакции с фиксацией победителя. Конкурентная выдача N > `quantity` наград **разным** identity не создаёт перевыпуска и не уводит `quantity` в минус. Допустимая альтернативная реализация — моделирование фонда как `quantity` строк-единиц, каждая уникально-востребуема.
- **REQ-RWD-011 (MUST)** `winnerSelection` использует серверный CSPRNG; сид не выводится из наблюдаемых или контролируемых участником величин (время, `seq`, клиентский ввод). Исход розыгрыша не предсказуем из состояния, доступного участнику.
- **REQ-RWD-012 — ОТЛОЖЕНО (ADR-010).** Публично-верифицируемый розыгрыш (commit-reveal / VRF), позволяющий участнику проверить честность исхода постфактум, активируется при подтверждённом спросе на удалённые розыгрыши между взаимно-недоверяющими сторонами; вводится аддитивной эволюцией контракта rewards (REQ-DEV-007).
- **REQ-RWD-013 (MUST)** При наличии у гостя нерешённой награды в состоянии `AWARDED` (не `FULFILLED` / `REVOKED`) истечение `guest_ttl` не анонимизирует identity: TTL приостанавливается до разрешения награды. *Предотвращает осиротение приза из-за обнуления имени победителя до вручения.*
- **REQ-RWD-014 (MUST)** Вес identity в `winnerSelection` определяется атрибутом розыгрыша `draw_eligibility ∈ {guests_allowed, verified}`; значение по умолчанию — `guests_allowed`. При `verified` вес имеют только REGISTERED-identity; гости входят, играют и наблюдают, но в розыгрыше не участвуют. Изменение — явным действием организатора. `verified` в текущем контракте = REGISTERED (REQ-ID-015); привязка веса к дефицитному внешнему ресурсу (напр. телефон) — точка расширения, вне текущего контракта. *При дефолте `guests_allowed` риск Sybil-накрутки гостевого розыгрыша (A6 × T7) принимается осознанно; штатное усиление для розыгрышей с материальным призом в открытом доступе — организатор устанавливает `verified`.*

### SEC — безопасность

- **REQ-SEC-001 (MUST)** Демонстрационные и тестовые пути аутентификации отсутствуют в production-артефакте: включаются только тестовой сборкой или флагом тестовой среды и исключаются из production-образа статически.
- **REQ-SEC-002 (MUST)** Секреты не хранятся в коде и репозитории. `JWT_SECRET` проверяется на минимальную длину (≥ 32 байта) при старте; старт с пустым или дефолтным секретом невозможен.
- **REQ-SEC-003 (MUST)** Чтение любых подресурсов комнаты (состояние, участники, события, награды) — только членам комнаты, без исключений; политика входа определяет, кто может стать членом, но не ослабляет проверку членства при чтении. Проверка обязательна и на REST, и на realtime, с учётом мягкого удаления участия и комнаты. Отзыв членства (исключение, мягкое удаление) немедленно завершает активные подписки этой identity в комнате — проверка непрерывна, не единовременна в момент подписки.
- **REQ-SEC-004 (MUST)** PII (email, provider-данные) отдаётся только самой identity и админ-контуру. Публичная проекция identity: id, name, avatar.
- **REQ-SEC-005 (MUST)** Пагинация ограничена сверху (limit ≤ 100); параметры пагинации валидируются схемой.
- **REQ-SEC-006 (MUST)** Ошибки наружу — типизированные коды без внутренних сообщений и стектрейсов; проброс сырого `error.message` клиенту запрещён.
- **REQ-SEC-007 (MUST)** Чувствительные эндпоинты (login, вход в комнату, refresh, OAuth callback) имеют собственные rate-limits, более строгие, чем глобальный (значения — §4).
- **REQ-SEC-008 (MUST)** Security-заголовки включены (helmet-эквивалент); CORS — allowlist из конфигурации, без wildcard в production.
- **REQ-SEC-009 (MUST NOT)** PII не попадает в payload'ы событий лога. Субъект события представляется только `actorId`; контакты, имена в открытом виде и provider-данные в лог не пишутся. (Инвариант делает лог совместимым с обязательством удаления PII через анонимизацию identity, REQ-ID-014.)

### OPS — эксплуатация

- **REQ-OPS-001 (MUST)** `/health` проверяет фактическую доступность БД; liveness и readiness разделены.
- **REQ-OPS-002 (MUST)** Миграции применяются детерминированно при деплое (`migrate deploy`); сид-данные не попадают в production.
- **REQ-OPS-003 (MUST)** Конфигурация валидируется при старте единой zod-схемой, включая согласованность производных значений: сроки жизни токенов, разрешённые origin, и взаимные инварианты параметров §4 (в частности гостевой `refresh_token_ttl` ≤ `guest_ttl`, REQ-ID-016).
- **REQ-OPS-004 (SHOULD)** Наблюдаемость: структурированные логи с корреляцией requestId / roomId / actorId; метрики латентности `publish → deliver`, длительности replay, ошибок фиксации событий, числа активных соединений по комнатам.
- **REQ-OPS-005 (MUST)** Поддерживается ровно одна реплика приложения; запуск нескольких экземпляров не поддерживается (in-memory проекции и Socket.io без внешнего адаптера). Ограничение зафиксировано в документации деплоя; снятие — через ADR (см. ADR-005a).
- **REQ-OPS-006 (MUST)** Резервное копирование БД выполняется по регламенту с проверяемой процедурой восстановления (лог — единственный источник истины по играм и призовым обязательствам; потеря без восстановимости недопустима). Периодичность — параметр `backup_policy` (§4).

### DEV — процесс разработки

- **REQ-DEV-001 (MUST)** CI на каждый PR: lint (включая boundary-check через dependency-cruiser или eslint-boundaries и правило против мутабельного module-level состояния), type-check, unit-тесты, контрактные тесты SDK, сборка артефакта.
- **REQ-DEV-002 (MUST)** Один lockfile на монорепозиторий.
- **REQ-DEV-003 (MUST)** Сессионные артефакты AIDD (handoff-файлы, промпты) не размещаются в корне репозитория; место — `docs/sessions/` либо вне репозитория.
- **REQ-DEV-004 (MUST)** Отклонение от принятого ADR оформляется новым ADR до слияния кода.
- **REQ-DEV-005 (SHOULD)** E2e-сценарии прототипа v1 (Playwright) переиспользуются как приёмочные спецификации соответствующих фаз.
- **REQ-DEV-006 (MUST)** Частичные уникальные индексы (REQ-ID-001, REQ-RWD-003) реализуются SQL-миграцией с автотестом наличия индекса в БД, без preview-функции Prisma `partialIndexes`.
- **REQ-DEV-007 (MUST)** Эволюция схем событий лога: конверт события несёт `schemaVersion` (REQ-RT-001). Изменения схем событий — только аддитивные необязательные поля; breaking-изменение вводится как новый тип события, старый сохраняется для replay. Исторические версии схем и их фикстуры хранятся в SDK бессрочно.
- **REQ-DEV-008 (MUST)** При недоступности БД действие, не зафиксированное в логе, отклоняется типизированной ошибкой (fail-closed); подтверждение клиенту выдаётся только после успешной фиксации. Поведение при повреждении лога — отказ построения проекции с алертом, а не «лучшее из возможного» (SHOULD).

## 4. Параметры конфигурации

Все параметры валидируются единой конфиг-схемой при старте (REQ-OPS-003). Дефолты — ориентиры для v1.x, уточняются в реализации; диапазоны — жёсткие границы.

| Параметр | Дефолт | Диапазон | Инвариант |
|---|---|---|---|
| `guest_ttl` | 24 ч | 1 ч … 30 сут | гостевой `refresh_token_ttl` ≤ `guest_ttl` (REQ-ID-016) |
| `room_participant_limit` | 500 | 1 … 100 000 | — |
| `room_code_min_len` | 8 | ≥ 6 | безопасный алфавит (без смешиваемых символов) |
| `join_rate_limit_ip` | 20/мин | ≥ 1/мин | — |
| `access_token_ttl` | 15 мин | 1 мин … 1 ч | единая точка для `expiresIn` и blacklist (REQ-ID-010) |
| `refresh_token_ttl` | 30 сут | 1 сут … 90 сут | см. `guest_ttl` |
| `cleanup_interval` | 1 ч | 5 мин … 24 ч | — |
| `max_event_payload` | 16 КБ | 1 КБ … 256 КБ | REQ-RT-012 |
| `soft_room_event_cap` | 100 000 | ≥ 1 000 | алерт; жёсткий режим — `room_event_cap_mode` |
| `room_event_cap_mode` | soft | soft \| hard | REQ-RT-014; hard → отказ вместо алерта |
| `event_emit_rate_limit` | 30/мин на actor | ≥ 1/мин | REQ-RT-014, отказ при превышении |
| `reconnect_rate_limit` | 10/мин на identity | ≥ 1/мин | REQ-RT-015, бэкофф |
| `arbitration_min_answer_interval` | app-задаётся | ≥ 0 | REQ-RT-013; 0 = окно приёма вместо интервала |
| `moderator_action_rate_limit` | 10/мин на модератора | ≥ 1/мин | REQ-ID-018 |
| `code_bruteforce_backoff` | вкл, экспоненциальный | — | REQ-ID-019, per-room + платформенный |
| `log_archive_policy` | по завершении + 30 сут | — | REQ-RT-008, фаза 4 |
| `backup_policy` | ежесуточно, retention 30 сут | — | проверяемый restore (REQ-OPS-006) |
| `login_rate_limit` | 10/мин на IP | ≥ 1/мин | REQ-SEC-007 |

Атрибут `draw_eligibility` (REQ-RWD-014) — свойство розыгрыша, устанавливаемое организатором, а не глобальный параметр; дефолт `guests_allowed`.

## 5. Фазовый план

### Фаза 0 — Walking skeleton
Монорепозиторий (pnpm workspaces + turbo), каркас NestJS, пакет SDK с первыми zod-схемами, полный CI по REQ-DEV-001, Docker-артефакт, health-эндпоинты.
**Критерии выхода:** минимум одна схема контракта с парой фикстур — валидная проходит, невалидная отклоняется, намеренная поломка схемы валит CI; boundary-check ловит специально внесённое нарушение границы и мутабельный module-level экспорт; артефакт собирается и поднимается одной командой.

### Фаза 1 — Ядро
Identity (гости по ADR-004 + Google OAuth по REQ-ID-015, токены по REQ-ID-007/008/016/017), ролевая модель (REQ-ID-011/012/018), Rooms с машиной состояний (REQ-RT-005) и lifecycle-событиями (REQ-RT-010), Membership с политиками входа, кодом комнаты (REQ-ID-013) и backoff (REQ-ID-019), Event log + Realtime-модуль (проекции, уровни видимости включая `appSettings`, per-level replay по REQ-RT-011, лимиты эмиссии/reconnect по REQ-RT-014/015, запечатывание лога REQ-RT-016, fail-closed по REQ-DEV-008), App-registry с манифестом, регистрацией схем событий с уровнями видимости (REQ-CTR-008/009) и проверкой совместимости контракта.
**Критерии выхода:** интеграционные тесты ядра; конкурентный тест назначения seq и его payload-нейтральности (REQ-RT-007); тест late-join через replay; тест видимости — `module-private` данные состояния, событий **и `appSettings`** недоступны участнику ни по одному каналу (REST, realtime, replay), включая отсутствие утечки метаданных seq; тест отказа фиксации события при `visibility` слабее задекларированного для типа (REQ-CTR-009); тест пина `(appId, manifestVersion)` при ACTIVE (REQ-RT-004); тест запечатывания лога в терминальном статусе (REQ-RT-016); тест переиздания токена при kind-флипе (REQ-ID-017); тест хард-лимита эмиссии и reconnect-бэкоффа (REQ-RT-014/015); тест немедленного отзыва подписки при исключении (REQ-SEC-003); тест единообразия ответа входа при закрытой политике (REQ-ID-013); fail-closed тест при недоступности БД.

### Фаза 2 — Quiz (первый app-модуль)
Валидирует наиболее рискованные примитивы: `module-private` хранение вопросов и ответов (включая `appSettings`), арбитраж «кто первый» по логу с анти-упреждающим контролем (REQ-RT-013), late-join участника и зрителя (роль SPECTATOR), регистрацию и валидацию app-схем событий с уровнями видимости. Счёт раундов — в состоянии модуля; начисления rewards подключаются в фазе 3.
**Критерии выхода:** приёмочные e2e-сценарии квиза проходят; **чит-тест** — участник не может получить правильный ответ ни через REST, ни через realtime, ни через replay, ни по метаданным seq, **ни через проекцию `appSettings`**; **анти-бот-тест** — ответ в субчеловеческом темпе отклонён (REQ-RT-013); тест payload-нейтральности гонки за seq (REQ-RT-007).

### Фаза 3 — Rewards + Lottery
Модуль rewards (REQ-RWD-001…005, 007, 009…014): призы и начисления, очное вручение и отзыв (автомат `AWARDED → FULFILLED | REVOKED`); лотерея с CSPRNG-розыгрышем и eligibility; перевод квиза на начисления rewards.
**Критерии выхода:** e2e лотереи; транзакционные тесты награждения — конкурентный дубль-запрос не создаёт двух победителей и не теряет quantity; **`K > quantity` конкурентных наград разным identity не перевыпускают фонд и не уводят quantity в минус (REQ-RWD-010)**; повторное вручение идемпотентно; двойной отзыв не возвращает quantity дважды (REQ-RWD-007); **непредсказуемость розыгрыша из наблюдаемого состояния (REQ-RWD-011)**; **eligibility розыгрыша — при `verified` гости не имеют веса (REQ-RWD-014)**; **приостановка TTL гостя при открытой `AWARDED` (REQ-RWD-013)**; невручённые награды видны организатору при завершении комнаты (REQ-RWD-009).

### Фаза 4 — Закалка и продукт
Архивация логов завершённых комнат (REQ-RT-008), полный набор rate-limits и лимитов payload, аудит и лимиты действий модератора (REQ-ID-018), глобальный backoff перебора кода (REQ-ID-019), security-заголовки (REQ-SEC-008), метрики (REQ-OPS-004), бэкап-регламент с проверкой restore (REQ-OPS-006), нагрузочный тест живой комнаты, продуктовый UI платформы.
**Критерии выхода:** нагрузочный отчёт с достигнутыми порогами: p95 латентности `publish → deliver` ≤ порог, доля ошибок фиксации ≤ порог, полный replay комнаты целевого профиля ≤ порог (ориентир профиля: 100 участников, всплеск ответов в пределах секунды); security-требования реестра закрыты полностью; проверенная процедура восстановления из бэкапа.

### Отложенная фаза (опцион, вне MVP) — заочные награды и верифицируемость
Активируется подтверждённым спросом (ADR-007, ADR-010): claim-автомат (состояние CLAIMED), сбор и защита контакта победителя (реактивация REQ-RWD-006), возврат невостребованного (реактивация REQ-RWD-008), параметр `claim_window`, инвариант `guest_ttl ≥ claim_window`, приостановка TTL гостя при открытом claim; публично-верифицируемый розыгрыш (реактивация REQ-RWD-012); привязка `verified`-веса к дефицитному внешнему ресурсу (REQ-RWD-014). Расширение выполняется аддитивной эволюцией контракта (REQ-DEV-007); схема данных фазы 3 не должна ему препятствовать.

## 6. Задание для проектной сессии

**Роль:** архитектор-проектировщик платформы MyMozhem v2, работающий по SDD: нормативный реестр v1.2 — источник истины, отклонения — только через ADR.

**Входы:** настоящий пакет v1.2; приложение «Выжимка v1» (Prisma-схема прототипа, механизм версионирования манифеста, перечень e2e-сценариев). Репозиторий прототипа v1 — вспомогательный источник; при отсутствии доступа выжимки самодостаточны. Автоматический перенос кода из v1 запрещён; выемка — только образцов, поименованных в выжимке.

**Порядок работ:**
1. **SDK-контракт ядра.** Zod-схемы: identity (kind, PII-проекция), room + машина состояний REQ-RT-005, membership + ролевая модель REQ-ID-011, событие лога с уровнями видимости и schemaVersion, манифест приложения (включая вложенную JSON Schema `appSettings` с **per-property visibility** REQ-CORE-008 и реестр схем событий с **per-type visibility** REQ-CTR-008/009), контракт rewards (фонд, автомат награды, eligibility REQ-RWD-014). Первые контрактные фикстуры, включая невалидные (в т.ч. событие с `visibility` слабее задекларированного).
2. **Prisma-схема ядра** (PostgreSQL-схема `core`): таблица лога REQ-RT-001; partial unique index по REQ-ID-001 и REQ-RWD-003 — SQL-миграцией с автотестом (REQ-DEV-006); инвариант фонда REQ-RWD-010 (`CHECK` + ограниченный декремент); политики удаления; анонимизация вместо удаления identity (REQ-ID-014) с приостановкой по REQ-RWD-013.
3. **Конфиг-схема** по §4 с инвариантами (REQ-OPS-003).
4. **Скелет фазы 0** по фазовому плану.

**Ограничения:**
- Не проектировать: мультитенантность, marketplace, billing, поддержку сторонних разработчиков (ADR-001); несколько реплик (REQ-OPS-005); заочные награды и верифицируемый розыгрыш (ADR-007, ADR-010).
- Следовать ADR-001…011 и ADR-005a; при несогласии — сформулировать новый ADR и остановиться для решения, не реализовывать молча.
- Стиль работы: пошаговый диалог, одно решение за раз, честный разбор trade-offs перед выбором; при неоднозначности — вопрос вместо тихого допущения.

**Готовность первого результата:** SDK-схемы ядра компилируются и покрыты фикстурами (валидные проходят, невалидные отклоняются); Prisma-схема ядра проходит `prisma validate`, partial unique index подтверждён автотестом в БД; конфиг-схема отвергает нарушение инварианта «гостевой `refresh_token_ttl` ≤ `guest_ttl`»; фаза 0 удовлетворяет своим критериям выхода.
