# Приложение к пакету v1.0 — Выжимка v1

Назначение: самодостаточные входные материалы проектной сессии для случая, когда доступ к репозиторию `aiaiai-copilot/mymozhem-platform-mvp` не гарантирован (AUD-033). Это **образцы для выемки паттернов**, а не код для переноса. Автоматический перенос запрещён (ADR-001, задание сессии).

---

## 1. Prisma-схема v1 — что заимствовать, что нет

Схема v1 (`platform/prisma/schema.prisma`, 345 строк, PostgreSQL, cuid-идентификаторы) — сильнейшая часть прототипа. **Заимствуются паттерны**, перечисленные ниже; **не заимствуется структура** (единая схема без multiSchema, User без kind, Prize/Winner в ядре — всё это переработано в v2).

### 1.1. Политики удаления (заимствовать подход)
- Мягкое удаление через `deletedAt DateTime?` на всех доменных сущностях.
- Защита ссылочной целостности через `onDelete: Restrict` на критичных связях: в v1 нельзя жёстко удалить User, создавшего комнаты (даже soft-deleted). Документируется прямо в PSL doc-комментарии с примером корректной последовательности удаления.
- Осознанный выбор Restrict vs Cascade на каждой связи с обоснованием в комментарии.

**Для v2:** тот же подход применить с учётом REQ-ID-014 (identity удаляется анонимизацией, не физически) и REQ-CORE-003 (межсхемные FK на ядро без каскадов).

### 1.2. Индексная стратегия (заимствовать)
- Composite-индексы под конкретные запросы, с комментарием о назначении каждого.
- В v1 присутствуют: `@@index([appManifestVersion])`, `@@index([appId, appManifestVersion])`, `@@unique([provider, providerId])`.

**Для v2:** сохранить дисциплину «индекс + комментарий назначения»; partial unique для REQ-ID-001 — не через PSL, а SQL-миграцией (REQ-DEV-006).

### 1.3. Что НЕ переносить
- `email String @unique` — в v2 заменяется на partial unique по `kind = REGISTERED` (REQ-ID-001).
- Единый `provider @default("google")` в самой строке User — в v2 provider-данные выделены и подпадают под PII (REQ-ID-015, SEC-004).
- Prize / Winner в ядре — в v2 вынесены в модуль rewards (ADR-003).
- Runtime-поля в конфиге комнаты — устранены event log'ом (ADR-005).

## 2. Версионирование манифеста v1 (образец)

В таблице приложения (`App`) v1 реализовано:
- `manifest Json` — текущий манифест приложения.
- `manifestVersion String` — семантическая версия (пример: `"1.2.3"`).
- `manifestHistory Json @default("[]")` — массив предыдущих версий с метаданными.
- В комнате: `appManifestVersion String` — версия манифеста на момент создания комнаты; **лочит комнату к конкретной схеме настроек**. Индексы по версии и по паре `(appId, appManifestVersion)`.

**Для v2:** механизм лока комнаты к версии манифеста переносится концептуально и расширяется: манифест теперь несёт вложенную JSON Schema для appSettings и реестр zod-схем событий (REQ-CTR-008); совместимость версии контракта проверяется при регистрации (REQ-CTR-004). `manifestHistory` как паттерн хранения версий — пригоден; для событий лога добавляется отдельный `schemaVersion` в конверте (REQ-RT-001, REQ-DEV-007).

## 3. Перечень e2e-сценариев v1 (приёмочные спецификации, REQ-DEV-005)

Playwright-сценарии прототипа, переиспользуемые как приёмка соответствующих фаз v2. Сгруппированы по исходным test-suite. Идентификаторы вида TS-* — из v1.

### Платформенные (→ фаза 1)
**TS-P-001 Platform Authentication API:** password login success; invalid credentials; logout; get current user; unauthorized; invalid token.
*В v2: password-login заменяется гостевым входом + OAuth; сценарии unauthorized/invalid-token сохраняются как есть.*

**TS-P-002 Google OAuth API:** get OAuth URL; URL с redirect-параметром; callback без кода → ошибка.
*В v2: расширить проверкой state/nonce (REQ-ID-009) и запретом токенов в URL (REQ-ID-008) — в v1 токен шёл фрагментом, это анти-паттерн.*

### Лотерея (→ фазы 1 и 3)
**TS-L-001 Authentication Flow:** login success/fail; logout; auth-state persistence; redirect на login для защищённого маршрута; redirect назад после login; несколько пользователей в разных сессиях.

**TS-L-002 Google OAuth UI:** кнопка видима/кликабельна; ошибка OAuth показывается; callback-страница loading; обработка token-фрагмента; сохранение redirect после ошибки; разделитель OAuth/email.
*token-фрагмент в v2 не применяется (REQ-ID-008).*

**TS-L-005 & TS-L-007 Room Actions:** join как участник; нельзя войти в DRAFT-комнату; список участников показывает роли; удаление комнаты организатором; отмена подтверждения удаления; не-организатор не видит кнопку удаления.
*«роли в списке» — прямо валидирует REQ-ID-011.*

**TS-L-003/004 Room Management/Status:** (управление и статусы комнаты) — переиспользовать для машины состояний REQ-RT-005.

**TS-L-006 Winner Draw (→ фаза 3):** одиночный розыгрыш (happy path); несколько победителей последовательно; нет подходящих участников; нет доступных призов; персистентность после reload; уменьшение quantity после розыгрыша; только организатор может разыгрывать.
*Прямо валидирует REQ-RWD-003 (атомарность, quantity) и ролевую модель. В v2 дополнить конкурентным тестом (дубль-запрос) и автоматом вручения/отзыва (REQ-RWD-007, очное вручение по ADR-007).*

**TS-L-008 WebSocket Real-Time Events:** participant joined (realtime); winner selected (broadcast); prize created (realtime); multi-user sync.
*Основа тестов Realtime-модуля; в v2 дополнить late-join через replay, per-level видимостью, немедленным отзывом подписки (REQ-SEC-003).*

### Квиз (→ фаза 2)
**TS-Q Authentication / Quiz Flow / Quiz Gameplay / WebSocket Events:** аутентификация; поток квиза; геймплей; realtime-события квиза.
*Ядро фазы 2. Критический дополнительный тест, отсутствующий в v1 — **чит-тест**: участник не получает correctIndex ни по одному каналу (в v1 этот дефект и присутствовал).*

## 4. Явные анти-паттерны v1 (не воспроизводить)

Краткий список того, что в v1 сделано и в v2 запрещено нормами — чтобы выемка образцов случайно не втянула дефект:
- Демо-логин с хардкод-паролем в production-пути (REQ-SEC-001).
- Токены в URL-фрагменте + localStorage (REQ-ID-008).
- Refresh-токены в plaintext без ротации (REQ-ID-007).
- OAuth state без nonce (REQ-ID-009).
- `correctIndex` в отдаваемом наружу appSettings (REQ-CORE-005).
- Runtime-состояние (`currentQuestionIndex`) в мутабельном appSettings; арбитраж в in-memory Map (ADR-005, REQ-CORE-004).
- email любому аутентифицированному через `GET /users/:id` (REQ-SEC-004).
- Бизнес-логика в роут-хендлерах, отсутствие сервисного слоя (REQ-CORE-006).
- Winner-выбор без транзакции (check-then-act) (REQ-RWD-003).
