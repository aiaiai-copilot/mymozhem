**Открытые вопросы владельцу (подняты срезом ф.3, НЕ решены — не решать молча; подробности со статусами — exit-аудит §6):**
- **C-9.1 (REQ-RWD-014):** defaulted-поле appSettings недостижимо через configure — `z.toJSONSchema` в output-режиме (defineApp не передаёт io) делает defaulted ключ required в JSON Schema-артефакте, гейт ядра verdict-only → `{}` отклоняется с AppSettingsInvalidError; дефолт живёт только в zod-parse handler'а. Fail-closed, безопасно, но «значение по умолчанию guests_allowed» по факту = «клиент обязан передать явно». Развилки: `io: 'input'` в toRegisteredSchema (SDK) ИЛИ применение дефолтов ядром — обе задевают принятый контракт SDK 1.6.0 → решение владельца.
- **Свипнутый гость остаётся в drawPool:** свип анонимизирует identity, membership не трогает → TTL-истёкший гость может выиграть (фонд списан, award на обезличенную identity, displayName null). `identity: { deletedAt: null }` в listActiveParticipantPool — решение владельца/дизайна. Окно: розыгрыш >25ч после join; фонд восстановим revoke'ом.
- **D-12.2 (семантика revoke vs winner-exclusion):** частичный индекс БД разрешает re-award после REVOKE, но редьюсер лотереи не забывает draw.completed → отозванный победитель навсегда вне пула этого приза. Продуктовое решение: должен ли revoke освобождать победителя для повторного розыгрыша? Текущее поведение fail-safe (двойной выигрыш одного лица невозможен).
- **Окно гонки свипа (ruling C-8.1, принятый риск MVP):** award, закоммиченный между гард-чеком и коммитом свипа, не увиден (гард читает вне tx). Закрытие (tx-aware гард / serializable+retry) — design-level, кандидат на ф.4.
- **Шов registered-join по HTTP отсутствует** (ruling D-12.1): JoinController игнорирует Authorization и всегда создаёт GUEST. Не дефект (в MVP registered играют через OAuth+? — продуктовый вопрос), но e2e registered-сценарии сидят membership на уровне БД. Задел — при появлении требования.
