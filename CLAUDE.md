# CLAUDE.md — инструкции агенту для репозитория MyMozhem

Этот файл читается автоматически при старте Claude Code в репозитории. Он задаёт рамку, внутри которой работают агент и плагин superpowers.

---

## 1. Что это за проект

MyMozhem — платформа для приложений-конкурсов (квизы, лотереи, дегустации) на живых и асинхронных событиях. Единый Docker-артефакт; ядро даёт примитивы (identity, комнаты, членство, realtime, реестр приложений), механики — подключаемые app-модули.

**Этап:** MVP (перепроектирование после негодного прототипа v1). Траектория: прототип → **MVP** → платформа → BaaS/SaaS. На каждом этапе — без оверинжиниринга и забегания вперёд.

**Метод:** AI-Driven / Specification-Driven Development. Спецификация в `docs/` — источник истины и вход для агента.

## 2. Источник истины и незыблемые правила

- **Главный документ:** `docs/spec/normative-package-v1.2.md` — 11 ADR, ~90 требований (RFC 2119), модель угроз, параметры, фазовый план. Это утверждённая спецификация, прошедшая независимый аудит и red-team.
- **Дорожная карта:** `docs/roadmap.md` — этапы, разметка «что окупается на MVP / что задел / что упростить», порядок контролей качества.
- **Точка входа для сессии:** `docs/sessions/handoff-to-aidd-session.md`.

**Правила, не подлежащие нарушению:**
1. **Принятые решения не переоткрываются походя.** ADR-001…011 приняты после аудита и red-team — это текущие лучшие решения, а не догма. Их МОЖНО пересматривать, но пересмотр стоит дороже принятия: чтобы тронуть принятый ADR, нужно сформулировать, что изменилось или было упущено, и оформить это как предложение нового ADR в `docs/adr/` для решения владельца (REQ-DEV-004) — не свободным обсуждением по ходу. Вся остальная архитектура (SDK-контракт, схема БД, внутренняя структура модулей, ещё не принятые развилки) активно проектируется — это открытая работа, а не запретная зона.
2. **Границы принуждаются машиной, не соглашением** (ADR-002, REQ-DEV-001): boundary-check (dependency-cruiser / eslint-boundaries) в CI обязателен с первого коммита. App-модуль общается с ядром только через SDK.
3. **Не забегать вперёд** (roadmap): не создавать директорий, модулей, схем под отложенные возможности (заочный claim, мультитенантность, второй транспорт, VRF-розыгрыш). Точка расширения фиксируется словами в ADR, не пустым кодом.
4. **Сессионные артефакты** (планы, handoff, промпты) — в `docs/sessions/`, не в корне (REQ-DEV-003).
5. **Один lockfile** на монорепо (REQ-DEV-002).

## 3. Интеграция с superpowers — ключевой раздел

В этом репозитории используется плагин **superpowers** (obra/superpowers): brainstorm → plan → TDD → двухстадийное ревью. Плагин и данный проект идейно совпадают — оба принуждают процесс машиной, а не пожеланием. Но их надо согласовать по уровням, иначе brainstorm плагина будет пытаться переоткрыть уже утверждённую архитектуру.

### Принцип: brainstorm везде, но пересмотр принятого стоит дороже

Superpowers-brainstorm работает на всех уровнях, включая архитектурный, — и это правильно: впереди большой пласт архитектурного проектирования (SDK-контракт, схема ядра, структура модулей, проекции Realtime), и вдумчивый brainstorm перед кодом здесь ценнее всего. Ничего не отсекается по признаку «это архитектура». Различие проходит не по уровню, а по статусу вопроса:

- **Открытый вопрос** (не решён ни одним ADR, либо помечен как развилка): brainstorm в полную силу, приветствуется. Сюда входит бóльшая часть предстоящей архитектуры — проектирование контракта, схемы, внутренностей модулей, ещё не принятые развилки (pnpm/nx, кандидаты на упрощение MVP). Это основная работа, а не запретная зона.
- **Уже принятое решение** (ADR-001…011): brainstorm НЕ запрещён, но пересмотр стоит дороже принятия. Реализация может вскрыть, что принятое решение где-то не сходится, — это законный сигнал, а не бунт; поднимай флаг. Но чтобы тронуть принятый ADR, требуется порог: сформулировать, ЧТО изменилось или было упущено, и оформить как предложение нового ADR для владельца — не пере-litигировать взвешенное свободным разговором по ходу задачи.

Практическое правило для агента: **прежде чем brainstorm, спроси не «это архитектура?», а «это решено или открыто?».** Открыто — brainstorm свободно. Решено — brainstorm допустим, только если у тебя есть конкретное новое основание; тогда путь один — предложение ADR и остановка для решения владельца. Нет нового основания — не переоткрывай, строй в рамках принятого.

Порог асимметричен намеренно: он отсекает капризное переоткрытие уже взвешенного, но остаётся проходимым, когда основание весомое (реализация обнаружила противоречие, новый факт, упущенный вектор). Так система и защищена от пере-litигации, и способна поймать реальную ошибку в принятом решении — ровно как это уже случалось (аудит развернул часть v0.2, red-team добавил 4 ADR, продуктовая ревизия отменила заочные награды).

### Привязка навыков superpowers к требованиям проекта

Не создавай параллельных процессов — срасти навыки плагина с требованиями пакета:

- **TDD superpowers** = контрактные тесты и фикстуры проекта (REQ-CTR-005, REQ-DEV-001). Тесты пишутся первыми; для контракта — из zod-схем SDK.
- **Двухстадийное ревью superpowers** (spec-compliance → code-quality): первая стадия сверяется с **конкретными REQ-\***, которые задача реализует, а не с абстрактной «спекой». В плане задачи явно перечисляй, какие требования она закрывает — ревью проверяет именно их.
- **План superpowers** сохраняется в `docs/sessions/` (REQ-DEV-003), не в корне.

### Порядок при типовой задаче реализации

1. Определи статус вопроса (см. выше). Затрагивает принятый ADR без нового основания — не трогай, строй в рамках. Есть новое основание против ADR — предложи новый ADR, остановись для владельца. Открытый вопрос — дальше по списку.
2. Определи, какие REQ-* закрывает задача, и к какой фазе плана (roadmap / §5 пакета) она относится.
3. Brainstorm уровня реализации: edge cases, структура, тесты.
4. План с явным списком затрагиваемых REQ-* → в `docs/sessions/`.
5. TDD: тесты (контрактные/unit) первыми.
6. Реализация внутри границ модуля.
7. Двухстадийное ревью: спек-комплаенс против перечисленных REQ-*, затем качество кода.
8. Убедись, что CI-гейты (boundary-check, контрактные тесты, lint, type-check) зелёные.

## 4. Целевой стек (ADR-006)

NestJS (Fastify-адаптер) · Prisma (PostgreSQL, `multiSchema`, схема на модуль) · zod-контракт в SDK-пакете как единственный источник истины (TS-типы + runtime-валидация + REST DTO + payload'ы событий + манифест) · Socket.io за Realtime-контрактом ядра · pnpm workspaces + turbo или nx — **развилка фазы 0, ещё не решена** (см. handoff §6.5).

**Партиклярности реализации, которые агент должен помнить:**
- Частичные уникальные индексы (REQ-ID-001, REQ-RWD-003) — SQL-миграцией с автотестом наличия индекса, БЕЗ preview-функции Prisma `partialIndexes` (REQ-DEV-006).
- Ограниченность призового фонда — DB-инвариант (`CHECK` + атомарный ограниченный декремент), не проверка перед записью (REQ-RWD-010).
- Уровни видимости строит ядро, не ручная фильтрация в обработчиках (REQ-CORE-005/008).
- Идентификатор актора — только из аутентифицированного контекста соединения, не из payload (REQ-RT-009).
- Одна реплика приложения (REQ-OPS-005); никакого глобального мутабельного состояния процесса (REQ-CORE-004).

## 6. Открытые вопросы (не решать молча — эскалировать владельцу)

Полный список — в handoff §6. Критичные:
1. **Юридика PII/лотерей** — потенциально терминальный гейт; решается живым юристом, не агентом. Агент может лишь готовить список вопросов. Не блокирует фазу 0 (каркас), блокирует уверенный старт работы с реальными PII.
2. **Продуктовые ставки** (нагрузочный профиль, гостевой доступ, дегустации) — не валидированы; проверяются реальностью, не кодом.
3. **Развилка pnpm+turbo vs nx** — первая техническая, решается в начале фазы 0.
4. **Кандидаты на упрощение для MVP** (roadmap §2): REQ-RT-011, REQ-RT-014/015, REQ-ID-019 — не тянуть в фазу 1 без подтверждения владельца.
